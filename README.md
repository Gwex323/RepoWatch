# RepoWatch

单用户、本地运行的多 Agent 工作台。第一阶段已实现 OpenAI Agents SDK 的真实
handoff、人工复现关卡、持久化状态与跨进程恢复。

## 当前范围

- Python + OpenAI Agents SDK 0.23.1，注册六个角色。
- FastAPI + SQLite 后台，React + TypeScript WebUI。
- 本地管理密码、会话校验、同源限制与 CSRF 校验。
- 系统发现样例：发现分页问题，人工操作复现，确认后恢复 SDK 执行。
- 已有 Issue 样例：自动验证后直接进入修复与审查，不要求人工复现，不重复生成 Issue。
- 可查看交接记录、预定义样例补丁、五项样例断言和本地 Issue/PR 草稿。
- 任务状态保存在数据库中；重启后可以继续等待确认或恢复已确认任务。
- 共享仓库记忆：按仓库和代码版本隔离，包含手工知识、复现记录及样例修复经验。
- 可登记 GitHub 仓库链接，下载固定提交的源码，并在本机 Docker 中安装、测试与运行。
- 可在运行配置中连接多个 GitHub 账号，校验身份、切换当前账号、更新令牌和解绑。
- 可检查已登记仓库是否能被指定账号的令牌读取；不会把读取成功当作写入授权。
- 测试或启动结束后自动排队分析源码与执行结果，保存疑似问题、代码依据和复现步骤。
- 可在 WebUI 配置仓库分析模型；未配置时任务等待，启用后自动继续。
- 可同步真实 GitHub Issue，按仓库和 Issue 编号去重，并可基于 Issue 发起源码分析。
- 后台每日自动同步已登记 GitHub 仓库的未关闭 Issue；同步只读取，不修改 GitHub 数据。
- 每个 GitHub 仓库可配置本地时间每日巡检；巡检复用现有下载、执行、分析和
  Issue 同步流程，不会自动修复、发布或合并。
- 仓库页提供每日巡检总览，集中查看各仓库的巡检时间、最近调度状态、失败详情
  和跳过原因；未启用巡检的仓库不会被隐藏。

**样例流程使用确定性的测试响应，默认不调用外部 LLM。** SDK 的 Agent、Runner、
handoff、审批中断和恢复是实际执行的；样例问题及补丁是预先定义的。
真实仓库分析和环境故障诊断可单独启用真实模型，见下方配置。
已接入真实仓库的受控自动修复与发布：仅对本人确认复现的问题执行，
先在隔离源码副本中修改并运行新增回归测试、完整测试，再经过独立审查，
由后端创建带标记的 Issue 和 PR。默认开关关闭，启用后不再逐问题审批；
PR 合并仍由项目拥有者在 GitHub 中完成。

以下能力尚未启用：自动合并操作。
任何自动合并操作均不在系统权限内。

## GitHub 账号连接

进入“运行配置 → GitHub 账号 → 连接账号”，填写 GitHub 用户名和该账号的
Personal Access Token，点击“验证并连接”。页面提供 GitHub 令牌管理入口。
这里只校验 GitHub 身份和仓库读取，不要求预先授予发布或合并权限。

- 后台向 GitHub 请求真实身份；用户名不匹配时不保存，首次连接不自动导入 `gh` 登录。
- 可以保存多个账号，同时选择一个当前账号。切换前重新校验，失败保留原有选择。
- “更新令牌”用于授权过期、撤销或更换令牌；提交后输入框立即清空。
- “检查访问”只验证所选已登记仓库可读取，写入权限明确显示“未核验”。
- 细粒度令牌未返回传统权限范围时显示“GitHub 未返回”，不推断它拥有全部权限。
- 解绑删除本地连接及加密令牌；解绑当前账号后不自动切到其他账号。
  解绑不会撤销 GitHub 上的令牌，需要撤销时在 GitHub 设置中处理。

令牌使用 Fernet 加密后保存在 SQLite，独立加密密钥保存在本机系统凭据库。
Windows 使用凭据管理器；Linux 需要可用且已解锁的 Secret Service。
系统凭据库不可用时不会退回明文文件。数据库备份本身不包含解密密钥，
迁移到新主机后需要重新连接账号。账号凭据不进入 Agent 上下文或仓库记忆。

当前提供访问令牌连接，尚未提供浏览器 OAuth/设备码登录或自动同步 GitHub CLI。
连接账号后可在仓库页面下载源码；不会自动启用真实 Issue 接入、Issue/PR 发布或自动合并。
发布能力需在“运行配置 → 自动修复”中启用，并以令牌的实际权限为准。
详见 [账号绑定设计记录](docs/adr/0014-github-account-binding.md)。

## 仓库下载与运行

1. 在仓库中打开“管理运行环境”。“下载后自动准备环境、测试、启动并分析”默认勾选，
   点击“下载最新版本”后，后台持久化执行整条流水线：
   **下载 → 准备环境／复用依赖 → 自动测试 → 测试通过后启动 → 检查 HTTP 地址 → 分析运行结果**。
2. 系统识别 Python、Go 和 npm / TypeScript 命令；Python 通过 AST 静态识别常见
   FastAPI 入口，不会在宿主机导入源码。需要的命令未配置时，流水线停在“等待补齐配置”。
   对“运行配置”进行补齐并保存后继续；测试失败不会自动启动，也不会把零测试视为通过。
3. 安装默认不联网。请在运行配置中明确允许下载依赖；本仓库、同一 GitHub 身份下
   保存过的配置差异会沿用到后续下载，页面会提示沿用安装联网选项。私有依赖不会获得
   GitHub 凭据。测试始终断网，项目运行使用隔离网络。
4. 服务必须监听 `0.0.0.0` 和配置端口。启动成功后检查固定本机预览地址的 HTTP 响应，
   不携带管理 Cookie、GitHub 凭据，不跟随重定向，也不保存响应正文。
   需要认证的 401/403 会标明“项目需要登录”，不代表已验证登录后的功能。
5. 纯测试或命令行项目需明确选择“仅测试项目”，通过测试后跳过服务和地址检查，
   进入结果分析；没有测试命令、没有启动命令都不会被默认为成功。
6. 关闭自动执行勾选可以只下载，继续使用独立的“安装环境”“执行测试”“启动项目”按钮。
   当前环境已有安装和通过的测试时，可用“从当前结果继续流水线”跳过有效的前置步骤。
   点击停止会取消整条链，之后不会因晚到的任务结果重新开始下一步。

### 配置保存不会无条件清空有效结果

- 仅改启动命令、端口或运行类型：保留已安装依赖、镜像和有效测试，清除旧访问检查。
- 改测试命令：保留安装，只清除测试及访问结果。
- 改语言、安装命令或安装联网选项：重新准备环境并重新测试。
- “保存并继续流水线”在同一个事务内保存配置并安排下一步，避免先触发分析再启动。
  旧分析仍保留，但会按完整配置标记过期；新的分析可引用仍有效的安装/测试日志。

模型未配置时，流水线在分析步骤等待，不调用替代模型。任务状态、步骤、错误和关联
执行记录保存在数据库，重启不会盲目重放已中断的命令。项目启动后最多保持 30 分钟。
详见 [自动执行流水线](docs/adr/0020-automatic-execution-pipeline.md)。

Docker Desktop 必须已启动并使用 Linux 容器。首次安装按语言下载官方镜像。
镜像固定为 Python 3.13、Go 1.25、Node.js 24 的 Debian 配置，实际使用的镜像
内容 ID 会随环境记录保存。命令仅在非 root、受资源限制的项目容器中执行。
Python 虚拟环境位于 `/workspace/home/venv`，项目目录为 `/workspace/project`。

安装和测试每次最多 10 分钟。源码、配置、命令结果和日志会保留；重新安装会重建
项目数据卷，清理按钮则删除该环境的源码、数据卷和网络。当前需要手工清理旧环境，
尚无数据卷总磁盘配额。允许安装联网时采用普通 Docker bridge，能访问可达网络服务。
项目启动后的网络由独立预览转发提供访问，不直接连接外部网络。

### 新版本与依赖复用

“下载最新版本”仍会校验账号并取得固定版本源码。若提交、源码内容均与同账号下
已安装且空闲的环境一致，会保留下载审计记录并返回原环境，沿用原配置，无需重复安装。
已删除、未安装、忙碌或源码不匹配的环境不会用于此复用。

新提交仍建立独立运行环境。点击“安装环境”时，会检查同仓库、同 GitHub 身份、
同镜像内容 ID、同安装命令与依赖输入的只读快照；命中后复制依赖到新数据卷，
同时使用本次下载的新源码，不运行重复的安装命令，也不继承旧版本测试结果。
页面会显示“依赖未变化”；新版本仍需重新执行测试。

本阶段支持保守可确认的安装：Python 纯 requirements 文件中的固定版本依赖、
无本地替换/工作区的 Go 模块，以及无生命周期脚本、本地或 Git 依赖的 npm ci 锁文件安装。
本地 Python 打包、可变版本范围、构建钩子、自定义命令等无法确认输入的情况仍完整安装。
缺失、不可读取或归属不符的快照会安全回退，不会改写或删除其他工作台的数据卷。

快照在成功安装后、任何测试或项目运行前保存；不从旧的可写运行环境反向补建。
每个仓库/账号最多三个快照槽位，满额时回退正常安装，目前不自动淘汰。
清理运行环境不会删除这些独立快照。首次安装及尚无兼容快照时仍需完整安装。
详见 [环境恢复与依赖复用](docs/adr/0019-environment-recovery-reuse.md)。

当前下载的是 GitHub 固定版本源码归档，不含 Git 历史、子模块或 LFS 实体。
含链接或不安全路径的归档会被拒绝；大型仓库、复杂多服务项目、非标准依赖可能需要
后续支持。下载上限为压缩 32 MiB、源码 128 MiB、20,000 条归档记录。
项目预览使用 `127.0.0.2`，与管理页面的登录 Cookie 隔离。

安装失败和测试失败只作为执行结果，不会直接创建问题、开始修复或提交 PR。
真实疑似问题由后续 Agent 源码分析产生，不能把失败本身当作已复现的项目缺陷。
详情见 [仓库执行设计记录](docs/adr/0015-repository-execution.md)。

## 自动分析与疑似问题

1. 在“运行配置 → 仓库分析模型”填写模型名称、服务地址、API Key 和接口类型，
   勾选“启用仓库自动分析”后保存。保存仅代表配置完成，实际调用时验证服务兼容性。
2. 安装后的测试或启动尝试结束，系统会自动排队分析，不要求先由你打开项目。
   现有执行记录也会在升级后补入队列；没有模型配置时显示“等待模型配置”。
3. Agent 读取限定范围的源码、执行记录和当前仓库同版本记忆，经“仓库分析 →
   问题调查 → 复现辅助 → 独立审查”交接，给出疑似问题、文件行号、依据与复现步骤。
4. 工作台提醒有待复现的问题时，你再操作目标项目，并在该仓库的“仓库自动分析”
   面板直接点击“复现成功”或“未能复现”，复现说明选填，无需重复勾选。
   点击“复现成功”即本人明确确认；旧配置或旧执行结果的报告不能确认新问题。

新分析会单独带入同仓库历史报告中“待人工复现／复现成功”的问题（不要求同一版本），
优先带入已人工确认的问题，每轮最多 8 项。页面逐条显示“仍存在、已修复、疑似误报、
本轮未覆盖”及当前源码依据；没有返回结论的条目和超出数量上限的部分均明确记为未覆盖。
历史描述会做长度限制与脱敏；重试复用同一份历史快照。旧报告不会被追溯改写。
这些是模型复核意见，不会覆盖原人工确认、自动重排修复或发布。没有新发现不等于旧问题
已解决；“已修复”也不是已执行新的回归复现。详见 ADR 0021。

这是工作台自身的模型配置，与目标项目的聊天模型无关。支持 Responses 与
Chat Completions 兼容服务；模型需支持工具调用及结构化输出。密钥通过系统凭据库
支持的加密存储保存，不进入目标容器，也不会回显。更换服务地址需要重新填写密钥。
DeepSeek 官方 Chat Completions 接口（`https://api.deepseek.com`，也支持 `/v1`、`/beta`）
自动采用兼容模式：所有阶段关闭思考，保留真实工具调用与强制交接；报告请求使用
JSON Object，并继续在本地严格校验字段和源码证据。此模式下保存的推理强度不生效，
页面会说明；普通工具与交接不启用服务端 Beta strict 模式。已有配置无需重新保存密钥，
更新后重启后台服务，再手动重试失败分析即可；旧失败记录不会自动消失。
启用分析后会向所选服务发送限定范围的源码、日志、记忆和历史问题描述；自动脱敏并不能识别所有秘密。

本阶段读取既有运行记录，不自动执行模型生成的测试或浏览器探索。源码数量、大小和
读取次数均有限制，报告会显示覆盖范围。SDK 工具与交接已通过测试模型验证；
真实模型已参与主流程的端到端验收；其他模型服务仍需分别确认工具调用与结构化输出
兼容性。确认后的真实问题会进入自动修复队列，
详见 [自动分析设计记录](docs/adr/0017-repository-analysis.md)。

## 自动修复与发布

1. 在“运行配置 → 自动修复”启用“自动修复并提交 Issue / PR”并保存。
   复用已启用的仓库分析模型，以及当前选定的 GitHub 账号。
   升级时默认关闭；已有且仍有效的复现确认会补入队列，不会自动扣费或发布。
2. 对系统发现的问题点击“复现成功”后，队列自动继续，不再逐操作审批。
   修复 Agent 只能修改已读取、哈希匹配的源码，并新增回归测试；
   本阶段不能修改既有测试、依赖清单、CI 或凭据文件。
3. 原版本测试、新增回归测试的修复前失败、修复后通过及完整测试结果会保存。
   测试在单独的 Docker 环境运行，不改动用于本人复现的原始源码或环境。
   独立审查 Agent 通过原生 handoff 检查实际差异和测试记录，否决则不发布。
4. 验证通过后，后端向固定版本对应的专用分支提交，并创建 Issue 与 PR。
   没有上游写权限时，只支持允许 fork 的公开仓库；不会覆盖已有同名无关仓库。
   远程默认分支已变化会停止，需重新下载、分析和复现。
5. 工作台显示补丁、测试日志、审查、历史尝试及 Issue/PR 链接。
   失败可在当前证据有效时重试，单问题最多 3 次、每轮最多 30 分钟。
   已验证补丁的发布重试会先核对远程记录，避免重复创建。

GitHub 令牌需要相应内容、Issue、PR 权限；读取成功不代表可发布。
所有合并由项目拥有者在 GitHub 操作，本系统没有合并或自动合并接口。
修复副本与记录暂时保留在本机，尚无自动磁盘配额或清理策略。
真实修复经验在 owner 标记“已解决”且修复 PR 合并核验通过后自动写回共享记忆；
每条经验绑定来源修复任务、PR 与代码版本，重复处置不会重复写入；内容同时保留
问题、修改、路径、回归测试、验证、审查和 PR 的结构化字段。
owner 手动断言解决不写修复经验，避免无可验证修复内容的记录污染后续分析。
主流程已在本机 Windows 环境完成真实模型与真实 GitHub 写入的端到端验收，覆盖
GitHub 账号连接、仓库导入与下载、测试、源码分析、人工复现以及 Issue 和 PR 创建。
模拟模型、模拟 GitHub 和真实 Docker 自建样例继续用于回归验证。此项验收不代表
其他仓库、模型服务或操作系统组合均已验证。
详见 [自动修复设计记录](docs/adr/0018-automatic-repair.md)。

### Docker 预检等待与恢复

新修复在调用模型前发现 Docker 不可用时，进入“等待 Docker 环境”，不增加修复次数。
系统以 5 秒起、最多 60 秒的退避周期检查环境。Docker 恢复后，只有自动修复和模型
仍启用、本人确认/执行证据仍有效、绑定身份和源码仍匹配时，才继续已授权的任务。
等待期间关闭自动修复或模型会暂停续跑。GitHub 发布权限失败不属于此自动恢复范围。

页面每十秒刷新当前 Docker 状态；旧任务的失败原因明确标为“上次失败”，不会假装
历史失败从未发生。模型或测试已开始后的 Docker 故障仍保留失败证据，不盲目自动重放。

升级不自动唤醒已有失败任务。对能证明在模型调用前直接因 Docker 预检失败、且没有
补丁或模型/工具执行记录的旧任务，恢复 Docker 后可手动“继续修复”一次，归还那次
预检占用的机会。原尝试序号、失败记录和后续模型次数限制保留，不重置计数。

### GitHub 发布权限与重试

读取仓库成功、账号具有 `push` 权限，都不能证明绑定令牌具有写入权限。
细粒度令牌需要授权目标仓库，并按发布操作授予 `Contents`、`Issues`、
`Pull requests` 的读写权限；仅本仓库直接发布不要求额外的管理权限。
在 GitHub 调整现有令牌权限，或在工作台更新同一账号的令牌后，再手动重试。
不要将令牌粘贴到日志、Issue 或聊天中。

新失败会区分权限不足、其他访问拒绝和限流。修复执行记录只保留白名单诊断：
HTTP 状态、操作类别、接口要求的权限、配额和等待时间，不保存原始响应或令牌。
旧的“权限不足或请求被限流”记录不能追溯判定具体原因。

测试和独立审查已通过、且证据仍有效的发布失败，可以“仅重试发布”，
独立于模型修复次数，最多手动重试三次；保留历史和原补丁，不调用模型或重跑测试。
重试仍校验本人复现、同一 GitHub 身份、源码和上游版本，并核对远程发布记录。
修改代码、审查未通过、证据过期或切换账号都不能借此绕过安全限制。
部署不会自动重试失败任务，也不会自动发布。

## 环境故障诊断

安装、测试或启动失败后，运行环境页面自动显示原因、日志依据和处理建议。
常见错误先通过本地规则分析；例如安装关闭联网时，DNS 失败可能进一步导致
“No matching distribution found”，应先恢复依赖源访问。
“Ran 0 tests”会提示测试收集问题，并根据项目声明提示核对 pytest 与测试依赖，
不会将没有运行测试视为已验证。

有可用配置建议时，点击“应用建议并重新安装”会保存建议并排队安装。
建议绑定失败任务、源码版本和当时的配置；修改配置或重试后，旧建议只能作为
历史记录查看。旧诊断默认收起到“历史失败诊断（非当前故障）”，不再显示重装按钮
或当前诊断进度；依赖已准备会单独标注。安装完成不代表测试或启动一定成功，新的有效
测试／启动失败仍正常显示“失败原因与建议”。诊断本身不执行命令、不修改源码，也不
代替问题复现或测试结果。

复杂故障可启用真实模型诊断，在启动服务的环境中设置：

```powershell
$env:REPOWATCH_DIAGNOSIS_ENABLED = "1"
$env:REPOWATCH_DIAGNOSIS_MODEL = "<模型名称>"
$env:REPOWATCH_DIAGNOSIS_API_KEY = "<专用模型密钥>"
$env:REPOWATCH_DIAGNOSIS_BASE_URL = "https://api.openai.com/v1"
$env:REPOWATCH_DIAGNOSIS_API = "responses"
.\scripts\start.ps1 -Background
```

不要把真实密钥提交到仓库。兼容服务可将 API 模式设为 `chat_completions`；
服务和模型需要支持工具调用及结构化输出。地址只接受 HTTPS 或本机 HTTP。
目前通过启动环境配置，尚无 WebUI 模型配置表单，也不会自动使用通用的
`OPENAI_API_KEY`。修改后需要重启服务，页面会显示是否配置完成。

真实诊断复用三个角色，以 SDK 原生 handoff 依次交接：
`repository_analyst → reproduction_assistant → independent_reviewer`。
输入限于脱敏后的失败日志、执行配置和限定大小的依赖清单，不提供 GitHub
凭据、宿主机执行或发布工具。脱敏不能保证识别所有自定义秘密，启用前应确认
目标项目日志和依赖清单可以发送给选定的模型服务。
调用失败或超时会保留本地建议，避免阻塞环境任务。

WebUI 区分“本地规则诊断”和“模型诊断”。明确的安装断网问题直接给出规则建议，
无需消耗模型调用。SDK 交接已通过测试模型验证；独立的故障诊断流程仍需使用真实
供应商单独验收，主流程的实测不覆盖此诊断入口。
详情见 [故障诊断设计记录](docs/adr/0016-execution-diagnosis.md)。

## Windows 启动

在项目根目录执行：

```powershell
python -m venv .venv
.\.venv\Scripts\python.exe -m pip install -e ".[dev]"
npm.cmd ci
npm.cmd run build
.\scripts\start.ps1
```

启动地址默认是 `http://127.0.0.1:8765`。端口被占用时脚本会选择后续空闲端口。
首次访问需设置至少 10 个字符的本地管理密码，没有预置管理员密码。

后台运行：

```powershell
.\scripts\start.ps1 -Background
```

启动脚本返回进程号、实际地址与数据位置；日志位于 `data/logs/`。
服务只绑定本机回环地址，不应直接暴露到局域网或公网。

## 体验第一阶段

1. 登录后选择“运行样例”。
2. 等待“待人工复现”状态，查看问题证据。
3. 使用总条数 `20`、页码 `3`、每页条数 `10` 执行样例。
4. 检查预期空列表与实际结果，勾选本人已操作复现，再提交确认。
5. 查看“交接记录”和“本地草稿”。确认后的五项断言只针对内置函数。

将页码改为 `1` 时，本次输入不会复现问题，确认成功按钮保持禁用。
提交“未能复现”后，不会生成修复或发布草稿。

这些操作不需要 GitHub 或模型 API 凭据，也不会向 GitHub 发送写入请求。

选择“已有 Issue 样例”可验证另一条路径：后台创建固定来源的内置 Issue 样例，
自动执行复现、修复和五项断言，生成三份本地材料，不出现人工确认表单。
它不是从 GitHub 下载的 Issue，不代表真实 Issue 接入已经完成。

## 来源与审批

- 系统自行发现：必须亲自复现并确认，才能创建 Issue 草稿或开始修复。
- 已有 Issue：无需人工复现，必须通过当前任务的自动验证；之后仍需修复测试和审查。
- 自动验证失败：暂停并在 WebUI 提醒，可重试，不自动转成人工复现关卡。
- 来源由后台入口确定且不可修改；客户端不能提交来源或验证证据来授权。
- 已有 Issue 不重复生成 Issue；两条路径都不提供合并或自动合并功能。
- 旧任务升级后仍按“系统发现”处理，已有快照和人工确认继续有效。

真实系统发现已支持分析报告和个人复现反馈，但修复与发布仍未接入。
已有 Issue 路径仍仅实现受控样例；真实 Issue 身份核验、去重和接入属于后续阶段。
详见 [来源分流设计记录](docs/adr/0013-origin-dependent-reproduction.md)。

## 仓库记忆

在“仓库记忆”中选择仓库，可以添加项目结构、环境与启动、测试约定三类知识，
填写适用的完整代码版本。手工知识标记为未验证，不会成为人工确认依据。
可以搜索、按分类或版本筛选、编辑、归档、恢复，并查看修改记录。

- 六个 Agent 共用记忆服务，但仅接收当前任务仓库、完全相同代码版本的有效记忆。
- 每个角色按相关分类和新近程度读取，最多六条、6,000 个 JSON 字符。
- 确认复现后自动保存带来源任务和证据的问题记忆；未能复现会单独记录。
- 已有 Issue 样例保存“自动验证”记忆，与“人工复现”证据明确区分。
- 样例补丁通过验证后保存样例修复经验，不将其标记成真实项目的已合并修复。
- “问题与复现 → 记忆引用”展示提供给各角色的记忆及当时版本。
- 流程产生的证据内容不可手工改写；归档只停止后续读取，不清除历史引用。
- 旧记忆不能替新问题确认复现，也不能赋予发布或合并权限。

首次升级启动会补入当前样例版本已有的复现与修复证据，不修改任务快照。
版本不匹配的记忆仍可查看，但不会自动应用于新版本。已完成的分析可发起内置成对
记忆 A/B 评测：同一源码快照分别以无记忆和最多六条同版本记忆运行，并输出发现、
路径、模型调用和耗时的结构化摘要。该结果只是参考证据，不是因果证明；修复、
发布和合并仍只由已有流程和人工授权决定。当前没有语义向量检索、
跨版本经验推断、自动过期清理或真实模型的经验总结。记忆检索会优先匹配当前源码路径、
Issue 文本和近期引用，但仍保持字面匹配和固定预算；老化候选只提示长期未引用记录，
不会自动归档。固定样例模型接收记忆上下文，但其预定义修复行为不会因此改变。
详情见 [记忆设计记录](docs/adr/0012-repository-memory.md)。

### 固定记忆评测

仓库附带八个已知缺陷和四个正常对照固定样本。启用“运行配置 → 仓库分析模型”后，
可在项目根目录运行以下命令；评测会调用已配置的真实模型：

```powershell
.\.venv\Scripts\python.exe -m repowatch.memory_validation --case pagination
.\.venv\Scripts\python.exe -m repowatch.memory_validation
```

第一条先检查单个样本和模型兼容性，第二条运行全部十二个样本；完整运行会调用
十二对真实模型分析并产生费用。每次运行创建独立的
`data/memory-validation/memory-validation-*.json`，保存两种变体的脱敏报告、失败码、
调用数、耗时、逐样本差异、全套汇总与人工核查线索。样本源码哈希不匹配会在模型调用前停止；
评分答案不会送给模型。结果是小样本观察记录，需人工核查发现是否真正命中缺陷。
固定入口只读取本机模型配置和样本源码，不启动样本项目或触发修复、发布。

记忆与任务共用 `data/repowatch.db`，迁移时随数据库一起保留。
请勿在知识内容中填写密码、API Key 或其他凭据。

## 状态与恢复

默认数据库为 `data/repowatch.db`。设置 `REPOWATCH_DB` 可使用独立数据库。
测试与实际试用实例使用不同数据库。

- SDK 快照只保存在后台，不接受浏览器上传的快照。
- 快照绑定 SDK 版本、Agent 图版本和样例源码指纹。
- 确认记录与后续任务入队在同一 SQLite 事务内提交。
- 任务使用租约领取；正常停止后可重新领取，意外退出后的租约约 30 秒到期。
- 重复确认不会重复创建后续任务，重复执行不会生成重复草稿。
- SDK 版本、源码版本或快照校验不一致时停止，而不是绕过人工确认。
- 当前执行时间上限为 120 秒，SDK 最大 24 轮，任务最多尝试 3 次。

管理密码仅保存加盐派生结果。数据库仍包含私有会话及运行记录，应保留在受保护的
本机目录中。本阶段没有密码找回入口或远程部署配置。

### 清理本地内置样例

内置分页样例与真实 GitHub 仓库分开存储。经所有者明确要求，可以先备份数据库、
停止工作台，再通过本地维护方法 `Store.remove_samples()` 原子清理样例仓库、运行、
交接记录、本地草稿及样例自动生成的记忆。清理会保存 `samples_enabled=false`，
后续重启不再自动创建样例；页面不再显示样例入口、样例模型说明和样例完成统计。
开发回归测试仍可在独立临时数据库使用受控样例，不会写回个人工作台。

清理遇到正在执行的样例、样例关联的个人记忆、运行环境或跨仓库引用时会拒绝并
完整回滚，不会为了删除样例而连带删除真实数据。没有新增公开删除接口，也不会
改变模型、GitHub 身份、真实分析或修复发布记录。


## Windows 桌面项目的离线验证

现支持识别部分 Python/Tkinter 桌面项目，包括没有 `requirements.txt` 或
`pyproject.toml`、运行只依赖标准库和本地模块的源码布局。识别只解析源码，不会在
宿主机导入或执行下载代码；`requirements-build.txt` 不会被自动当作运行依赖安装。

- 首次下载会生成“仅容器离线测试”的候选命令，并列出未纳入的 GUI、Windows 原生
  或依赖未确认测试。首次需勾选范围确认，再点击“确认离线范围并继续”。
- 已下载但命令为空的旧环境，可在运行配置点击“识别桌面测试配置”。识别只保存方案，
  不自动安装、测试或调用模型；已有安装和自定义命令不会被覆盖。
- 确认后走“离线环境 → 兼容 unittest 测试 → 源码分析”，不启动 Windows 窗口、
  不检查网页地址、不读取或挂载真实客户端配置。后续同仓库、同账号可沿用已确认模式。
- 结果会区分实际执行、跳过和未纳入测试的模块。零测试、全部跳过或无法确认执行量
  不会被记为成功。自定义命令不会自动继承候选模块的覆盖声明。
- Windows 界面、DPAPI 和真实客户端集成始终标注未覆盖；离线通过不等于整个桌面
  程序已验收。当前自动范围面向 unittest，其他框架或依赖不明时仍需要人工配置。

完整边界见 `docs/adr/0022-desktop-offline-verification.md`。
