# ADR 0057：已有 Issue 的修复 PR 直接关联原编号

日期：2026-10-22
关联：Issue #57

## 问题

GitHub Issue 同步后的分析记录已有 `context.issue`，但创建修复任务时没有
保留来源。发布器随后无条件创建新 Issue，使修复 PR 关联到了重复 Issue。

## 来源契约

新任务在后端保存 `source_kind` 与 `source_issue`。来源由分析记录、所属仓库
和 GitHub 同步缓存共同确定，包含内部 Issue ID、仓库 ID、原编号和规范 URL。
旧分析快照缺少 `repo_id` 时，使用分析所属仓库与缓存所属仓库交叉核对。
不接受模型输出或 API 请求提供的编号作为发布依据。

旧修复任务缺少来源字段时从上述记录恢复；已有字段与原分析不一致则停止。
`issue` 字段存在但缺失、无效或属于其他仓库时，不能回退为系统新发现。
任务详情提供来源和校验错误；来源异常的任务不能直接重试。

## 发布行为

- 已有 Issue：先 GET 原 Issue，核对仓库、编号、URL 和真实 Issue 类型，
  保存 `source_issue` 本地操作记录，然后沿用分支与 PR 发布流程。
  创建 PR 前再次核对原 Issue，正文使用 `Closes #原编号`。
  原 Issue 可以是 open 或 closed；系统不会重开、编辑或评论原 Issue。
  此路径不执行创建 Issue 的 POST 请求。
- 系统新发现：仍使用原有 Issue 创建与 PR 创建流程，保留原请求内容和幂等键。
- 已有 Issue 的旧任务若存在 `issue` 操作记录，或已有 PR 操作但没有原 Issue
  绑定记录，停止并要求人工核对。不会将既有发布意图重定向到另一个编号，
  也不会删除、重写或重复提交远程产物。
- 新路径的重试核对持久化来源、操作摘要与远程 PR 标记、分支和原 Issue
  关闭引用。结果不确定的 POST 仍先查询核对，不能盲目再次写入。

现有本人复现确认、版本与源码校验、测试验证、独立审查、GitHub 账号及
仓库权限检查继续生效。此变更没有切换到自动复现策略。

## 本次验证范围

执行 Python 静态检查、语法编译、TypeScript 类型检查和前端构建，并审查
来源传递、旧任务恢复、原 Issue 发布、系统发现发布和发布重试的代码路径。
本次未新增或运行自动化测试，未调用真实模型，也未对用户仓库发布修复产物。
