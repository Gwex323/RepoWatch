# ADR 0059：原始任务范围与逐项证据决定整体完成

日期：2026-10-22
关联：Issue #59；包含 Issue #57 的已有 Issue 关联修复

## 问题与决策

一次 Issue 可能同时涉及多个入口、相似实现或平台。单个 finding 的修复、回归测试和
独立补丁批准，只能说明该补丁通过已有检查，不能证明原始请求全部完成。

保留五个实际角色，在既有分析、修复与发布之间增加持久化范围和验收账本。
不按客户端名称编写特例，也不自动执行模型提出的宿主机或客户端命令。

## 数据契约

- `task_scopes` 保存仓库、来源、活动分析、源码版本、原始问题快照、摘要与范围版本。
  Issue 来源按仓库与同步 Issue ID 聚合；系统分析按分析 ID 分组。
- `analysis_task_scopes` 保留历史分析关联。后续分析接管同一 Issue 的范围时保留条件，
  提升版本并回到待审；历史分析和旧证据不能据此获得当前完成状态。
- `task_scope_items` 保存稳定 key、标题、预期、快照路径、必要证据类型。
  条件只可追加，更新和删除有数据库触发器阻止；总数上限 32，路径必须在实际快照内。
- `task_scope_reviews` 保存独立审查；`task_scope_findings` 关联各项与持久化发现，
  `task_scope_evidence` 追加证据，`task_scope_events` 留存变动和操作者。
- `task_scope_publications` 按 repair ID 保存引用模式、范围版本、补丁摘要和剩余项快照，
  支持发布重试和不确定写入核对。

旧数据库只增加表、索引、触发器和未核验的分析关联，不追认旧任务完成，也不改写远程产物。

## 角色与审查

仓库分析拆解原始问题，问题调查检查相似实现与漏项，复现辅助说明必要验证。
受控工具 `register_task_scope` 仅允许前三者中的仓库分析、问题调查及独立审查追加条件；
复现辅助整理验证方法，不直接改变范围。实际角色来自 SDK 运行事件。

独立审查返回当前范围版本和每个 key 的结论，不能遗漏已登记项，也不能改动本人复现状态。
新 finding 用 `scope_keys` 关联；继续审查可用既有 finding ID，保留人工状态而不重复建发现。
任何持久化 finding 未映射或原始问题已截断，均不能冻结为完整范围。

执行排除和跳过项单独分类为必需、无关或未知。必需项必须关联具有客户端验证（Windows
原生或 GUI）或集成验证要求的条件；无关项必须提供已读取源码的精确依据。未分类、未知
或验证缺失都阻止整体完成，容器离线测试不能代替必要客户端证据。

## 证据及完成计算

独立补丁审查的 `approved` 只批准补丁；`scope_version`、`scope_coverage` 声明实际新增
回归文件覆盖的条件。后端从存储的补丁、审查和实际执行阶段生成回归证据：原测试通过，
新增回归修复前失败、修复后通过，修复后全套通过；新增回归不得跳过，全套跳过数不得增加。
声明中的回归路径必须属于真实补丁的新增回归文件。证据绑定实际验证和审查记录的摘要，
这两类记录变化后，旧证明不能继续作为当前验收依据。

本人可提交回归、集成或客户端观察，必须确认亲自验证并填写环境、步骤与实际结果。
记录标明 owner 来源，绑定原版本或实际候选补丁摘要。后端不将这些声明显示为自动运行。
同类型、同补丁最近一次失败观察否决此前通过证据，历史保留。候选观察提交时携带选择时
的补丁摘要；后端在事务内核对，补丁发生变化就拒绝记录，避免观察被归给另一版补丁。

单项状态包括待调查、已确认、待验证、受阻、已验证修复、已核验无缺陷。
“已验证修复”必须有真实回归证据和同一候选补丁的全部必要证据；“已核验无缺陷”须有
独立源码依据、无当前已确认发现及全部必要的原版本观察。模型自述不能直接完成验收。

当前源码、执行记录身份、原 Issue 内容、活动分析和范围版本均需一致。计算既使用当前
版本的最新证据，也保留历史；历史显示上限不会挤掉仍有效的最新证据。
整体完成还要求所有已登记条件通过、排除项核清、所有修复来自同一候选补丁。原版本
无缺陷证据仅可与未修改该项涉及路径的补丁组合；不同 PR 不能简单拼接为整体验收。

## 发布与幂等

默认 `Refs #编号`，只有当前候选补丁使整体范围完成，后端才追加 `Closes #编号`。
模型正文、标题和提交文本中的关闭引用会被清理；引用编号仍由已有 Issue 来源契约确定。
已有 Issue 不另建 Issue；系统新发现沿用创建 Issue 的既有流程。

发布前持久化判断；部分 PR 重试维持原 `Refs`。原 `Closes` 在范围、源码、执行证据变化后
停止，不能沿用旧完成结论。读取原 Issue 时核对新鲜度，内容变化使范围升版、回到待审。
每次远程写入均校验当前决定；保留既有账号、权限、源码、分支和不确定 POST 意图核对。
旧发布意图与新正文摘要冲突时停止，不自动改写既有远程产物。

## API 与界面

- `GET /api/analyses/{id}/scope`：范围、状态、剩余项、证据及排除项。
- `POST /api/analyses/{id}/scope/requirements`：本人按范围版本追加遗漏条件。
- `POST /api/analyses/{id}/scope-review`：按分析版本排队继续分析和独立范围审查。
- `POST /api/task-scopes/{id}/items/{key}/observations`：按范围版本追加本人观察。

沿用登录和 CSRF 校验。没有直接设置完成、删除条件或降级必要验证的接口。
范围面板展示原始问题、进度、结论、证据来源、历史和排除项，并提供本人记录和续办入口。
继续审查使范围升版；源码或执行依据过期时须新建分析，不能继续沿用过期依据。

## 边界与本次检查

范围识别仍依赖模型语义和有限源码快照。独立审查与本人补充降低漏项风险，后端保证已经
登记的条件持续保留；不能保证模型永不漏掉尚未登记的需求。未新增 Windows 客户端执行器。

最初的范围验收增量只执行静态检查和构建；未进行真实模型与端到端验收。

## 2026-10-26：补齐审查拒绝后的自动返工

生产任务 `repair_2275e1e24f6a46a5` 的回归和原测试通过，但审查发现完整文件替换中夹带
无关改动。原实现仅把 `approved=false` 转成 `repair_review_rejected`，测试纠正循环没有
覆盖审查。这是范围完成与修复执行之间缺少状态回边，范围账本不能代替返工控制器。

现在拒绝结论、风险、当前补丁和真实验证结果自动回到同一个修复角色。修订从同一原始
源码重建隔离候选，不允许原样重交或回到历史候选；必须重新执行四类验证，再由审查员
重新读取本轮证据。保留两次测试纠正及两次审查返工，共最多五个候选；统一任务期限、
读取/字数、参数纠正及模型输出/超时重试预算不重置。每轮 reviewer 探索预算按轮限制，
修复角色探索总预算仅随实际纠正次数有界增长。

工作区保存当前审查及每轮审查；`verification._reviews` 与既有 `_rounds` 同步持久化，
API 分别返回 `review_rounds`、`verification_rounds`，不把元数据作为测试阶段展示。
新补丁准备后立即清除当前审查；历史拒绝及测试记录保留。模型未读证据、暂停、取消、
原确认失效、源码变化、预算耗尽、受保护文件等错误依旧停止，不绕过发布门槛。

旧策略拒绝任务可自动续办一次：必须已有本人确认、自动修复和模型均启用、同一有效
分析证据、完整通过验证、真实拒绝结论、合法候选及源码摘要、没有远程产物。事务按
任务版本归档原尝试并设置独立策略和一次性标记；新工作区在模型调用前核对原始源码
摘要，携带原补丁和结论并禁止原样重交。当前策略和已使用标记的失败不自动重排。
部署到启用了自动修复的工作台可能因此恢复这类已授权任务并调用模型、按现有授权发布。

防止同类遗漏的约束：每个失败分支都必须说明是可修订反馈、等待外部条件，还是终止
原因；每种可修订反馈必须有实际状态回边、持久化历史及离线运行器回归，不能只改提示。
本增量的回归使用原生 Agents SDK 与合成执行器，覆盖重审、混合验证失败、旧任务续办
及发布阻断；不以离线测试声称真实客户端或目标仓库修复已完成。

## 2026-10-27：自动验收接续与真实证据登记

DSML 任务的补丁已有真实测试和批准，但复用历史 finding 使范围升版到待审，
`record_repair` 因未审查直接返回。原系统仅有账本和人工入口，没有消费待办的后台控制器，
因此不会自动重新审查范围、登记已有测试或执行其余验证。不能靠人工补写数据库解决此类断点。

新增 `Acceptance` 作为既有自动修复的后台接续。任务绑定范围版本、活动分析、执行身份、
原始需求和每个已批准补丁的完整证据摘要，并按依据去重。仍使用既有独立审查角色，
要求精确范围 key、全部 finding 映射及已提供源码的原文引用。版本升高后的旧测试只有
重新通过独立覆盖复核才生成当前证明，不修改原测试或旧批准，不降低原要求。

四张新增表保存验收运行、检查、修复证据复核和修复续办。当前有效证明必须与持久化计划、
当前补丁及实际执行/审查摘要一致；未知证据来源拒绝，真实失败否决对应旧通过证明。
目前支持已有 pytest 配置的 Python 隔离测试；模型只能提供新增测试文件，不能提供命令，
不能修改既有源码、测试、依赖或范围。测试阶段断网；必要的原生客户端、外部服务或凭据
无法获得时，保留具体受阻项。离线模拟不能代替原需求所需真实服务。

验收中的真实缺陷，或需要把新增回归纳入完整补丁时，自动续办同一个已确认问题。
新任务携带原补丁、实际验证及审查意见，保留原确认和历史，范围重新审查；
仍须通过原测试、修复前回归失败、修复后回归/全套通过及独立审查才能按原发布规则提交。
没有原确认、新发现、误报、已取消或失效任务不会据此自动获得授权。

每个原问题最多两轮验收后续办；每轮 30 分钟、12 次请求、每项两次执行、最多两次运行尝试。
额度、期限和模型身份持久化，等待或重启不会清零。保存的实际结果恢复时只补审查；
纠正测试先清除原结果。同环境验收串行；账户、源码、范围或执行身份变化停止旧运行。
界面展示系统自动处理状态和具体障碍，不再把登记已有真实证据作为用户必做事项。

本增量只进行静态检查、模块导入和前端构建；未新增/运行自动化测试，未调用真实模型、
运行 Docker 验证或推进目标仓库发布。部署及真实端到端结果另行确认。
