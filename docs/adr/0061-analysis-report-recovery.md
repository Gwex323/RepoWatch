# 0061：独立审查预算、紧凑证据与持久化恢复

- 关联：Issue #61
- 状态：已实现，等待合并及真实供应商验收

## 问题

最终报告固定 5000 tokens 时，多个验收项、历史复核和模型推理可能共同耗尽额度。
扩大额度重试又可能耗尽十分钟总时限。此前只能在同一次进程调用内纠正或重试，
报告失败后再次点击重试会重新运行所有分析角色，重复付出取证成本。

## 预算与输入

- 基础 5000 tokens，验收项与历史条目合计超过两项后，每多一项增加 650，最高 100000。
  例如六个验收项为 7600；已配置推理强度保持不变，预算包含供应商计入输出的推理消耗。
- 最终阶段预留 260–360 秒，包含最多两次 120 秒请求及退避时间；仍受 600 秒总时限限制。
  模型服务自身持续超时、拒绝或不支持额度时仍可能失败，本机制不承诺供应商可用性。
- 同一文件重叠、相邻的真实读取范围合并为原始文本块，带起止行号；未读间隙不会合并。
  重复长文本只保存一份，以 `shared_text_ref` 引用；原始需求、执行限制和历史编号不截断。
- 只保留最近十二条去重后的助手观察，每条最多 2000 字符。超出时显式标记
  `observations_clipped`，要求披露覆盖限制。原始源码与完整验收要求不由此裁剪。
- 最终报告截断或超时的自动重试也切换到紧凑输入，关闭工具，保留原有格式和引用校验。

## 检查点与信任边界

`analysis_review_checkpoints` 是服务端私有表，每个分析最多一条。独立审查员每次请求前，
保存此前实际发生的完整 SDK 交接链、执行读取标记、文件与范围、有限观察及上下文摘要。
即使审查员在工具尚开放时直接生成最终答案，也会先保存；后续审查读取会刷新检查点。
保存和任务完成都受运行状态及版本 CAS 保护，取消或过期运行不能覆盖有效任务。

检查点不包含原始工具对话、模型推理正文或凭据。供应商回显的已知 API Key 会在保存前
替换；原有日志与快照脱敏规则继续适用。完整检查点不进入事件 API，页面只获得可恢复标记
和固定事件说明。检查点最大 160000 字节，不兼容或损坏数据不复用。

绑定包括任务 ID、触发执行记录、不可变源码/上下文、当前 Issue 缓存、可选验收范围版本、
分析流程模型与供应商配置（包括凭据的加密值摘要）。恢复同时校验协议版本、内容摘要、
真实交接链、读取范围和当前执行依据。模型配置在建客户端前再次核对，写报告前再次检查
任务状态和依据，防止运行期间的变化被接受。

有效检查点通过既有 retry 接口排队；后台仅启动独立审查员并关闭工具，使用保存的
真实读取/交接元数据验证最终报告，不追加虚假的读取或交接事件。成功后删除检查点；
失败后保留供再次重试。失败不会保存半份报告或新增发现，也不会替代人工确认或创建修复。

Issue 更新以后台只读同步缓存为准，不在重试时额外访问 GitHub。缓存变化使检查点失效，
重新探索使用更新后的原始需求。新执行使旧任务过期时保持原有过期保护，不能复用旧证据。
旧任务未保存检查点时走完整流程，绝不从历史报告补造检查点。

## 验收范围模块兼容

此变更从最新主干独立实现，不复制尚未合并的 PR #60。预算与输入读取可选的
`context.task_scope.items`。数据库存在 `analysis_task_scopes` 时，额外核对范围 ID、
版本、当前分析 ID、源码版本和原始需求摘要；不存在时兼容旧库。
范围模块仍负责生成 `task_scope`、验收结论的 schema 及其原有校验；合并时须保留
其工具注册、最终验收校验和检查点恢复入口，不能让报告恢复绕过范围验收。

## 验证

使用离线模型及真实 Agents SDK/SQLite 服务验证预算上限、紧凑引用、重启后仅审查员
恢复、依据变化失效、精确引用失败、旧任务兼容及原有交接恢复。不调用真实供应商，
不在目标仓库发布 Issue/PR。具体检查结果记录在 PR 的验证/验收章节。

## 2026-10-27：最终审查自动续办

检查点恢复增加后台调度：有效审查遇到 JSON/字段/证据校验失败、输出截断、超时或
可恢复中断时，最多续办三次，分别退避 10 秒、30 秒和 60 秒，仅继续独立审查员。
拒绝、权限、协议、鉴权、未知错误和依据变化不自动重试。失败记录继续保留，
恢复排队期间页面显示等待状态，不要求用户帮助组装证据或手动触发正常额度内的恢复。

新增 analysis_report_recovery 私有表；从本版本首次 claim 开始，累计最多 32 次
delegate 模型请求和 1800 秒，包括超时、退避及重启期间。每次请求前事务预占，
重启不归还请求和续办名额。原局部格式、证据、超时及输出纠正计数跨续办持久保留，
不会每次新调用 run_analysis 就获得一套新额度。单次运行及请求期限仍保留。
人工 retry 也占用同一续办额度，不能通过重复点击无限增加调用。

现有失败任务不因建表而重新执行。新运行或用户显式 retry 才建立新版本的额度记录；
之前版本未记录的调用无法补算。租约中断恢复仅处理已加入恢复链的当前任务。
已排队的检查点若失效，自动续办直接停止，不静默转为完整探索。

JSON 诊断增加固定错误原因及安全字段路径，与行列位置一并传入当前纠正及续办请求；
不保存或回传失败报告正文。详情见 docs/tasks/0061/design.md。

## 2026-10-28：提高分析输出和续办上限

单次生成硬上限提高到 100000 tokens，报告预算及截断扩容共用该值；初始预算仍按
任务规模计算，供应商计入输出的推理 tokens 包含在内。截断扩容仍受原有局部重试次数、
请求时限和任务总期限限制，提高硬上限不表示每次请求都会使用 100000 tokens。
自动恢复与人工 retry 共用三次续办，退避为 10/30/60 秒；页面从后端读取上限。
累计请求、期限和纠正计数继续持久保存，已停止任务不会因上限变更自动重新排队。
