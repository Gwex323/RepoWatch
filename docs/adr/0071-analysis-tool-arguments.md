# 0071：分析工具参数的有界自动纠正

- 关联：Issue #71
- 范围：四个仓库分析角色中的三个函数工具和原生交接

## 原因

`analysis_85bd1409a36647ea` 在问题调查阶段返回未截断的工具调用后，由 SDK 参数解析
抛出 `ModelBehaviorError`，分析直接失败。已有输出截断、报告格式和证据纠正不覆盖
工具参数；修复流程的参数纠正也不会自动应用到分析流程。

## 执行前检查

`StageModel` 在把响应交给 Runner 前，对当前开放的已知工具及交接检查参数 JSON 对象。
源码读取、运行记录读取、范围登记还使用 SDK `function_schema` 生成的同一 Pydantic
参数模型校验字段。保留 SDK 对无参数工具的空参数字符串约定；有参数工具不适用。
不补括号、不抽取 Markdown、不解码内嵌 JSON 字符串、不猜测缺失字段。

响应里任意已知调用参数错误时，整份响应不交给 Runner，因此同一批里的其他有效调用
也不会执行，不会出现范围登记重复或半批读取被误认完成。修正请求保留同一次调用之前
的真实 SDK 对话，并要求重新生成相同完整批次。响应的正文不进入纠正上下文；未执行
参数按下述补充方案作为非可信用户数据临时回传。有效响应仍由 SDK 原生工具处理器
校验、执行并记录真实证据。

未知工具名继续拒绝，不通过参数纠正扩大工具集合。关闭探索、强制必读及指定
交接仍使用已有规则；失败的函数参数不产生读取额度、证据事件、范围变更或 handoff。

## 预算与安全

`RetryBudget.tool_arguments_used` 在四个角色间共享，最多两个额外纠正请求，不重启
Runner，不重置阶段已用轮数、读取数量/字数、任务期限、超时、截断、报告或证据预算。
超时和截断与纠正组合时仍分别使用原有全局预算。重试前检查剩余总时间，每个请求受
120 秒及剩余任务时间的较小值限制。指定交接的兼容重试也经过这一统一请求循环，
不能绕过参数校验和时限。取消由原任务取消链传播，写入报告保留原有状态和依据校验。

事件只包含已知角色/工具名、固定原因、契约字段路径、是否可纠正及剩余次数；不保存
原始参数、模型正文或校验异常文本。纠正反馈包含服务端生成的 schema，审查意见、源码
或模型输入不能修改它。Langfuse 仅记录事件名称，不上传载荷。

## 2026-10-26：按实际失败补全契约、权限和预算

`analysis_9da31ce04adb4b90` 暴露第一版只做有界纠正的不足：复现辅助仍看到无权执行的
范围登记工具；诊断只有顶层 `items`；high 推理与工具参数共用 3000 tokens。
两次纠正的 usage 均达到上限，尽管 finish_reason 是 tool_calls。这是疑似预算不足，
原始参数未保存，不能断言具体在哪个字符被截断。

`analysis_tools.py` 集中定义角色权限，Agent 工具集合、响应预检、实际函数处理器和
范围持久化使用同一策略。四角色均可读取；范围登记仅供仓库分析、问题调查和独立审查，
本人追加 API 的 owner 权限保留。仓库分析在已有运行记录和源码读取后，须成功登记至少
一个范围项才可首次交接；已有非空范围可直接沿用，未登记成功不能靠交接绕过。

范围调用每批 1–3 项，由同一 SDK schema 和 Pydantic 模型约束，继续使用追加、去重、
版本递增和禁止弱化语义。复现辅助从已登记项整理步骤和观察，需要追加时交给独立审查。
嵌套错误提供例如 `items[0].required_evidence[0]`、固定错误类别和可信 schema 的允许值；
未知字段名替换为 unexpected_field，绝不记录模型值、原始参数或异常正文。
JSON 语法错误只提供长度和位置。事件上限 4096，前端展示嵌套字段、位置和预算提示。

工具调用预算同时留出推理与载荷：high/xhigh/max 预留 5000 推理 tokens，其他预留
2000；读取载荷 1000，含范围登记时载荷 3000。取配置与该预算较大值，上限 12000。
保留用户配置的推理强度；审查报告预算与工具预算也取较大值，不互相覆盖。
仅在 JSON 语法错误且可信 output usage 达当前上限时标注疑似不足，允许预算内翻倍至
12000；合法 JSON、字段错误不会因此扩容。扩容消耗原截断预算，纠正仍全流程最多两次。
扩大预算不能保证任何模型永不返回错误；额度、取消和期限耗尽仍明确失败。

真实运行还观察到报告证据纠正时 8000 输出中推理占 7990，明确 length 截断；随后在
十分钟总期限停止。最终报告的预算也须覆盖推理：high/xhigh/max 在原按验收项计算的
载荷预算之外预留 5000，合计仍不超过 12000；对应报告预留时间最多 360 秒。
不会因此重置重试次数或总时限。支持用合法检查点显式恢复审查，复用真实读取和交接。

真实重放进一步发现最终报告可以把 scope_review 留空。已有范围项时新增本地报告契约：
必须使用当前范围版本、逐项且不重复覆盖全部验收项和执行限制；缺少结论时使用既有
一次报告格式纠正预算，从同一真实证据生成完整报告。仍不合格则停止，不能标记分析完成。
`validate_report` 持久化前再次检查，检查点恢复也适用；未测试项可如实 blocked/unknown，
不要求模型把未通过项改成通过。

## 2026-10-26 17:33：纠正必须完成原失败批次

已部署 `e97471f` 后，任务 `analysis_9da31ce04adb4b90` 的第 11 次尝试又失败。
17:31:39 仓库分析的范围项缺少 title；其纠正响应直接交接给问题调查，没有范围登记
成功事件。17:32:56 问题调查的两个范围项缺少 title，17:33:14 纠正后三个范围项仍缺少
title，最后耗尽两次共享纠正。参数为可解析 JSON，响应未截断，输出远低于 8000。
这不能归因于输出长度；局部校验和增加重试没有约束纠正是否真正完成原调用。

`ToolArgumentRepair` 在首次参数错误时绑定本批全部已知调用的工具名、数量和顺序。
纠正请求只开放本批工具，指定单一工具或 required；提供商的 tool_choice 只是请求约束，
响应还必须通过本地批次匹配，不能改为其他工具、额外调用、少调用、交接或正文报告。
原批次本来包含的交接也必须保持原位置，且整批参数通过后才由 SDK 处理。

对于可解析的对象，使用同一 Pydantic 参数模型确定原错误路径；纠正仅能修改无效字段
或补上缺失字段，其余合法子树须保持一致，包括混合批次中原本合法的源码读取参数。
若列表本身长度违规，可以更改该列表；只有列表内部字段出错时，不得靠增删或改序条目
绕过修复。JSON 无法解析时不猜测原字段，仍要求相同调用批次并重新通过完整校验。

将原参数的候选值作为单独的非可信用户消息交回同一模型，明确 executed=false，不能
当作源码读取、执行结果、证据、指令或授权。不回传原响应正文或伪造工具执行结果。
候选数据最多 24000 字符，超出时省略参数值而不截坏 JSON；其内容只存于本次请求内存，
不进入 SDK 已执行对话、恢复检查点、数据库事件、日志或 Langfuse。纠正后真正通过的
响应才返回 Runner，原生工具处理器继续负责权限、路径、范围持久化和真实事件。

参数反馈保留完整可信 schema，范围工具和 title 字段补充明确必填说明。批次不匹配使用
repair_batch_mismatch，合法字段被改写使用 repair_valid_fields_changed；诊断只包含
可信工具名、脱敏字段路径和调用数量，未知模型值和工具名不写入事件。
工具校验通过事件 tool_arguments_repaired 仅表示可以交给 SDK，不声称实际执行成功。

审查角色的参数纠正遇到超时或截断时，继续同一纠正请求，不得清空工具直接切换报告。
两次全局参数纠正、原超时和截断预算、120 秒单请求及十分钟总期限继续生效。
页面的失败摘要和事件区分 JSON 语法、缺字段、改变合法参数及跳过原调用；失败摘要只
查当前尝试的最后一条校验记录，避免拿上一轮错误解释当前失败。

本次仅维护原有用例以适配临时候选数据和完整批次纠正，没有增加或运行测试，也未调用
真实模型。此前 269 项通过的记录属于前一轮代码，不能用作本次改动的回归验收。

## 2026-10-26 18:41：合法字段由程序保留

`9c368fb` 部署后，第 14 次尝试先两次缺少 `items[0].title`，最终纠正通过字段契约
检查，却改写原合法的 `items[0].expected`，被 `repair_valid_fields_changed` 拒绝。
三次响应均未截断。日志未保存参数，无法判断这段改写是措辞变化还是实质变化；
不能放开对验收内容的修改，也不能把静态检查通过当作恢复流程已验收。

改为确定性保留原合法字段。批次与完整模型响应先通过原 JSON/Pydantic 检查，再以
首次响应的错误路径为界，仅采纳模型对原错误字段的修正，其余值从本批原参数复制。
例如原调用只缺 title，而纠正同时改写 expected，执行候选使用模型的新 title 和
原 expected。不比较自然语言语义，不猜 title，不采用改写后的验收标准。
混合批次里原本合法的读取参数也从原调用保留。复制后重新执行完整参数检查和合法
字段一致性检查，任何一项不通过都不能交给 SDK；调用 ID、用量等仍来自真实纠正响应。
原候选及 SDK 响应均不原地修改，不合并入真实工具执行结果或证据。

原错误位于列表内部时，增减列表条目仍被拒绝，避免恢复整个列表时丢掉需要修正的
字段。原列表本身长度错误时按原规则允许修正该列表。原 JSON 不可解析时仍不猜补，
必须由模型重发同批完整调用。原来的两次共享纠正、角色权限、取消、超时、预算及
范围持久化/报告门禁保持。

成功保留字段时记录 tool_arguments_preserved，只有可信工具名和字段路径；事件上限
4096，前端说明等待工具实际执行。Langfuse 仅记录事件名称，参数仍不进入遥测。
本轮只执行静态检查与构建，不新增或运行测试，不运行真实模型。

## 2026-10-26 19:36：证据纠正不再重写整份报告

第 20 次真实尝试运行在 f7a17f5。参数缺失纠正及四角色交接均完成；19:32:16 首份
报告输出 3888 tokens、推理 298，但问题 1 第 3 条证据 quote_mismatch、问题 3 第 1 条
证据 unread_file。既有证据纠正要求从完整证据包重写报告，随后耗尽 11300 tokens
（推理 9038），扩容至 12000 后再次截断（推理 11975，仅余 25 非推理 tokens）。
这说明固定扩容不能保证推理后还有报告空间。前一轮针对工具参数的修复未覆盖报告
证据纠正的整份重生成行为，静态构建也无法证明实际模型可以完成该恢复链。

`ReportEvidenceCorrection` 保存本次尚未接受的 Review，只向同一模型发送错误项目和
真实已读证据包。输出是受限的纠正契约，不是完整 Review：section、项目编号、是否
撤回、理由和被标记证据的替换。section 明确区分新问题、历史问题、范围项、运行限制，
避免它们的相同数字编号指向不同对象。纠正必须逐一覆盖所有目标，不允许重复、遗漏、
新增项目、修改其他字段或调用工具。仅缺少必要证据的空列表允许使用编号 0 追加证据。

修正证据只替换本地校验指出的位置，其他报告字段和合法引用从原 Review 保留。撤回
必须给出理由及说明不确定性的摘要；新问题移除并记入 limitations，已知历史问题变为
not_covered，未知/重复历史 ID 移除后由原持久化逻辑补齐真正遗漏的历史结论；范围项
变为 blocked、运行限制变为 unknown，并将范围 accepted 置为 false。撤回不表示
无缺陷、修复成功或人工确认，原任务范围和验收要求继续保留。

合并结果重新执行完整 Review 契约、范围版本/覆盖和所有源码证据检查，之后才返回
SDK。保留真实响应 ID 与用量；不伪造读取、交接、执行结果或证据，不自动为错误 quote
填入源码。引用仍必须落在原已读文件与区间。失败候选和局部纠正数据仅在本次调用内存
中存在，不写入事件、日志、Langfuse 或恢复检查点。已有检查点仍只含真实读取和交接。

局部纠正使用原一次证据纠正额度；契约或坐标错误使用原全局一次格式纠正额度。输出
扩容、超时、取消、120 秒请求上限和十分钟总期限继续生效，保留 high，不扩大 12000
上限。超时/截断重试始终保留局部协议，不能退回整份报告重写。拒绝响应直接终止。

事件记录纠正项目/错误数量、固定阶段以及可信 token 用量，不包含候选正文或引用。
output_limit 区分报告、证据纠正、工具纠正及探索，并记录能否继续扩容；非推理用量
仅在可信供应商同时给出输出和推理计数时计算，不能把缺失计数当成零。
