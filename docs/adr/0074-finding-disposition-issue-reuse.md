# 误报关闭与相似 Issue 复用

关联 Issue #74。

## 原因

人工处置与修复队列之间缺少明确的误报终态：旧记录只能记为未复现或已解决，
且只取消排队任务，导致失败修复仍作为待处理展示。发布幂等标记只能阻止同任务重发，
无法识别另一个任务已登记的同类问题。

## 处置契约

- `false_positive` 只能由用户处置接口提交，要求确认原因及 finding 版本 CAS。
- 保留原状态、操作者、源码版本、时间和说明；运行中任务仍拒绝改判。
- 停止排队、等待、失败及中断的修复，保留历史尝试和补丁。
- 列表、当前问题、历史复核和修复页优先显示人工终态；未来历史待复核只带入未关闭项。
- 误报不是修复成功，不能生成回归通过证据。范围验收仍须独立证据满足全部要求。

## 发布契约

1. 可信来源 Issue 优先，不能被模型、客户端或匹配器替换。
2. 新发现的问题在发布前读取同仓库所有状态的 Issue（排除 PR，最多 2000 条）。
   规范化标题完全一致，或同时满足源码路径与标题症状相似阈值，才作为候选。
   此规则保守匹配，不能保证识别所有语义改写；不使用远程正文中的指令。
3. 保存 `issue_target` 决定及匹配理由。已绑定目标后不切换；未绑定且未产生 POST 意图
   的新建决定允许刷新扫描。旧版已创建 Issue 的任务继续使用原发布记录。
4. 复用目标按仓库、编号、URL、Issue 类型重新验证。补充评论包含任务唯一标记，
   通过持久化 POST 意图、账号与正文校验恢复；不确定的 POST 不盲目重发。
5. 相似 Issue 可能比当前发现范围更大或已关闭，PR 只使用 `Refs`，不自动关闭或重开。
   原任务范围审查、源码版本、凭据身份与独立验证检查继续生效。
6. 读取失败或达到扫描上限时停止发布，不把“未完成检查”解释为“没有相似 Issue”。

## 本轮验证范围

执行 Ruff、Python 编译、TypeScript 类型检查与前端构建，并人工检查读写链路及
发布重试路径。按会话约束未新增或运行自动化测试；部署核对以服务实际响应和生产
数据记录为依据。DSML 的真实修复验证由已授权的 RepoWatch 处理流程执行。
