# 误报关闭与相似 Issue 复用

关联 Issue #74。

## 原因

人工处置与修复队列之间缺少明确的误报终态：旧记录只能记为未复现或已解决，
且只取消排队任务，导致失败修复仍作为待处理展示。发布幂等标记只能阻止同任务重发，
无法识别另一个任务已登记的同类问题。

## 处置契约

- `false_positive` 只能由用户处置接口提交，要求确认原因及 finding 版本 CAS。
- 保留原状态、操作者、源码版本、时间和说明；运行中任务仍拒绝改判。
- 停止排队、等待、失败及中断的修复，保留历史尝试和补丁。
- 列表、当前问题、历史复核和修复页优先显示人工终态；未来历史待复核只带入未关闭项。
- 误报不是修复成功，不能生成回归通过证据。范围验收仍须独立证据满足全部要求。

## 跨版本续办契约

用户明确请求续办时，后端同时检查旧问题和新分析的版本、同仓库同来源、原用户确认、
最新已完成分析、`still_present` 独立复核、真实读取的当前源码证据以及已确认的范围项。
当前源码快照必须与分析一致，执行和发布不能处于冲突状态。生成新问题记录和修复任务，
保留原用户确认与复核出处；旧问题转为 `superseded` 并取消旧任务，旧记录不删除。
新增关联后原范围验收失效。模型本身不能调用此用户接口，也不能通过历史复核授权发布。

真实续办连续两次耗尽旧版六轮读取额度且未提交补丁。修复探索基础预算改为十轮，
末两轮只提供 `submit_and_test_repair` 并指定工具选择，要求对已读源码提交最小补丁。
若未提交或验证失败，保留原有失败门禁及总体 30 分钟时限。

第三次实际执行证明，模型可能忽略指定工具并返回并行源码读取。SDK 仍保有完整工具表，
仅过滤请求工具不能阻止执行。响应必须先按当前工具表和单调用约束准入；提交阶段只接收
一个 `submit_and_test_repair`，不允许夹带消息。违规整批不执行，保留原输入和源码证据，
全任务最多纠正一次工具选择；再次违规给出明确错误。读取额度不足以容纳下一个最大文件
时提前进入提交阶段，不放宽源文件保护或读取上限。

仅对旧策略、已到尝试上限、当前尝试存在可信 `submission_required` 事件，且以读取预算
或缺少验证失败、无补丁/验证/审查/远程产物的任务，提供一次显式重试恢复。CAS 更新
`submission_recovery_used`，保留失败快照，正常队列执行第四次；新策略在领取时登记，
新策略失败或已用过恢复机会的任务不再获得此机会。原确认与当前证据门禁继续生效。

另有显式用户授权的模型变更续跑：只有当前任务次数已满、上次以工具选择违规失败且无
补丁/验证/审查/远程结果，实际修复模型与当前尝试记录不同，用户提供明确说明时，
服务允许同一任务额外尝试一次。保存原/新模型、用户说明、配置指纹、下一次尝试编号，
使用正常 retry CAS 与失败快照；模型不能通过工具、普通重试或自动策略触发该授权。
执行期间配置指纹变化即停止；不重置次数、不新建任务、不反复获得模型变更额度。

## 验证通过后的固定交接

实际第五次尝试已通过全部测试，但模型返回文本而未执行指定 handoff。固定流程不再
请求模型选择：后端在 `ready_for_review` 成立后返回明确标记的 SDK 控制调用，SDK
执行原生 handoff 和 `on_handoff` 门禁；独立角色开始后同样由后端触发真实证据工具。
这些控制动作不调用供应商、不记录虚假 provider 响应或用量；唯一调用 ID 不重用。
真实工具仍校验当前角色和验证状态，审查结论仍必须由独立模型产生并通过严格校验。

旧策略交接失败、当前尝试有可信验证通过事件、无审查/远程产物且补丁可严格还原时，
允许一次保存补丁恢复。正常 retry CAS 保存失败快照并记录 `handoff_recovery_used`，
保留源码摘要，重新执行现有的补丁准备和真实测试后触发交接。原/新尝试分别保存，
不重置次数、不改写测试结果、不跳过复验或独立审查。队列恢复绑定修复和审查模型
指纹；新策略失败或已使用恢复的任务不再获得此机会。

## 发布契约

1. 可信来源 Issue 优先，不能被模型、客户端或匹配器替换。
2. 新发现的问题在发布前读取同仓库所有状态的 Issue（排除 PR，最多 2000 条）。
   规范化标题完全一致，或同时满足源码路径与标题症状相似阈值，才作为候选。
   原标题已命名首个修复变体时，也检查正文风险段落；要求相关标题、同路径及高比例
   症状片段交集，较低交集还必须命中至少两个具体英文标识，避免仅凭同一文件复用。
   此规则保守匹配，不能保证识别所有语义改写；不使用远程正文中的指令。
3. 保存 `issue_target` 决定及匹配理由。已绑定目标后不切换；未绑定且未产生 POST 意图
   的新建决定允许刷新扫描。旧版已创建 Issue 的任务继续使用原发布记录。
4. 复用目标按仓库、编号、URL、Issue 类型重新验证。补充评论包含任务唯一标记，
   通过持久化 POST 意图、账号与正文校验恢复；不确定的 POST 不盲目重发。
5. 相似 Issue 可能比当前发现范围更大或已关闭，PR 只使用 `Refs`，不自动关闭或重开。
   原任务范围审查、源码版本、凭据身份与独立验证检查继续生效。
6. 读取失败或达到扫描上限时停止发布，不把“未完成检查”解释为“没有相似 Issue”。

## 本轮验证范围

执行 Ruff、Python 编译、TypeScript 类型检查与前端构建，并人工检查读写链路及
发布重试路径。按会话约束未新增或运行自动化测试；部署核对以服务实际响应和生产
数据记录为依据。DSML 的真实修复验证由已授权的 RepoWatch 处理流程执行。
