## 故障证据

正式工作台运行 `96f5105`。分析 `analysis_8b72bb9f2f08492c` 于
2026-10-30 12:39:35（Asia/Shanghai）继续独立审查，12:41:07 收到模型报告；
引用诊断和证据错误事件已记录，12:41:08 以 `OperationalError` 失败，
错误码落到 `analysis_failed`，续办因 `non_recoverable` 停止。

静态核对发现 `analysis_review_corrections` 的表结构只有六列：
`analysis_id`、`binding`、`checkpoint_digest`、`payload`、`payload_digest`、
`created`；原 INSERT 却写七个占位符，参数元组只有六项。首次保存必然失败。
失败前真实读取检查点仍在，纠正表没有该分析的候选记录。日志没有保存 SQLite
原始错误或堆栈，因此原始异常消息无法补回；以上归因来自实际事件时序和源码核对。

此前 #103 的静态检查没有覆盖 SQL 字段数与参数数的一致性，静态自审漏掉了这一错误。
构建和进程启动只说明服务能启动，不能证明纠正现场写入成功。

## 修改

1. INSERT 显式列出六个目标字段，并使用六个占位符，参数顺序与字段一致。
   冲突更新字段、摘要、可信检查点绑定及事务提交行为保留。
2. 将 `sqlite3.DatabaseError`（包含 `OperationalError`、`IntegrityError` 等）
   归类为固定码 `analysis_storage_failed`，页面提示先处理数据库错误再重试。
3. 新失败事件和服务日志记录异常类型及 SQLite 的整数错误码；统一故障诊断允许
   该数字字段。没有错误码属性时省略，不读取异常消息、SQL、数据库路径或报告正文。
4. 数据库错误继续走原有停止策略；不把持久化失败视为候选已保存，不自动无限续办，
   不放宽真实读取、范围、所有权、脱敏或完整报告校验。
