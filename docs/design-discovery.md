# 需求澄清记录

本文件保留按时间推进的访谈。前轮的“后续确定”不表示当前未决，后轮决定及用户后续调整以[设计基线](design-baseline.md)和[实施契约](implementation-contracts.md)汇总为准。2026-11-03 一致性修订未新增或改写 Q1—Q36 的用户答复。

## 工作方式

- 使用 grill-with-docs → grilling + domain-modeling 原技能链。
- 先确定最终产品的职责与架构，再规划分阶段实施；阶段划分不替代最终架构设计。
- 按决策依赖分轮访谈，同步维护术语表和必要的 ADR。
- 功能、项目框架和核心流程均需达成共同理解；关键技术决策前可进行必要的只读源码／文档调查。访谈收敛后撰写正式可行性报告，当前不开始产品实现。

## 用户已明确的目标

1. 处理 GitHub 仓库已有 Issue，修复后提交 PR，并定时巡查新 Issue。
2. 首次导入仓库时分析代码，主动发现 Bug／缺陷。
3. 本地用户可管理多个仓库，不要求并行解决。
4. 支持多个模型供应商，不同 Agent 可选择不同供应商。
5. 提供记忆能力，加快同仓库或跨仓库相似问题的解决。
6. 使用场景以项目开发为主，修复应有证据支持后才可提交 PR。

## 第一轮：已确认

用户接受以下三项推荐：

### Q1：提交 PR 的证据门槛

- 证明修改前存在问题、修改后问题消失。
- 通过相关回归检查和独立审查。
- 无法复现或验证条件不足时进入阻塞状态，不提交 PR。
- 此门槛提供可核查的验收依据，不声称证明代码绝对正确。
- 测试基线及无测试仓库规则已由 Q9 明确；具体验收适配与证据格式在技术方案中推荐。

### Q2：主动发现的缺陷

- 首次导入后发现的问题先保存为本地缺陷候选，由用户选择是否启动修复。
- 候选发现本身不触发对外创建 Issue 或 PR。
- 已有 GitHub Issue 按 Q4、Q8 的分诊与自动入队规则处理。

### Q3：最终运行形态

- 本机运行的服务配合浏览器管理界面。
- 支持 Windows 使用，允许 Docker／WSL 提供代码执行环境。
- 浏览器关闭不应终止后台巡查；后台服务安装、停止后的检查点恢复和巡查补偿在技术方案中推荐。

## 第二轮：已确认

### Q4：已确认的自动修复范围

- 有明确验收条件的 Bug／缺陷可直接进入自动修复。
- 功能请求和大规模重构先生成方案，待用户确认后再进入实现。
- 自动修复仍须满足 Q1 的证据门槛，不能因自动处理而跳过验证或独立审查。

### Q5：模型 API 接入

- 仅接受模型 API 接入，不要求通过 CLI 或订阅账户接入现成 Agent。
- 供应商导入方式参考用户指定项目：https://github.com/Gwex323/repo 。用户原始链接末尾的中文逗号按标点处理。
- 已通过本机 GitHub 登录读取该私有仓库；公开页面 404 不代表仓库不存在。
- 核查版本：`039494d933fae95e74895ffb67af208d1e3b9cd9`，默认分支 `feature/pre-108-baseline`。
- 依据：`docs/model-providers.md`、`frontend/model-providers.tsx`、`frontend/agent-models.tsx`、`docs/adr/0056-agent-role-models.md`。
- 导入交互：手工新增／编辑，或读取 JSON 文件／粘贴 JSON 文本；JSON 接受单个供应商、供应商数组或含 `providers` 数组的对象。
- 供应商字段：`name`、`base_url`、`api`、`api_key`、`models`；模型包含 `model` 与 `reasoning_effort`。
- 接口类型为 `chat_completions` 和 `responses`，允许自定义服务地址。
- 提供模型列表拉取与连接测试，列表接口不可用时可手填模型；基础连接成功不等于工具调用和交接能力已验证。
- JSON 导入只新增，不覆盖同名供应商，整批校验后一起保存；保存／导入本身不调用供应商。
- 每个 Agent 分别选择供应商与模型，可设置默认模型；正在运行的任务保留启动时的配置快照。
- 参考项目使用系统凭据库支持的加密保存，配置读取不回显密钥。其具体数量上限和旧版本迁移逻辑属于参考实现事实，不自动作为本项目产品限制。
- 借鉴范围为供应商管理交互与配置格式；本轮时 Agent 角色和运行时尚未确定，后续已由 Q19—Q24 确认。

### Q6：仓库记忆与共享经验

- 仓库原始代码、日志和完整历史默认保留在各自项目内。
- 跨仓库共享经过提炼和去敏的问题特征、修复方法与验证经验。
- 复用经验后，仍须在当前仓库重新验证，不能继承其他仓库的验收结论。

## 第三轮：已确认

### Q7：受支持的仓库路径

- 支持用户有维护权限的公共／私有仓库，在有权限的仓库创建修复分支并提交 PR。
- 支持允许 Fork 的第三方公共仓库，通过用户的 Fork 提交 PR。
- 权限不足时任务进入阻塞状态。

### Q8：自动入队与串行处理

- 已有和新增 Issue 经分诊确认符合 Bug 自动修复条件后，自动入队。
- 每仓库可暂停，可排除具体任务，用户可调整优先级。
- 全局同一时刻只执行一个修复任务。
- 正常等待释放执行位，执行障碍触发全局暂停（见 Q14）；同一修复任务内部的子 Agent 策略由后续架构方案论证。

### Q9：验证难例

- 无测试时先补充可证明修改前失败、修改后通过的回归测试。
- 原仓库已有失败检查须证明与本次修改无关且未恶化。
- 新增、相关或无法归因的失败均阻塞 PR。

## 第四轮：已确认

### Q10：独立工作区（已确认）

- 系统在受管副本或独立工作区中修改代码，由用户指定目标分支。
- 保留用户日常开发目录中的分支和未提交修改。
- 验证和 PR 绑定到系统实际处理的代码版本。

### Q11：导入必须全仓深度扫描（已确认）

- 用户选择每次导入都必须完成全仓深度扫描，不采用导入轻量分析加可选深度扫描的推荐方案。
- 扫描结果仍先保存在本地作为缺陷候选，由用户选择是否启动修复。
- 全仓扫描范围已由 Q13 明确，完成证据和预算耗尽后的状态已由 Q16 明确；未完成扫描不能标记为已完成，也不能使该仓库进入自动修复。

### Q12：阻塞时暂停整个队列（已确认）

- 用户选择出现阻塞就暂停整个队列，等待用户处理，不采用跳过阻塞任务并继续其他任务的推荐方案。
- 执行上限耗尽后的任务不得自动无限重试或自动跳过。
- 每个任务的时长、模型调用量和修复轮数上限可配置，具体默认值在方案中给出。
- 阻塞与正常等待的区分及只读巡查行为已由 Q14 明确；人工处理后恢复的具体交互在方案中设计。

## 第五轮：已确认

### Q13：全仓扫描范围

- 逐模块检查仓库自己维护的源码、测试、配置、CI 和依赖声明。
- 排除构建产物、下载的第三方源码及二进制文件，并保留排除记录。
- 第三方依赖仍检查其声明、版本与使用方式。

### Q14：阻塞与正常等待

- 权限不足、环境无法启动、验证无法完成、预算耗尽等执行障碍触发全局暂停。
- 等待用户批准功能方案或等待 PR 评审属于正常等待，可释放执行位并处理其他任务。
- 全局暂停期间仍保留只读 GitHub 巡查和状态同步。

### Q15：记忆写入与人工管理

- 修复通过验证和独立审查后，自动提炼可复用经验。
- 失败尝试作为失败经验单独标记，不能作为已验证解决方案。
- 用户可查看、纠错、禁用和删除经验。

## 第六轮：已确认

### Q16：扫描完成的证据门槛（已确认）

- 扫描绑定明确的代码版本。
- 生成覆盖清单、逐模块审查记录、适用检查的基线结果，以及发现缺陷时对应的候选证据。
- 上述工作全部完成后，该仓库才可进入自动修复。
- 按后续 Q36 的细化规则，覆盖／证据缺口先在原预算和授权内自动补全；无法恢复或耗尽上限才标为阻塞并全局暂停，等待用户处理。未完成工作不能被标为扫描完成。
- 完成状态表明约定扫描工作已完成，不代表已证明仓库不存在任何缺陷。

### Q17：最终支持边界与首批验证样本（已确认）

- 最终产品可适配多语言项目，以 Python、JavaScript／TypeScript 的 Web 和命令行项目作为开发路线的首批验证样本。
- 需要专用设备或无法获得的私有服务时明确阻塞，不声称已完成验证。
- 首批样本是分阶段验证安排，不改变最终架构的多语言可扩展目标。

### Q18：PR 提交后的持续跟进（已确认）

- 提交前通过验收并创建 PR 后，持续跟进 CI 和维护者评审。
- 必要修订重新进入串行队列，并再次执行验证和审查。
- 跟进持续至 PR 合并或关闭；合并由用户或仓库既有规则执行。
- PR 关闭与 PR 合并分别记录，不能仅因关闭而宣称 Issue 已解决。

## 第七轮：架构根决策（已确认）

- Q19：一个代码仓库内的模块化单体，本机分别运行 API 与独立 Worker。API 管配置、人工操作与状态，Worker 管长任务。
- Q20：Python + FastAPI 后端，React + TypeScript + Vite 前端。
- Q21：程序化工作流管理状态转换、预算、全局暂停和验收门槛；Agent 分析、修改并提交结构化证据，由专门发布程序核验后操作 GitHub。

## 第八轮：执行底座与协作（已确认）

- Q22：LangGraph 承载明确阶段、检查点和暂停恢复，Deep Agents 承载任务内模型与工具循环；应用补齐任务调度、扫描覆盖、验收、幂等发布和沙箱，不要求托管 MDA。
- Q23：处理 Agent 与独立审查 Agent 两类核心角色。扫描、调查、规划、复现和实现作为处理角色的不同任务模式；复杂工作按需委派子任务，分开会话和模型配置；测试与验收由程序掌握。
- Q24：全仓扫描、Issue 修复和 PR 返修共用一个全局重任务队列，同一时刻仅执行一项，API 和只读 GitHub 巡查独立运行。

## 第九轮：持久化与执行边界（已确认）

- Q25：最终本地单用户版默认 SQLite WAL，保留 PostgreSQL 适配边界；接受单写约束，将双进程锁等待、目标负载和崩溃恢复纳入验收。
- Q26：仓库、扫描批次、业务任务、运行和 PR 分别管理状态；业务数据库记录为对外权威，LangGraph 检查点保存运行内部进度与上下文，恢复时核对业务记录、检查点和实际产物；验收绑定代码版本，修改后重新验证。
- Q27：仓库命令与 Agent 文件操作默认在 Docker Linux 中执行，Windows 使用 WSL2 后端；本机 API／Worker 协调；原生执行适配须显式启用。

## 第十轮：核心流程与恢复（已确认）

- Q28：固定代码版本，由程序建立文件／模块清单和检查基线，逐模块审查并保存覆盖证据，程序核验完成门槛。同版本断点续扫；目标分支变化后旧结论过期，补扫受影响范围，影响无法可靠确定则全仓重扫；每次重新导入仍全仓扫描。
- Q29：修改前复现证据 → 修改 → 受控 Runner 验证及基线比较 → 独立只读审查 → 程序核对当前版本证据包 → 发布 PR。预算内返修，修改测试不能削弱验收，证据失效后重新验证。
- Q30：数据库持久队列配合短事务领取、租约和心跳；异常退出或宿主重启发现未结束运行时，先暂停并核对记录、检查点、代码、旧命令和远端操作，由用户处理后恢复。PR 回执丢失先核对，结果不明不重发。

流程图与具体故障场景见 `docs/workflow-design.md`。

## 第十一轮：能力、记忆与 GitHub（已确认）

- Q31 已确认：Agent 通过 Harness 的结构化任务／结果协议交接，子任务默认串行、同一工作区单写，审查使用独立只读会话；供应商密钥留在宿主模型适配层，GitHub 写凭证留在发布程序，按当前运行授予工具，程序收集和核验验收记录。
- Q32 已确认：业务记忆为事实源，使用结构过滤、FTS5 关键词与 sqlite-vec 语义候选的本地混合检索，CPU embedding，索引可重建。语义未就绪时明确降级到关键词／结构检索；禁用和删除影响新检索，经验仍在当前仓库验证。
- Q33 已确认：GitHub 用户 token 配置与本地条件轮询为默认，按仓库权限使用适用的 fine-grained PAT，第三方 Fork 贡献使用有对应权限的 classic PAT 用户路径，保留认证适配边界。轮询处理分页、去重、限额和周期复核。

## 第十二轮：跨系统验收与模型能力（已确认）

- Q34：按仓库预设复现、回归、基线比较和独立审查门槛取得有效证据后创建 PR，再跟进 PR 事件专属 CI，两类证据分开记录。如果目标问题只能在 PR 环境验证且没有其他有效提交前证据，则保持阻塞。
- Q35：运行前按角色检查必需工具／结构化结果能力，记录配置版本并保持运行快照；瞬时错误有限重试，必需能力不兼容、持续错误、配额／预算耗尽全局暂停；默认不自动跨供应商切换，由用户调整配置并恢复。保存／导入供应商仍不自动调用模型。

## 第十三轮：扫描自动补全（已确认）

- Q36：用户选择最终覆盖／证据核验发现缺口时，在原预算和授权范围内先自动补扫、拆分重试、重跑检查或重建受管环境；无法恢复或耗尽上限才转入全局阻塞。
- 具体动作和边界见 `docs/scan-recovery-proposal.md`；进入阻塞后的人工恢复规则不被自动补全绕过。
