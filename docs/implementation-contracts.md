## 2. 进程及调用归属

| 执行者 | 可执行的工作 | 调度边界 |
| --- | --- | --- |
| API 进程 | 配置、人工操作、状态读取、持久化任务请求；管理只读 GitHub 同步循环 | 默认单 API 实例；同步另有数据库租约，避免启动多个同步器 |
| 只读同步循环 | GitHub 读取、对象更新、记录待分诊／返修信号、更新同步进度 | 不调用推理模型、不运行仓库命令、不发布 PR；允许写本地业务记录 |
| Worker | 扫描、模型分诊、方案生成、修复、审查、返修、模型提炼及维护任务 | 共用唯一执行位，不在旁路再启动 Agent 或仓库命令 |
| 受控 Runner／发布器 | Worker 调用的执行与发布组件 | 不是另一个自由调度器；同样校验执行权和当前操作版本 |

本地 API 默认只监听回环地址，生产前端使用同源静态资源；配置和执行操作校验本地会话及请求来源，开发 CORS 限定具体前端来源。不能把“本地单用户”解释为所有来源均可调用的无认证发布接口。会话和模型／GitHub 密钥不交给仓库进程，密钥存储使用宿主凭据库及其权限，不能把明文或解密密钥直接放在业务库旁。

同步循环由 API 生命周期管理，依靠持久化水位恢复；它不是持久重任务执行器。FastAPI `BackgroundTasks` 不承载扫描／修复或代替数据库队列。

“合格 Bug 自动入队”分两步：同步先保存待分析对象，Worker 取得执行位完成分诊，再推进原任务的修复阶段。巡检不会为了分类而绕过暂停规则调用模型。未完成扫描的仓库可同步、分诊或等待方案，但不能开始修复，包括用户选中的本地缺陷候选。

用户发起的模型连接／能力测试由有界诊断任务执行；模型列表等显式读取操作可由宿主适配层完成。保存／导入供应商不触发这些请求。全局阻塞时，用户可明确启动仅用于排障的诊断模式：确认旧执行停止后，独占执行位进行指定测试，不修复仓库、不发布，也不解除全局暂停。这样可以验证新配置而不绕过人工恢复。

需要模型调用的记忆提炼仍在 Worker 执行；没有模型调用的记忆编辑、状态禁用和查询可以由 API 完成。大批量本地编码／索引重建作为受管维护任务排队。在线查询编码属于当前任务；轻量查询与索引读不能发起额外推理 Agent。

## 3. 状态、任务标识与执行权

### 任务与运行

同一仓库的同一 GitHub Issue 使用稳定主任务标识。分诊、规划、修复及 PR 返修是它的不同运行模式；评审反馈、重试或重启不创建另一份独立修复和重复 PR。本地候选使用持久候选标识。用户选择候选并通过下述准入及敏感信息核验后，系统在目标 GitHub 仓库查询相似 Issue；确认是同一问题则关联该 Issue 及其主任务，未发现相似项才创建 Issue 并以远端 Issue ID 建立／复用主任务。查询不完整或结果含义不确定时不得创建重复 Issue，保存候选并等待核对。Issue 写入失败、回执丢失或结果未知时先按远端状态对账，Issue 身份未确认前不得创建修复分支或修改代码。扫描及维护任务有各自标识，并关联仓库、来源任务或导入请求。

GitHub Issue 创建采用持久操作意图与本地稳定幂等键；重试前按仓库、操作意图和候选来源查询可能已创建的 Issue，确认远端结果后才继续，不凭标题单独认领。Issue 标题与正文引用扫描位置、目标 SHA 和可核查证据，不把 Agent 推测写成已证实事实。Issue 创建成功是允许进入修复分支阶段的必要条件，不代表 Issue 自动进入修复就绪。

用户选择本地候选触发 Issue 查重／创建时，系统查询 Issue 列表及必要详情，所有必要分页成功后才可得出“未发现相似项”。相似度判定依据保留候选证据、标题／正文、涉及路径／符号、版本与已有 Issue 摘要；明确为同一问题时关联，无法确定是否重复时等待用户判定，不自动创建。GitHub 接口无法原子保证语义查重并发下不重复；同仓相同候选使用本地唯一操作意图和执行位串行化，创建前重新查询并在写后核验。不能将相似度分数单独当作无重复证明。

系统创建 Issue 由宿主受控发布适配器执行，仓库命令、Agent 容器和只读同步循环不持有写凭据。创建前保存操作意图，正文只陈述候选位置、代码版本、可复现依据与不确定性；创建后读取并核验仓库、稳定 Issue ID、标题／正文和状态。写请求回执未知时查询远端并对账，不盲目重试；远端身份确认后才绑定主任务并进入开放 PR 检查。创建 Issue 的权限不足、接口持续失败或远端结果无法确认时等待／阻塞，不能建修复分支。

同一 GitHub 稳定仓库 ID 的重新导入复用仓库身份，不复制 Issue 主任务、PR 关联或记忆范围；另建导入请求与扫描代次。人工排除／取消以持久标记保护，重复同步、Issue 重开或重新导入不得自动撤销；用户明确重新启用后再核对原任务及交付链。已结束任务有新反馈时可保存信号，是否恢复须按原终态处理，不能把“收到更新”直接等同于新建修复。

### Issue 准入与分诊

仓库配置保存版本化的 Issue 准入模式、允许／排除标签映射、当前 GitHub 执行身份、严重程度映射及认领评论开关。同步范围与修复准入分开：首次同步已有 Issue，后续同步新增及更新对象；未准入对象也保留事实和原因，不因模式过滤丢失用于查重、PR 竞争或终态核对的信息。只读同步不调用模型、不修改 GitHub，模型分诊仍由取得唯一执行位的 Worker 完成。

| 准入模式 | 可进入分诊与后续处理的来源 | 初始选择 |
| --- | --- | --- |
| 手动选择 | 用户在 UI 明确选择的 Issue／本地缺陷候选 | 用户可按仓库启用 |
| 标签准入 | 命中仓库配置允许标签的 Issue，或用户明确选择的 Issue／候选 | 第三方公共仓库默认；允许标签未配置时显示待配置，不自动降级为全部准入 |
| 全部合格 Bug | 所有开放 Issue 可分诊，确认符合条件的 Bug 才自动进入修复；功能／重构仍须方案批准 | 用户自有或有维护权限的公共／私有仓库默认 |

仓库类型依据实际权限及贡献路径确认，不能仅凭公开／私有推断。标签名称由仓库映射配置，不假设统一标签体系，也不为准入自动给远端打标签；不要求合格 Bug 一定有 `bug` 标签。人工选择只替代入口筛选，不跳过持久排除、他人占用、敏感信息、Issue 身份、外部 PR、扫描、复现或验收门槛。

自动修复须同时满足：Issue 开放且属于当前仓库／目标范围；未被用户排除／取消；分诊确认是 Bug、目标和验收条件清楚，有可执行的定位／复现路径；没有同一问题的外部开放 PR、另一活跃受管修复或他人明确处理中的证据。外部 PR 及受管任务命中时分别关联等待或复用原任务，不复制任务。进入正式复现前只是判断信息是否足够，不能将“存在复现路径”记作已复现；后续仍须取得修改前失败／修改后通过证据。

默认不自动处理以下来源：有非当前 GitHub 执行身份的 assignee；维护者明确表示正由他人处理；命中 `needs-info`／`blocked`／`wontfix`／`duplicate`／`question` 等已配置排除标签；问题信息不足、需产品决策或涉及安全披露。assignee 为当前身份本身也不证明已由本系统认领；须核对本地原任务与处理上下文。普通评论活跃或仅文件重叠不能单独证明他人占用。标签与正文矛盾、身份／占用关系不明时等待 UI 澄清，不凭模型置信分数强行入队。

安全漏洞、密钥／敏感数据泄漏及披露方式不明的候选默认只保存仓库范围的脱敏待人工事项，不自动创建公开 Issue、PR 或认领评论；此检查在本地候选创建 Issue 之前执行。用户须在 UI 明确处理方式与适用范围后才重新分诊，普通选择或允许标签不等于批准公开披露。记录及诊断不回显秘密。

分诊输出保存类别、原因码、证据引用、Issue／评论／标签／assignee／目标版本、准入策略修订、验收规范或待补充项及重新分诊条件；类别与业务任务状态分别保存：

| 分诊结果 | 状态与处理 |
| --- | --- |
| 自动修复 | 准入和目标明确，推进原任务；扫描／权限／复现／发布等仍按阶段核验 |
| 等待补充信息 | 描述不足、占用／分类／关系不清或需确定敏感处理方式；正常等待并在 UI 提供材料补充、范围／接手确认、重新分诊及取消入口 |
| 等待方案批准 | 功能、大规模重构、需产品决策或一个 Issue 含多个独立交付目标；正常等待具体方案和验收确认 |
| 已排除 | 不符合入口策略、他人已指派／明确处理、排除标签、已关闭或用户明确排除等；保存原因，不创建修复执行；已关闭仍先核对相关 PR 终态 |
| 外部修复处理中 | 已确认同一问题的外部开放 PR；关联观测并正常等待，不建重复分支／PR |
| 执行阻塞 | 已执行任务遇到复现、环境、权限、预算、无进展等障碍；持久化原因并全局暂停，UI 提供处理及显式恢复 |

`needs-info`、普通描述不全等在分诊阶段映射为等待补充信息，`blocked` 等原因可映射为策略排除；这类输入／策略未满足不等于系统执行失败，不触发全局暂停。进入正式复现后仍无法证明 Bug，或必需权限／环境等执行障碍，继续按已有阻塞规则处理。因标签、assignee、入口策略等形成的排除记录与用户持久排除标记区分：相关事实变化可重新分诊前者，后者必须由用户明确重新启用。

### 本地占用、优先级与重新分诊

分诊／修复复用原主任务，通过数据库唯一约束及执行权取得本地占用；本地占用不代表独占 GitHub Issue，建分支前及发布前仍读取最新 assignee、占用证据、Issue 状态及相关 PR。他人中途接手时在安全边界保存现场，停止按旧条件自动发布，并在 UI 展示新的排除／澄清原因；不覆盖、移除他人 assignee 或继续争抢任务。

默认不修改 Issue assignee、不发表评论。仓库可显式开启认领评论，启用时展示拟发布的模板及发布时点；仅在准入确认、扫描就绪且即将实际开始修复时由宿主受控发布器执行，未配置权限或结果未知时按写入对账规则处理。认领评论使用稳定意图去重、回执未知先读取核对，不因重试／重启反复评论；评论不是分布式锁，不能替代前述占用和 PR 核验，也不扩展为自动索取信息或发布进度评论的授权。

只在已就绪任务中排序，不抢占正在运行的重任务。用户显式设置的优先级最高；未人工排序的任务按可配置严重程度标签形成自动优先级，未命中映射取普通级、多个映射取其中最高级，同级按原入队时间和稳定标识。自动排序域采用老化规则：累计可执行排队时间每满一个配置间隔提升一级，最高至最高自动优先级；初始间隔 24 小时为待实验校准的可配置值。暂停、缺前置条件及正常等待不累计该时间，重试不重置原排队历史。老化不越过用户显式优先级或任何就绪门槛，持续人工置顶时不承诺自动域之外的绝对无饥饿。

Issue 编辑、相关评论补充、关闭／重开、标签／assignee、准入策略、目标分支及验收范围变化均登记重新分诊信号，重复相同载荷不重复分诊。纯同步只保存对象及信号，Worker 在取得执行权后消费；暂停期间不旁路调用模型。执行中保持原快照并在安全交接／发布前核对最新修订，实质范围／验收变化使旧方案批准失效；目标 SHA 变化本身按补扫／重验处理，不在目标与验收不变时无故作废方案。手动模式的新事实不自动变为用户选择，持久排除不会因重开或重导入撤销。

| 业务任务状态 | 可领取执行位？ | 含义 |
| --- | --- | --- |
| 排队 | 满足前置条件后可领取 | 全局正常、仓库未暂停、无其他执行者；修复还要求当前目标版本扫描就绪 |
| 执行中 | 已持有 | 阶段及产物持续记录，不能由另一运行接管 |
| 正常等待 | 否 | 等待方案／意见澄清、额度耗尽前的预算续期批准、前置扫描、CI 或评审；无遗留写命令时释放执行位 |
| 阻塞 | 否 | 执行障碍且需要人工处理；业务状态持久化并触发全局暂停 |
| 结束／取消 | 否 | 必须记录原因和结果；未修复、不合格 Issue、关闭未合并及合并分别表达 |

任务运行完成可以使业务任务进入正常等待，不等于整项任务结束。PR 等待或正常图中断是有意挂起，重启时不因存在 checkpoint 就误报崩溃；只有实际处于执行中的旧运行或无法解释的执行权／副作用需要异常恢复。

### 执行权与暂停

领取时在同一短事务内核验全局暂停、仓库暂停、任务前置条件及唯一执行位，写入运行标识、递增执行代次、租约和心跳。工具、产物写入与发布器均校验当前代次；旧 Worker 的结果不能覆盖新运行。心跳使用独立短事务，长模型请求或命令不能阻塞续约。

只在满足前置条件的任务中按本节“本地占用、优先级与重新分诊”的人工优先级、自动严重程度与老化、入队时间和稳定标识排序领取；正常等待／仓库暂停的队首任务不挡住其他可执行任务。前置扫描与其依赖关系必须持久化，调高修复优先级不能越过未完成扫描；全局阻塞则禁止领取所有常规重任务。

依赖创建、父任务进入等待和释放执行位须形成可恢复的业务交接；依赖成功后以同一事务记录结果并唤醒符合条件的等待任务，防止“扫描已完成但修复永久等待”。多任务依赖同一有效扫描时可共享其结果，取消非预算归属的等待方只解除其依赖。若取消同时撤销扫描的预算授权，须安全停止扫描、保留其他等待方的依赖并等待用户明确处理，不继续消耗已撤销预算，也不自动转移成本。

租约丢失后停止发起新调用并进入恢复核对；租约到期不证明旧命令已停止。启动新 Worker 不自动接管旧命令。取消、人工暂停或退出时，要停止／隔离旧进程并核实无残留写入，再释放工作区和执行位；不能先释放再等待旧命令退出。

全局暂停期间只读同步、人工管理与明确授权的排障仍可工作。每仓库暂停禁止领取该仓库的常规重任务，仍可同步；活跃运行在安全阶段边界保存并停止，尚未结束的命令占用执行权。恢复需显式核对所有未解决阻塞原因；取消某个任务不会自行解除全局暂停。

### 人工处理入口与操作

凡流程需要用户选择、确认、澄清、排障或恢复，必须在 UI 提供可到达、可执行的处理入口，不能仅显示“等待人工”或“阻塞”。任务详情为处理上下文，仓库／扫描／PR 详情及系统暂停页提供对应入口或直接跳转；待人工处理列表集中展示仍未解决的事项。全局／仓库暂停期间这些管理入口仍可用。P1 提供通用事项与处理框架，各阶段引入能力时同步交付对应入口，不将必要人工操作推迟到 P6。

每项人工事项保存稳定标识、类型、原因、关联仓库／候选／Issue／PR／任务、当前输入及对象修订、证据引用、可用操作、所需输入、操作前置条件和处理结果。页面展示操作后的预期状态；暂不可执行的操作须说明缺少的条件并提供补充入口。刷新后回读持久记录，已完成事项保留决定、依据及操作结果，不因刷新重复发起执行。

| 人工介入类别 | UI 必须提供的处理入口 | 后续核验与状态 |
| --- | --- | --- |
| 本地扫描候选选择 | 查看位置／版本／证据，选择处理或排除 | 选择后由系统查重并创建／关联 Issue，不让用户手工创建成为必经步骤 |

人工操作由 API 校验并持久化，携带稳定操作标识、请求内容及预期对象修订；相同操作同内容返回原结果，不同内容或过期修订返回冲突并要求刷新核对。需重新执行的请求保存为受管任务／诊断意图并展示排队、等待恢复、执行中、失败或完成及其原因；API 不在旁路执行模型、仓库命令或发布。无法持久化时明确报错，不把点击成功当作决定已保存。

人工决定不等于验证通过或队列恢复。提交后重新核验 Issue 身份、PR 关系、最新输入／代码版本、扫描就绪、预算、执行权及所处阶段的证据；仍有障碍时保留原因与处理入口。普通确认仅推进原任务的正常等待；阻塞暂停必须另有显式恢复操作或在同一请求中明确包含恢复意图，并通过全部恢复核验。用户不能通过“忽略阻塞／强制通过”按钮绕过必要门槛。

### 预算

模型调用、SDK 内置重试、子任务、扫描拆分、环境重建和返修都计入原任务的预算。运行／batch 的变化不重置累计计数；等待队列或人工输入的时间不计入有效执行时长。任务至少有累计有效时长、模型请求／token 上限及修复／恢复轮数。区分可经批准追加的任务授权总额与运行安全上限：单次请求／命令有超时、模型有最大输出，阶段有工具步数和有界尝试限制，具体值在运行前按版本化策略解析保存；不能通过新建阶段或运行绕过原任务账本或无进展检测。

修复轮数按“修改→验证”计数，PR 返修继续累计；不能因新建运行就重新获得完整预算。达到上限后按规则阻塞，用户可以明确调整预算并恢复，调整留记录。报告中的数字是实验初值，任务启动前解析并保存具体值；时长、调用量与轮数等任一适用上限触发即停止继续消耗，不能用另一项尚有余额抵消。记忆提炼等后续模型工作也要预留和计入预算，不能隐含免费调用。

每项实际执行必须绑定持久的预算归属标识。导入及其漂移批次计入该导入预算；修复新建的前置补扫计入发起修复的原预算，不能因另建扫描 Task 获得新额度。关联已有合格扫描时保留其既定预算归属，同一执行只记账一次，不重复收费或事后转移消耗。明确发起的诊断单独解析有限预算，不恢复已耗尽的业务预算。等待本身不计时，但有归属的扫描／维护执行时间照常累计。

### 无进展检测

程序对扫描补全、调查／分诊、模型工具循环、修改—验证—独审、PR 返修及提炼等重任务记录可比较的尝试。尝试有明确子目标及结束条件；工具返回、检查完成及阶段交接时记录主任务／预算归属、阶段与目标、输入／验收／环境／策略修订、目标与候选代码内容、归一化动作、失败签名、有效覆盖／证据引用及新增进展。单阶段不能无限延迟结束尝试来逃避检测；请求／命令超时、工具步数和阶段安全上限仍独立生效。

进展须由程序核对实际产物与目标关联，不采信 Agent 自述的完成百分比。有效进展包括：新增有效模块／子范围覆盖、补齐可验证证据、用真实实验排除一个此前未排除且与目标相关的假设、复现或验证条件得到实际改善、修复了一个经证据确认的子问题。仅改代码／Diff、生成新日志或报告、增加调用量／token、刷新时间戳、重命名任务／阶段、重启、新建 Run／批次、分支 SHA 改变及重复取得相同结果，均不能单独作为进展；已有证据失效须同步扣除其当前有效性。

| 检测项 | 初始默认规则 | 处理 |
| --- | --- | --- |
| 连续无进展 | 同一阶段目标连续 3 次已完成的可比尝试，没有新增有效证据或目标推进 | 在下次模型／工具调用前停止，保存尝试及差异，记为无进展阻塞并全局暂停 |
| 状态／代码振荡 | 同一目标在 A→B→A 等状态／候选内容间完成 2 个重复周期，且没有净新增有效覆盖、证据或已解决子目标 | 记为振荡阻塞并全局暂停；阶段按正常设计往返但持续取得有效进展不算振荡 |
| 长时间单步不返回 | 请求／命令或阶段达到预先保存的安全上限 | 停止或隔离执行并核对现场，未确认旧命令停止前不释放执行位，不靠等待更多尝试规避超时 |

上述 3 次、2 个周期为可配置的实施初值，需用复杂任务与故障样本校准，尚非实测结论；策略修订留痕，运行中不得自动放宽。比较指纹忽略时间戳、随机 ID、非语义日志差异，基于阶段目标、归一化动作、代码／验收内容、失败类别及有效证据差异；不同阶段按对应目标解释，不机械比较日志字符串或仅凭测试退出码。只有经核验的实质进展才清零连续无进展计数并推进水位，原尝试及振荡比较历史仍保留。新发现的真实反证可算调查进展，但重复排除同一假设不算。

正常排队、人工／CI／外部 PR 等待、退避间隔不计为失败尝试；未结束且未超时的长检查不因心跳间隔内没有新产物而被判无进展，心跳本身也不能证明进展。目标分支持续变化时保存失效与重验链，换 SHA／Run／批次不能清空原目标的无进展历史；新版本出现本身不构成进展，单纯追赶而反复失去已有成果仍受无进展及累计预算控制。

检测记录、进展水位、计数、策略修订及阻塞决定持久化，崩溃、续期和返修不清零。触发后 UI 展示窗口内尝试、证据／失败签名、已完成与剩余工作，提供补充材料、修改策略／环境、有界诊断／重试及取消；单纯提高预算或点击恢复不足以清除该阻塞。用户提交实质处理方案并明确授权有界重试、完成安全与输入前置核验后可开始新的检测窗口，旧记录保留；重试仍失败时按新窗口或更早命中的安全上限停止。恢复前核验的是安全重试条件，不能要求先取得尚未执行的重试通过证据；交付仍须通过真实验证与独审。

### 进度驱动的预算续期

初始授权按任务类型、仓库规模、批准范围及预计工作量分配，不能把首批样本的固定额度当作所有复杂任务的永久总额。每次模型／工具／子任务开始前检查剩余授权并预留该步上界，已用、已预留及用量未知的保守占用都计入可用余额；没有足额授权不发起新消耗。初始预检即发现额度不足、尚无执行进展时，明确显示预算配置不足并提供有限调整入口，不能编造进展作为自动续期理由，也不凭零次尝试判为无进展。

任一授权维度达到 80% 时初始预警；若尚有必要工作且预计剩余不足、估计不可靠，或下一必要步骤无法在剩余额度内足额预留，则在安全边界保存检查点并提出有限追加申请。若有证据表明现有额度足够完成，则可在原授权内继续，不能仅因超过预警比例强制停下。80% 为可配置的实施初值，预警不自动加额；请求不能通过缩小预留绕过限制。

申请从持久产物生成，至少展示：原授权及各维累计／预留消耗、最近有效进展与证据、已完成／剩余子目标、继续策略、下一阶段交付目标、申请追加的时长／调用／token／轮数及估算依据和不确定性。无法可靠估计时标为待核实，由用户填写或选择有限额度，不编造精确费用或剩余时长；模型辅助估算须在现有额度内执行，不足时用已有记录生成申请，不能为申请额度先超额调用。

耗尽前、仍有实质进展且没有其他执行障碍时，申请进入“正常等待预算续期”并释放安全执行位，不因预先申请就全局暂停；原阶段继续所需的额度等待批准。已耗尽任一实际授权上限、触发无进展检测或其他障碍时仍进入阻塞及全局暂停，不能改名为续期等待绕过原规则。正常续期等待不占有效执行时长，也不计为无进展尝试。

UI 提供查看证据、批准建议追加、填写其他有限额度、要求调整方案／范围、拒绝／取消；自动推荐须有进展证据，用户仍可在无进展时提出实质处理方案，但加额本身不解除无进展阻塞。追加须用户明确授权，系统和 Agent 不得自批、无限续期或自动扩大任务范围；实质范围／验收变化先按方案批准规则处理。

授权事务绑定主任务、预算归属、账本／申请修订、当前输入及进展水位，保存稳定操作标识、批准人、依据、各维增量与新总额。新授权总额等于原总额加已批准有限增量，累计已用及历史检测记录不变；重复批准同一申请不重复加额，过期申请须刷新核对，权限不允许给共享扫描转移成本。拒绝仅保持等待或按用户明确选择取消，不隐含启动执行。

耗尽前正常等待的任务在批准后重核当前输入、代码、配置、预算、安全与扫描等前置条件后重新排队；已有全局／仓库暂停或无进展阻塞时，批准额度不自动恢复，仍需明确恢复意图及相关原因处理。每个主任务／预算归属的同一续期修订仅有一个待处理申请，新消耗或输入变化时更新／作废旧提案；不能用重复通知或新建任务反复索取同一额度。单阶段／单请求安全上限的调整须另有明确、留痕的授权，追加总额度不自动关闭这些保护。

## 4. 扫描版本、补扫与修复就绪

仓库扫描就绪绑定目标分支的确切提交。扫描批次固定一个提交及清单；同一提交内可补齐缺口，不能将批次中的 SHA 改掉后保留旧“完成”标签。

就绪标识同时绑定仓库 ID、目标分支配置修订、当前导入代次、目标 SHA 和扫描策略修订，SHA 相同只是必要条件。每次新的导入请求在同一业务事务内增加导入代次、撤销当前就绪并登记完整扫描；重试同一人工操作不增加代次。旧代次完成只能登记历史结果，不能重新放行当前代次；当前代次必须取得本次完整审查证据，不能以旧全仓扫描结果替代。正在修复时发生重新导入，运行到安全边界保存现场并等待该门槛，发布前必须再次核验。

扫描范围／排除／适用检查策略发生实质变化时增加策略修订并重新建立覆盖依据；环境、依赖解析或检查工具变化时重新评估对应检查结果的有效性，不因代码 SHA 相同就无条件复用。目标分支配置改变使旧就绪失效；已有任务和 PR 仍保留原目标快照，未经明确处理不自动改投另一分支。

目标分支变化时保留旧批次的历史结果，撤销其对新版本的就绪效力，建立新批次。可靠确定影响范围时，新批次关联旧覆盖依据并补扫受影响文件及其依赖、配置、测试；无法确定影响范围就全仓重扫。新版本清单中的每一受检项都必须有新检查或明确的可复用依据。一次导入内的漂移、补全与拆分共用该导入任务原预算；每次用户重新导入仍建立完整扫描任务。

PR 分支中的未合并修复不改变目标分支扫描就绪状态；其变化由任务验证与独立审查覆盖。修复开始前及发布前重新读取远端目标分支：如已变化，先保存现场、让任务等待前置扫描并释放执行位，给补扫任务运行机会；补扫完成后把最新 base 纳入候选、重新验证及审查。不能持有唯一执行位等待另一个扫描任务。普通版本变化是受管前置工作，只有补扫／整合无法完成或预算耗尽才转阻塞。

### 覆盖完成依据

- 清单来自固定 Git 树，包含隐藏文件、CI 配置、测试和依赖声明；不能用 `.gitignore` 或文件过大作为排除自有受检内容的理由。排除项记录路径、归属、原因与版本；Agent 不能临时扩大排除范围。
- 每项记录路径、内容标识、模块和分块范围；过大文件拆分，子范围必须覆盖原输入。记录实际送入审查的内容及对应结构化结果，不能只记录“列举到文件”或接受 Agent 的全仓完成声明。此证据证明完成约定审查，不证明模型理解或发现所有 Bug。
- 自有子模块按固定子提交处理，第三方内容明确排除并检查声明；LFS 指针不等于实际内容，符号链接不越过工作区读取。需要的自有内容无法取得时不能声称完成；二进制／第三方等约定排除项单独登记。
- 检查结果区分通过、已有失败、有依据的不适用、无法执行。没有测试配置可以注明不适用；声明存在的检查因缺环境无法运行属于缺口，先自动补全，失败后阻塞。已有缺陷导致的真实失败可以记录基线和候选，不要求扫描把全部测试修绿。

扫描不修改业务源码、锁文件或验收配置来取得通过。依赖准备在隔离环境按已有声明进行；运行生成的缓存和产物存放在受管位置，核对扫描前后的源码内容。新发现缺陷先建本地候选；用户选择后查询相似 Issue，关联已有项或由系统创建 Issue。完成 Issue 关联且仓库扫描就绪后，才可进入修复分支及代码修改。

扫描模式的文件工具只读受检源码，临时分析输出使用独立目录；需要构建写文件时由 Runner 在受管检查副本执行并记录差异，不把“禁止修改”仅写在提示词中。扫描能够记录已有失败，不表示后续修复可绕过必要的可执行验证。

## 5. 证据与验收的准确对象

证据绑定的对象至少包括：任务输入／验收规范版本、base SHA、候选提交及 Git 树、复现探针、环境与工具版本、命令、退出结果、日志摘要、检查范围、独立审查结果。仅保存分支名或 `HEAD` 不足以确定被测内容：未提交修改、未跟踪源文件和测试产生的改写都可能改变实际运行内容。

最终验证前冻结候选代码，停止处理 Agent 写入，在只读或内容可核对的候选副本上执行 Runner 和独立审查。只允许已记录的运行产物；候选源码、测试或检查配置在验证后变化，相关证据与审查必须重新取得。发布的提交／树必须与最终证据一致；不能验证脏工作区后再另行拼出未经核对的提交。

### 不同任务的验收

| 范围 | 修改前与修改后要求 |
| --- | --- |
| Bug | 同一有效复现／回归探针在未修复代码上证明目标失败，在修复代码上通过；相关回归、基线比较与独审均通过 |
| 已批准功能 | 按批准的验收规范证明原代码缺少目标能力、新代码满足能力，并通过回归与独审 |
| 已批准纯重构 | 方案须包含可核查的结构目标及行为保持要求；证明原代码未满足结构目标、修改后满足，并用前后行为／回归证据证明约定行为保持。不能把环境错误伪装成修改前 Bug |

方案批准必须包括具体的验收规范，不能仅批准一句“重构一下”。以上不允许把 Bug 改名为重构来规避复现门槛。目标、规范和审查结论作为证据的一部分保存；批准任务也不能跳过 Runner、独审和发布核验。

复现探针在独立的 base 副本执行，可携带必要的测试文件和测试辅助材料，但不能夹带实现修复；记录探针内容及其在两侧的依赖。导入失败、缺包、超时或未执行到目标断言不自动算作复现成功。

PR 返修使用三个明确对象：当前上游 base、返修前 PR head、新候选。原 Issue 的前失败／后通过针对上游未修复 base 与新候选；不要求已修好问题的旧 PR head 再失败。针对评审发现的新增缺陷，另用返修前 head 与新候选证明修正；格式／结构意见按对应验收目标检查，不伪造失败。完整候选相对当前上游 base 的回归比较与独审仍必需，不能只检查本轮小 Diff 而漏掉原 PR 内容。

旧扫描基线不能永久代替修复基线。使用当前 base 和相同／可解释的环境与命令重新取得检查结果，核对测试发现数量、跳过项、断言及配置变化。新增、相关或无法归因的失败在预算内返修；无法消除或验证时阻塞。Runner 控制执行、记录和来源校验，独审判断测试有效性；二者不构成任意代码绝对正确的证明。

基线比较记录失败用例／原因特征，不能只比较失败总数或退出码；波动失败在有限预算内重新核验，仍无法归因就阻塞。检查没有运行、发现的测试变少或新增 skip 都不能简单记为“未恶化”。

## 6. Docker、凭证与宿主边界

API 和 Worker 使用同一操作系统侧的本地数据库路径；默认宿主进程均在 Windows，任务在 Docker Linux／WSL2 中运行。不能一个进程在 Windows、另一个在 WSL，再通过共享路径跨侧访问同一个 WAL 文件。若提供 WSL 宿主部署方式，API、Worker 及数据库也统一迁入该环境。

任务容器不挂载业务数据库、证据归档写目录、宿主凭据库或 Docker socket。处理角色只能写当前任务工作区，审查角色只读候选及必要证据；审查没有通用可写终端，需执行检查时请求 Runner 在独立临时环境完成。受控文件工具仍要限制符号链接和路径穿越。

原生执行适配仍需用户显式启用并满足任务权限和证据边界，不因切换执行方式而把模型／GitHub 凭据交给命令。原生进程与宿主用户共享能力的限制必须体现在适配验收中；不能满足边界的项目明确标为不支持或阻塞。

clone／fetch 和发布使用宿主受控 Git 适配，令牌不得留在 remote URL、仓库配置、环境快照或日志。持凭据的 clone 使用不检出代码的路径，后续物化与命令执行分开，避免宿主 checkout 调用仓库过滤器。私有包等额外凭据由宿主受控下载／代理处理；不能满足环境条件就明确阻塞，不把高权限凭据放进通用命令容器。

发布器只处理冻结提交与 Git 对象，不在持有 GitHub 写凭证时执行仓库脚本、测试、hooks、过滤器或不受控凭据助手。Git 操作使用受管配置；PR 评论和仓库文件均当作待分析输入，不能授予额外工具或改写 Harness 验收规范。

工作区物化、Git 换行、大小写、可执行位、符号链接及 LFS 需要在 P0 核对，最终候选树必须与容器实际被测内容对应。工具命令、退出结果和外部归档由 Runner 收集，被测代码输出的“通过”文字不能自行变成验收记录。

Git bundle 不包含 LFS 实体或子模块仓库的对象，物化与交付清单须分别跟踪这些外部内容。发布前核验所引用内容可由接收方取得；新增 LFS 内容只有具备已验收的受控上传适配时才可交付。若修改涉及未发布的子模块提交或无法交付的 LFS 内容，则阻塞当前发布，不自动扩展到子仓库推送、额外 PR 或在持凭据宿主运行仓库 hook。

## 7. 巡检、分诊和变更同步

初始巡检频率按用户调整为：活跃仓库约每 2 小时、空闲仓库每天一次，均可按仓库修改。为避免未定义的运行行为，实现默认把存在未结束任务／开放受管 PR，或最近 7 天观测到 Issue／PR 变化的仓库视为活跃，其余为空闲；7 天阈值是可配置的工程初值。PR／CI／评审跟进默认也使用该仓库频率，不暗中另加分钟级轮询。首次同步、人工“立即同步”和发布前必要读取不必等待定时器。

单 API 同步器保存每仓库的最近成功时间、下次到期时间和独立 endpoint／查询／分页验证器。服务停机后到期仓库执行一次补偿同步，不补跑全部错过的定时点；定时、人工和启动触发合并，凭同步租约防止重复请求。

定时、启动补偿和人工立即同步均读取当前目标配置对应的 GitHub REST `GET /repos/{owner}/{repo}/branches/{branch}`，取得响应的 `commit.sha`，与该配置下最新已确认的目标 SHA 和扫描就绪标识比较；路径参数按接口规则编码，使用仓库授权。为该仓库、目标配置修订及端点单独保存条件请求验证器和对应 SHA；304 仅在对应已确认 SHA 和配置仍有效时复用，否则重新无条件读取。P2 提供目标分支读取及漂移处理能力；P4 将其接入定时与人工同步。修复开始前及发布前独立发起无条件读取当前目标 SHA，不以定时同步缓存代替必要核验。

发现新 SHA 时，以当前仓库、目标配置修订、导入代次和 SHA 为范围持久化观测，撤销旧就绪并登记或关联相应前置扫描；重复触发及相同观测不得重复建立活跃扫描。旧请求返回时须核对同步代次和目标配置，不能覆盖较新观测；无法判断顺序或分支移动冲突时重读。目标分支不存在、权限不足、限流、网络或响应无有效 SHA 时记录失败或不确定状态，保留上次成功结果，不报告无变化；按同步退避，任务必要的最新状态无法核验时按执行障碍处理。补扫及预算归属遵循 §3—4，不因手动同步新建预算。

用户选择本地候选触发 Issue 查重／创建时，系统查询 Issue 列表及必要详情，所有必要分页成功后才可得出“未发现相似项”。相似度判定依据至少保留候选证据、标题／正文、涉及路径／符号、版本与已有 Issue 摘要；自动规则明确为同一问题时关联，无法确定是否重复时等待用户判定，不自动创建。GitHub 接口无法原子保证语义查重并发下不重复；同仓相同候选使用本地唯一操作意图和执行位串行化，创建前重新查询并在写后核验。不能将相似度分数单独当作无重复证明。

仓库界面提供“检查更新”入口，立即请求同一只读同步，展示请求中、最后成功时间、目标 SHA、无变化／发现变化／读取失败及关联扫描状态。相同操作标识与内容的重复请求返回原结果；不同触发在同步租约下合并，运行期间新请求不能被误报为已完成，须在已有读取能覆盖该请求时关联，否则安排后续读取。检测到变化后，扫描作为受管重任务排队；全局或仓库暂停期间只读同步仍可进行，扫描等待相应恢复。此操作不增加导入代次、不触发同 SHA 全扫，重新导入仍按 §4 执行。

更新以仓库 ID＋GitHub 对象 ID 去重；Issues 列表中的 PR 标识必须分流，不能当作 Bug Issue。评论、review、check runs、statuses 等按各自端点的分页能力读取，不能假设均支持 Issue 的 `since`。变更先持久化为待分析／待返修信号，Worker 按稳定主任务推进，重复请求修改不创建多个活跃修复。

对象更新、输入／反馈修订、待处理信号和对应事件一并提交。每次运行领取明确的信号集合及最高修订，结果落库时只确认该集合；运行期间新增的信号保留待处理，不能按 task_id 清空全部反馈。相同载荷不重复增加修订或刷新“最近有变化”时间；过期同步代次／较旧对象结果不覆盖较新观测。时间戳相同但载荷冲突，或端点没有可排序版本时，记录不确定性并重读，不把响应到达顺序当作远端先后。发布前必要读取也通过这一修订协议，不能写回旧快照覆盖巡检新状态。

分页可逐页保存，但只有该查询的全部必要页面成功并落库后才推进同步水位；使用重叠时间窗口与周期复核覆盖分页期间的变化。失败不能把 cursor 推到“现在”而丢失中间事件。304 只表示对应请求缓存有效；任何一页都不是全仓原子快照。

临时网络／限流等纯同步错误记录同步健康、保留上次成功时间、退避重试，不冒充“没有新变化”，也不自行触发模型或把正常运行任务全部标成失败。若任务在运行／发布时必须取得的权限或最新状态无法核验，才按执行障碍进入全局阻塞；暂停期间可继续尝试只读同步。

Issue 被编辑或关闭时更新原任务的输入版本，执行中不悄悄替换快照；发布前检查需求是否仍有效。已经关闭、被排除或发生实质范围变化的 Issue 不继续自动发布，按取消原因或正常等待澄清处理；重新打开先重分诊，不自动复制新 PR。关闭信号可能源于 PR 合并，终态判定需核对相关 PR，不能因同步先后顺序把已合并修复误记为取消。

## 8. PR 发布、返修与终态

### Issue 与 PR 一一对应

系统管理的交付关系采用一一对应：每个受管 PR 必须且只能绑定一个稳定 GitHub Issue；每个 Issue 在其受管生命周期内最多一个受管 PR，创建前可以为零，返修只更新原 PR。使用 Issue 稳定仓库／对象 ID 与 PR 稳定仓库／对象 ID 分别建立双向唯一约束，创建前占用该 Issue 的唯一发布意图，创建／回执对账事务及发布前核对均执行约束，不能只限制“同时打开”的数量或只凭正文链接判断。回执未知时不开始第二个创建意图；若远端已出现多个可能的创建结果，保留冲突并阻塞核对，不任意认领一个或宣称 GitHub 天然具备原子唯一创建。

不得将多个独立 Issue 合并进一个 PR，也不把一个 Issue 拆成多个受管 PR；为当前 Issue 必需的跨文件／跨模块改动可以在同一 PR 交付。若原 Issue 含多个独立目标，先在 UI 确认收敛或拆分方案，再由系统按查重／创建契约处理各独立 Issue，分别走自己的 PR；原跟踪项不能再用一个 PR 批量修复所有目标。未经确认不自行修改原 Issue 的范围或关闭状态。

受管 PR 正文、提交消息中的自动关闭声明及实际修改范围只针对所绑定 Issue，不生成同时关闭多个 Issue 的声明；必要的背景引用不作为第二个交付绑定。PR 已关闭未合并、合并后原 Issue 重开或原分支删除时均保留绑定，不自动重开／重建 PR，不因新 Run、重导入、解绑或换名绕过唯一关系；后续处理由 UI 按当前终态明确决定，不自动创建第二个受管 PR。新且独立的缺陷须先查重并确认独立 Issue，不能复制同一 Issue 来绕过限制。

GitHub 上他人可为同一 Issue 创建多个外部 PR，系统无法强制远端一一对应；这些 PR 作为竞争／历史／外部修复来源的观测记录保存，不占用或替换受管 PR 绑定，也不认领为本系统发布。确认外部开放 PR 解决同一问题仍等待，合并后仍核验目标分支；外部 PR 关闭未合并可在本系统尚无受管 PR 时恢复原任务。已有受管 PR 时只延续原交付链，不能再建一个。外部合并结果与本系统交付状态分别记录，保留事实，不通过丢弃外部 PR 伪造远端唯一。

### 发布与外部 PR 核对

进入修复前，在 Issue 已确认后读取该 Issue 及目标仓库相关开放 PR；发布前再次读取并核对同一 Issue 的 PR 状态、base／head 和最新版本。按问题关系分类：明确处理同一问题的外部开放 PR 关联到原候选／主任务并进入“等待外部 PR”，不创建自有修复分支或重复 PR；有证据确认与当前问题无关的 PR 不构成人工确认门槛，记录依据后继续原任务；只有关系无法判定时进入“等待用户决定”，并提供 §3 的 PR 对照与决定入口。不得仅因关联同一 Issue、涉及不同范围或修改相同文件就认定同一问题或要求人工；读取不完整与权限故障属于待核对／执行障碍，不能当作已确认无关。没有同一问题的外部修复且无待核实关系时，满足其余门槛即可创建分支或继续发布。

等待外部开放 PR 是等待其交付结果，不表示合入或问题已解决；等待期间继续只读同步。首次发现时已合入目标分支的相关 PR 不再进入开放 PR 等待，直接核验；等待中的外部 PR 合并后也须核验合并提交已进入目标分支，并在最新版本取得有效扫描／复现证据。确认问题已解决后将任务记为“由外部修复解决”，不声称本系统修复或发布重复 PR；问题仍存在或仅部分解决时重新核实剩余范围及相关 PR，再按当前输入和最新目标版本继续原任务，不能沿用失效证据。外部 PR 关闭未合并时重新读取 Issue 和全部相关 PR，确认问题仍存在且无同一问题的外部修复或待核实关系后才恢复原任务；其他情形按最新状态处理或在 UI 请求澄清，不设无操作入口的永久等待。Issue 关闭或合并期间状态变化按 §7 与 §8 复核。

发布前核对全局／仓库状态、执行代次、当前 Issue 输入及准入策略／标签／assignee／占用、Issue／PR 唯一绑定、base／head、候选树、验收及独审。写入操作意图后推送受管分支；已有分支须核对预期旧 SHA，禁止盲目覆盖外部更新。默认追加可快进提交；需要改写历史时按明确授权及预期旧版本保护执行。

任务保存上游仓库 ID、发布目标仓库 ID／Fork 所有者、base／head 分支及受管任务标识，不仅保存仓库显示名称。直接分支和 Fork PR 两条路径分别核验，受管分支稳定且不与用户日常分支混用；分支被删除或 PR 关闭后不自行重建提交链。

核对远端分支后创建／更新 PR，再读取实际 PR 的仓库、base、head、SHA 与预期一致才记录成功。回执丢失或超时先查所有相关状态，不凭标题认领、不盲目重发。创建接口没有通用幂等键或原子 expected-head-SHA，期间发现竞争就保留不确定结果、阻塞核对，不能承诺完全消除远端竞态。

PR 描述包含“概述、变更内容、设计方案／说明、验证／验收、review 记录”，必须关联已确认的 GitHub Issue 编号及候选来源。PR 专属 CI 发生在创建后，检查结果必须绑定实际提交、base／合并 ref 与来源；缺结果、旧版本绿灯或 pending 不算通过。

必要检查集合由版本化仓库策略及可取得的分支规则确定，记录检查来源／上下文和最新适用运行尝试。重跑中的同一必要检查不能沿用旧绿灯，已被适用新尝试取代的历史失败也不能永久压住状态；neutral、skipped、cancelled 或未产生检查的情况不默认视为成功，须按明确策略解释，不明确则等待或按任务必需验证障碍处理。无关检查不自动触发代码返修；政策变化后重新评估必要结果。

请求修改后，先记录评审 ID、对应提交及意见，再合并进原任务。Worker 对意见分类：明确范围内修改自动返修，歧义或功能／重构／验收范围变化等待确认。先核对意见是否已撤销、被新版本处理或引用旧代码，不能重复应用。返修从最新 PR head 开始，保留外部合法改动，重新验证与独审后更新同一 PR；多轮意见共享原任务预算，不生成重复 PR。意见到达不抢占正在执行的另一个重任务。

任务分别记录代码验证结果、PR 交付状态和 GitHub Issue 状态。PR 批准或合并不能倒填尚未完成的验证；关闭未合并不记作成功交付。合并由用户／仓库规则执行；系统不自动重开已关闭 PR、另发替代 PR或自动合并。PR 正常等待不持有执行位，CI／评审出现可处理失败时重新排队；持续执行障碍或预算耗尽才全局暂停。

## 9. 记忆写入、使用及纠错

| 内容 | 保存／使用规则 |
| --- | --- |
| 原始仓库上下文 | 代码、日志、完整处理历史归属该仓库；大型内容保留在受管工作区／产物归档，记忆记录引用路径、版本与摘要，不把整个仓库重复写成向量 |
| 已验证经验 | 有证据的症状、适用技术栈／版本、根因、修复方法、复现与验证方法；关联 Issue／本地候选、任务、运行、提交及证据 |
| 共享经验 | 从已验证经验提炼并去敏的通用方法，保留可追溯来源，不混入其他仓库原始代码、日志或凭据 |
| 失败经验 | 失败方法、失败原因和证据，单独标识；只能作为风险／避坑上下文，不作为已验证方案 |

验证和独审通过后自动提炼，不必等 PR 合并；提炼使用同一有效运行或串行维护运行、仅授予证据读取能力，不因再次调用处理模型而开放源码写入。它共享来源任务预算，失败保留待提炼状态和真实证据，不伪称已完成；持续模型错误／预算耗尽仍按执行阻塞处理。“代码已验证”和“维护者接受／PR 合并”分字段保存。扫描候选和模型猜测不能直接变成成功经验，根因推测不能因修复通过就自动标为已证实。提炼输出仍需程序验证来源、范围、必填项与敏感信息；无法确认可共享内容时保留仓库范围，不提升共享权限。

新任务及需要重新调查的返修按当前范围检索：先限定本仓与允许共享的记忆，区分成功／失败状态，再做 FTS5＋向量候选融合，回源核对版本、禁用／删除状态，限制注入量并附来源。经验不取代当前复现和验证；审查角色仍独立评估当前 Diff 和证据，不能把历史经验当作审查通过。

只读同步接到关联提交的新 CI 失败或请求修改时，先给相关经验记录“反馈待判断”，暂停其作为成功方案的新复用，由 Worker 串行判断关联性，不在巡检里调用模型。若证据推翻原修复／验证结论，保留待复核并在返修通过后生成新版本；若只是格式意见或无关失败，可以恢复原有效状态。纯格式意见不自动否定修复；PR 因非代码原因关闭也不自动把已验证修复改成失败。问题解决状态与交付状态始终分开。

反馈修订先保存在来源任务／验证记录，即使记忆尚未提炼也能拦截旧结论。提炼和反馈复核提交时核对来源证据、反馈水位及记忆修订；期间新增反证或人工编辑／禁用／删除时，不得把迟到结果写成有效成功版本，也不能用新 ID 绕过删除标记。来源记忆的共享派生经验一并受该来源的有效性约束；复核仅可恢复仍匹配的修订。提炼意图以来源证据版本去重，重试不复制成功经验。

记忆编辑产生内容版本；修改根因、方法等语义内容不能自动继承原验证标签，需重新关联证据或标为人工未验证。禁用／删除先更新事实源可用状态和修订号，再异步清理索引；回源过滤使旧索引无法重新返回该记录。注入块单独记录记忆 ID／修订，与原任务历史分开；恢复 checkpoint 时移除旧注入块并重新检索核验，不能从注入缓存重新加载已删除／禁用内容。已形成的代码证据仍按本次实际检查判断。

每次新的模型请求前都复核其记忆依赖，不只在恢复 checkpoint 时检查。模型摘要、压缩上下文及跨步骤缓存若包含记忆，也须保留可撤销的来源关联；无法可靠拆除失效内容时，舍弃对应上下文并从当前任务输入及有效代码／证据重建干净会话。不得将带失效经验的历史摘要重新发送为普通任务背景；已经发送的请求不能撤回，其返回也不自动恢复记忆有效状态。

记忆删除影响未来检索、注入和派生缓存；原任务审计产物及已发出的模型请求是独立留存对象，不能声称删除记忆会抹除这些历史。需要清理原任务产物时提供对应管理操作，不以删除记忆偷偷破坏验收证据。保留中的证据不得对外共享为原始上下文。

记忆事实更新和待索引事件在一个业务事务中保存。FTS／向量可以不同步，但索引记录须带内容版本和 embedding 配置，回源剔除滞后版本；换模型完整重建并在验证后切换索引，禁止混用维度或编码规则。语义不可用明确降级到关键词／范围检索。索引损坏可重建，业务事实源损坏则属于需人工处理的数据故障。

## 10. 持久化、迁移与正常启停

业务记录、图 checkpoint、记忆索引和产物归档的所有者及路径必须显式配置。可以分文件，但不能因同是 SQLite 就假定跨文件／连接原子提交；恢复关联任务、运行、图线程／检查点和内容摘要进行核对。产物先写临时文件，完整落盘后登记摘要；丢失或不完整时重建真实证据，不凭数据库引用推定存在。

默认配置 WAL、短事务、有限锁等待及各连接的外键约束；长模型／命令不持有写事务。双启动仍以执行权记录检查，而非寄望 SQLite 单写锁管理长任务。数据库不可写或存储已满时停止新执行／发布，不能在状态无法持久化时继续远程写入。

启动器管理 API／Worker 生命周期；正常停止先停止领取，结束或确认停止命令、保存产物并记录有意挂起。非正常退出或状态无法确认时，重启后暂停并人工恢复。数据库迁移由唯一迁移者执行，API／Worker 先停止访问；校验 schema 和依赖版本，不在运行中自动做破坏性迁移。

备份需要停止写入或使用一致性备份接口，图状态与归档建立同一备份清单；不能只复制活跃数据库的主文件而遗漏 WAL。恢复备份后先核对 GitHub 远端和工作区，因为备份时间之后可能已创建 PR，不能仅按本地旧记录重发。

默认备份先取得统一维护屏障：停止新任务领取，等待或安全挂起运行，并暂停 API 配置写入、同步落库、检查点、索引和产物清理等全部相关写者。此时分别取得数据库一致快照并固定不可变产物清单／摘要；完成核验后才标为可恢复备份，再按此前控制状态释放屏障，不解除既有人工／阻塞暂停。逐个 SQLite backup API 调用不等于跨文件同一时间点；将来若支持不停写备份，须另外证明跨库版本及产物一致。备份不导出明文凭据；恢复须重新核验宿主凭据引用和实际配置。

供应商整批导入横跨业务数据库与宿主凭据库，不能假定一个 SQL 事务覆盖二者。先全量校验并登记导入操作，暂存不可见的凭据修订，全部成功后在业务事务内激活整批配置；失败／重启时按操作记录清理或续接未激活引用，不暴露半批配置、不破坏旧凭据，不把密钥写入操作日志。相同人工操作标识只在请求内容一致时返回原结果；标识相同而内容不同返回冲突。

工作区、日志与归档回收遵循用户配置的保留策略；未完成／阻塞任务正在引用的候选与证据不能自动回收。删除已结束任务产物时同步标记引用可用性，后续不能依靠已丢失证据给新任务验收。磁盘预算和清理界面属于 P6，不能无限堆积直到无法持久化。

## 11. 编码前与发布前的退出条件

P0 产出依赖锁、最小工具／角色协议、任务与运行字段、版本化证据结构及数据库迁移初稿，验证 Windows 工作区、模型协议、唯一执行位与异常核对。后续各阶段按[报告实验清单](feasibility-report.md#9-必须通过的可行性实验)验证本契约；未实现的框架适配、协议兼容和语义判定均不能在文档复核阶段宣称已通过。

持久化失败即停止工具／发布、执行权校验、凭据隔离和最小安全停止必须随 P1 内核建立，并在首次真实发布前验收；P6 补齐启动器、备份和清理界面，不把这些前置保护延迟到产品化阶段。分诊和方案也必须先取得执行位，流程图中的“修复排队”只是同一主任务的后续阶段。
