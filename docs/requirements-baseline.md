# GitHub Issue 自动化 Agent Harness：需求基线

状态：功能、关键架构／流程及扫描自动补全 Q1—Q36 已逐项确认，[正式可行性分析与开发路线报告](feasibility-report.md)已完成。架构与流程见[完整设计基线](design-baseline.md)，补全规则见[扫描自动补全](scan-recovery-proposal.md)。当前交付为研究与设计文档，不表示产品已经实现。

2026-11-03 一致性复核补充的执行细节见[实施契约](implementation-contracts.md)，不将访谈历史或研究候选解释为另一套当前需求。

## 产品目标

为本地项目开发提供可管理多个 GitHub 仓库的 Agent Harness：处理已有和新增 Issue，导入时主动发现缺陷，取得可核查的修复证据后提交 PR，并持续处理反馈。先设计最终架构，再据此划分实施阶段。

## 最终产品范围

### 运行与仓库

- 本机后台服务配合浏览器管理界面，支持 Windows，允许 Docker／WSL 执行环境；浏览器关闭不终止后台巡查。
- 所有需要人工选择、确认、澄清、排障或恢复的节点，都须在 UI 提供证据、具体操作及处理结果，并有待人工事项入口；不能只有等待／阻塞状态。覆盖候选、Issue／PR 核对、方案／意见、任务有效性、扫描／复现／验证、配置／预算、异常恢复和暂停；合并提供 GitHub 跳转。操作与恢复边界统一见[实施契约 §3](implementation-contracts.md#人工处理入口与操作)。
- 管理多个仓库，由用户指定目标分支，使用独立修复工作区，保留用户日常开发目录中的分支和未提交修改。
- 支持用户有维护权限的公共／私有仓库，以及允许 Fork 的第三方公共仓库。分别采用直接修复分支和用户 Fork 提交 PR。
- 最终可适配多语言项目；首批路线验证采用 Python、JavaScript／TypeScript 的 Web 和命令行项目。

### 导入与全仓深度扫描

- 每次导入都必须完成全仓深度扫描。逐模块检查全部自有源码、测试、配置、CI 和依赖声明；排除构建产物、下载的第三方源码和二进制，并保留排除记录。
- 依赖检查覆盖声明、版本和使用方式。
- 扫描绑定明确代码版本，生成覆盖清单、逐模块审查记录、适用检查基线，以及发现缺陷时的候选证据。
- 扫描完成后该仓库才进入自动修复。可恢复的覆盖／证据缺口先在原预算和授权内自动补全，无法恢复或耗尽上限后维持“扫描未完成”并全局暂停，等待用户处理。
- 发现的问题先保存为本地缺陷候选，用户选择后由系统查询相似 Issue；确认关联已有 Issue 后复用该 Issue，未发现相似 Issue 时系统创建 GitHub Issue。Issue 创建或关联及外部 PR 检查完成前不得创建修复分支或修改代码；扫描发现本身不创建 PR。
- 扫描完成表示约定检查工作已完成，不声称证明仓库不存在缺陷。

### Issue 与任务队列

- 定时巡查新 Issue，并处理已有 Issue；仓库支持手动选择、标签准入、全部合格 Bug 三种模式，自有或有维护权限仓库默认全部合格 Bug，第三方公共仓库默认标签准入。标签未配置不自动放宽；命中准入且符合 Bug 条件才自动推进，模式不缩减事实同步范围。
- 对用户选中的本地缺陷候选，系统先在目标 GitHub 仓库查询相似 Issue；相同问题关联已有 Issue，确认无相似 Issue 后创建 Issue。创建失败或查重结果不确定时等待／阻塞，不创建分支或修改代码。
- 按后续用户调整，初始巡检频率为活跃仓库约每 2 小时、空闲仓库每天一次，按仓库可配置；模型分诊由 Worker 串行执行，巡检只保存对象及待分析信号。
- 用户可在仓库界面手动检查更新，立即同步 GitHub 并检查目标分支；发现代码版本变化后按既有就绪与补扫规则处理，不视为重新导入。具体读取、失败和去重契约见[实施契约](implementation-contracts.md#7-巡检分诊和变更同步)。
- 功能请求和大规模重构先生成方案，待用户确认后再实现。
- 分诊保存自动修复、等待补充信息、等待方案批准、已排除、外部修复处理中、执行阻塞六类结果及依据。其他 assignee／明确他人占用、排除标签、信息不足和敏感披露不自动修复；分诊缺信息正常等待，实际无法复现等执行障碍仍全局阻塞。敏感候选在创建 Issue 前先转脱敏人工事项。
- 本地占用不等于 GitHub 独占；默认不修改 assignee、不发表评论，认领评论须按仓库显式启用并由宿主受控发布器去重执行。优先级按人工设置、自动严重程度与老化、原入队时间排序；相关评论／标签／assignee／范围等变化重新分诊，用户持久排除须明确重新启用。权威细则见[准入与分诊](implementation-contracts.md#issue-准入与分诊)。
- 批准方案须包含可核查验收规范；功能证明新增能力，纯重构证明结构目标及约定行为保持。Bug 仍必须有有效的修改前失败／修改后通过证据，不能改名绕过。
- 全局同一时刻只执行一个修复任务；支持每仓库暂停、排除任务和人工调整优先级。
- 权限、环境、验证、预算等执行障碍触发阻塞，暂停整个队列，等待人工处理。
- 等待方案批准或 PR 评审属于正常等待，释放执行位；全局暂停期间保留只读 GitHub 巡查和状态同步。
- 任务时长、模型调用量和修复轮数上限可配置，默认值由技术方案推荐。
- 累计预算不会因拆分、重试、重新运行或 PR 返修而重置；正常等待不占用有效执行时长。全局暂停仍允许用户明确发起有界排障，但不自行恢复执行。
- 程序按真实覆盖、实验和验证产物检测无进展与状态振荡，重复日志、代码变动或重启本身不算进展；触发后暂停并提供 UI 排障／有界重试入口，记录不因续期清零。复杂任务持续有进展但预计额度不足时，可在耗尽前展示证据和剩余计划、由用户批准有限追加；账本不清零、不自动续期或降低验收。耗尽前的正常续期等待与耗尽后的全局阻塞分别处理，细则见[无进展检测](implementation-contracts.md#无进展检测)与[预算续期](implementation-contracts.md#进度驱动的预算续期)。

### 验证与 PR 交付

- Bug 修复提交 PR 前须取得“修改前存在问题、修改后问题消失”的证据，通过相关回归检查和独立审查；其他已批准任务按方案内的能力／结构目标与行为保持规范验收。
- Bug 无测试时先补充能够在修改前失败、修改后通过的回归测试；功能和纯重构也须补齐各自适用的验收与回归检查。
- 原仓库已有失败检查仅在证明与本次修改无关且未恶化时不阻塞；新增、相关或无法归因的失败均阻塞 PR。
- Bug 无法复现，或任务目标无法按批准规范验证、环境不具备、依赖不可用、预算耗尽、证据不足时进入阻塞，不以 Agent 自述替代验收。
- 验证和 PR 绑定到实际处理的代码版本。
- 创建修复分支前及发布前检查同一 Issue 是否已有外部开放 PR；确认处理同一问题则关联并等待，不重复建分支或 PR；确认无关则继续，仅关系无法判定才在 UI 请求人工决定。相关 PR 已合入目标分支时直接重新取得扫描／复现证据，确认解决则记为外部修复解决，仍存在则按当前范围继续。
- PR 创建后持续跟进 CI 与维护者评审；必要修订重新排队并再次验证、审查，直至 PR 合并或关闭。
- 合并由用户或仓库既有规则执行。关闭和合并分别记录，关闭不等于 Issue 已解决。
- Issue 与受管 PR 一一对应：一个 PR 只修复一个 Issue，同一 Issue 生命周期最多一个受管 PR，返修更新原 PR；关闭／合并后保留绑定，不重建或另发替代 PR。多个独立目标先确认范围再分别建 Issue。外部竞争 PR 作为观测保存，不冒称系统能强制他人的 GitHub 关系，细则见[一一对应契约](implementation-contracts.md#issue-与-pr-一一对应)。
- 验收提供约定范围的可核查证据，不提供代码绝对正确的保证。

### 模型 API 与供应商

- 仅接入模型 API，各 Agent 可分别选择供应商和模型。
- 按用户指定私有参考项目 `Gwex323/repo` 的供应商导入方式设计：手工新增／编辑，以及 JSON 文件／文本导入；接受单供应商、数组和含 `providers` 数组的对象。
- 字段为 `name`、`base_url`、`api`、`api_key`、`models`，模型含 `model` 和 `reasoning_effort`；接口类型包含 `chat_completions`、`responses`，支持自定义地址。
- 支持模型列表拉取、手填模型和连接测试；基础连接测试不替代真实工具调用兼容验证。
- 批量导入仅新增、整批校验保存；保存与导入不自动发起模型调用。
- 每个角色可分别选择模型与默认配置，运行中的任务使用启动时的配置快照；密钥加密保存且不回显。
- 参考依据固定为提交 `039494d933fae95e74895ffb67af208d1e3b9cd9` 的文档与前端源码。现有项目的角色数量、架构和历史迁移规则不构成本项目已确认设计。

### 记忆与经验复用

- 仓库原始代码、日志和完整历史默认留在各自项目内。
- 跨仓库共享提炼、去敏的问题特征、修复方法和验证经验；当前仓库必须重新验证。
- 修复通过验证及独立审查后自动提炼经验；失败尝试单独标记，不作为已验证方案。
- 已验证修复与 PR 被接受分别记录；后续证据推翻修复结论时停止复用关联成功记忆，返修通过后更新。
- 用户可查看、纠错、禁用和删除经验。
- 记忆系统需要通过后续验证实验评估是否提升解决速度和效果，报告不把未执行的实验写成实测结论。

## 技术推荐的边界

用户明确要求在访谈中确认项目框架、流程等关键问题，不能只确认功能后将全部技术决定留给报告。候选方案先经必要的只读源码／文档调查，再按依赖关系提出推荐、讨论取舍并记录用户决定。

已经确认：一个代码仓库内的模块化单体，API 和独立 Worker 分进程；Python + FastAPI 后端与 React + TypeScript + Vite 前端；程序化工作流掌握状态、预算、暂停、验收和发布控制权，Agent 在任务内分析与修改。

已经确认：LangGraph 承载明确阶段、检查点与暂停恢复，Deep Agents 承载任务内模型／工具循环；处理与独立审查两类核心角色加按需子任务；扫描、修复和 PR 返修统一使用一个全局重任务执行位，API 与只读同步独立运行。

已经确认：默认 SQLite WAL 并保留 PostgreSQL 适配；业务状态与运行检查点分层，数据库为对外权威，恢复时对账且证据绑定代码版本；Docker Linux 为默认代码执行环境，Windows 使用 WSL2 后端，原生执行须显式启用。

已经确认：全仓扫描使用版本化模块清单与覆盖账本，支持同版本断点续扫，代码变化后补扫或必要时全仓重扫；修复使用受控 Runner、独立审查和当前版本证据包；数据库持久队列配合执行租约、心跳和异常后的对账／人工恢复。

已经确认：Agent 通过 Harness 结构化交接，子任务默认串行、工作区单写，独立审查只读；按当前运行授权工具，供应商与 GitHub 写凭证留在宿主受控模块，验收记录由程序收集和核验。

已经确认：业务记忆为事实源，结构过滤、FTS5 与 sqlite-vec 组合混合检索，本地 CPU embedding，索引可重建，语义不可用时明确降级；GitHub 用户 token 和本地条件轮询为默认，按仓库和贡献路径适配 token 权限，处理分页、去重、限额与周期复核。

已经确认：提交前通过预设复现、回归、基线比较与独立审查后创建 PR，再跟进 PR 专属检查；若目标问题缺乏其他有效提交前验证证据，保持阻塞。模型按实际角色检查必需能力、保持配置快照并有限重试，不兼容或持续失败全局暂停，默认不跨供应商自动切换。
