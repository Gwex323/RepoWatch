# 统一故障记录（中央调度阶段 1/6）

对应 Issue：#78，父 Issue：#77。实施分支 `feature/system-fault-records-78`，基础提交 `03d43fe0d35066d5a154859429c1e152b71a825b`，实际默认分支为 `codex/initial-upload`。远程操作身份为 `Gwex323`。

## 用户如何使用

登录后选择左侧“系统故障”。按仓库、流程、处理状态或任务 ID 筛选，打开一组故障，可查看每次出现的字段诊断、执行确定性、本次实际模型绑定、预算和处理时间线。点击“查看来源任务”回到原环境和相应处理环节；分析和修复页面也有返回同一台账的链接。

- **次数**按稳定来源故障事件计数；同一事件重放不增加次数。检查失败后同一检查的终止包装不重复计数。不同请求、尝试和任务的故障分别保留。
- **剩余次数**是尚未恢复或关闭的出现数，一次成功不会遮盖其他失败。
- **关闭此出现记录**必须填写原因，显示“已关闭”；这不是修复通过，不会修改原任务、用户确认、验收结果或预算。
- **补录一批历史故障**是显式、可重复调用的本地读取操作，每个来源最多扫描 200 条，游标持久化。补录事件标记“历史补录”。后续点击继续下一批，不自动运行旧任务。
- **停用故障采集**只关闭记录功能。已入账内容仍可查，原流程按原策略运行。重新启用从保存的来源游标补采停用期间仍存在的事实。
- **采集健康详情**显示各来源游标、最近成功时间、累计采集异常及未入账数量。数据库整体不可用时，认证和页面也可能不可访问；不能将“页面未显示错误”当作没有故障。

第一阶段保持原来的五个 Agent 角色，不增加中央模型，不增加模型请求或重试机会，不修改代码、发布 Issue/PR、合并或部署。原来已启用的分析、修复和验收恢复仍按原有策略运行。后续五阶段分别由 #79–#83 跟踪。

## 来源、字段与分类

| 内容 | 记录方式 |
| --- | --- |
| 来源身份 | 流程、来源表/稳定事件 ID、根任务、实际任务、尝试、账号、仓库、环境 |
| 运行依据 | 目标源码修订；加载的 Python 模块内容摘要作为工作台版本；本次模型、模型配置版本及供应商版本 |
| 字段诊断 | 调用/匹配/其他/允许数量、检查原因、字段路径与约束、异常类别；不复制输入值或异常正文 |
| 时间 | 事件发生时间、首次/最近出现；请求等待与请求耗时分开，整次尝试耗时明确标注口径 |
| 预算 | 来源实际已有的请求、续办、尝试与纠正计数、已知上限及停止原因；不修改额度 |
| 执行确定性 | `not_executed` 未执行、`executed` 有实际执行证据、`unknown` 结果未知 |
| 追踪 | 仅保存已有 Langfuse trace ID；未启用或无可用关联时为空，本地台账不依赖远程服务 |

分类为模型超时、协议/调用约束、外部服务、运行环境、目标测试、审查拒绝和未知。分类是定位线索，不等于已确认 RepoWatch 或目标仓库存在代码缺陷。仅观察到超时，无法推断供应商负载、连接超时或读取超时，`timeout_kind` 显示未知。

实际模型绑定来自本次请求的 `model_configuration`，不能用页面当前模型选择反推。每次分析/修复开始保存 `fault_attempt`，验收模型事件另带真实尝试编号，跨尝试不借用旧配置。诊断通过 SDK 的角色开始事件记录实际角色；角色尚未开始时保持未知。执行领取时保存原源码依据，诊断使用自身保存的修订。预算优先使用来源事件的当时快照，补采不会用后来的计数填充旧记录。缺少可靠绑定的旧记录显示未知，并保持任务隔离，不据此合并恢复结论。

典型前置异常如下，第一阶段只记录，不放宽“一条调用”原约束：

```json
{
  "required": "scope",
  "calls": 2,
  "matching": 2,
  "other": 0,
  "allowed": 1,
  "accepted": false,
  "reason": "too_many_calls",
  "recovery": "request_mismatch"
}
```

本批调用未执行；它不是 JSON 解析失败。远程发布请求发出后断线则是结果未知，不能显示为未执行。

## 持久化与重启

新增六张表：`system_fault_configuration`、`system_fault_outbox`、`system_fault_occurrences`、`system_faults`、`system_fault_history`、`system_fault_ingestion`。旧任务表仅增加可空诊断字段，不改变既有状态、供应商密钥、用户决定或累计计数。

`Store.connection` 在来源写事务提交前，以保存点收集来源并登记脱敏信箱；来源、信箱和游标尽可能同事务提交。采集异常回滚采集保存点，保留原来源事务。独立记录 worker 每两秒按游标补采，单来源每轮最多 100 条，最多消费 200 条信箱记录。唯一来源键和事务消费保证重复投递不重复入账。

分析和修复读取持久化事件；执行与诊断读取持久化状态版本/更新时间；验收异常读取失败表，验收行为失败读取单独来源事件。额外的角色开始、模型绑定和验证事件只补充事实。服务 worker 自身异常也会尝试记录；记录器自身异常只影响健康诊断，不递归创建服务故障。

首次安装将当前来源高水位保存为基线，旧失败不会自动入账或执行。重启保留原游标。已有台账升级采用加法初始化、唯一约束与可空字段。未采集的旧事件缺少版本时显示未知，而不是贴上新版本。来源记录本身被删除后无法补采；数据库整体不可写也不能承诺零丢失。进程完全退出期间的离线监测属于阶段五。

## 聚合与状态

聚合键包含账号、仓库、环境、流程、角色/阶段、错误码、结构化约束、实际模型绑定、源码和工作台版本。任务 UUID、时间和完整错误正文不参与已知依据下的相似聚合。依据未知时额外按任务隔离。

逐次状态：待诊断、诊断中、恢复中、验证中、已恢复、受阻、已关闭。第一阶段观察已有恢复事件，不创建新的恢复动作。已有分析完成需通过原报告及证据校验，已有修复需通过原测试和独立审查，已有验收需原范围完成，发布需有真实回执；之后才记录对应出现的恢复。跨分析续办还检查同一账号/环境/版本与实际模型绑定。人工关闭永久保留其原因和历史，不被后续来源事件改成已恢复。

## 数据保护与访问

`fault_contract.py` 是唯一持久化信箱入口，按字段及类型白名单构造快照。认证头、密钥、凭据 URL、原始模型正文、推理、源码、命令日志和异常消息不进入台账。标识符限制字符与长度，常见令牌/URL/凭据赋值被过滤。单条诊断最多 32 KiB，列表项数、嵌套深度及字符串受限；截断有标记。人工关闭原因先脱敏再保存，最多 512 字符。故障记录本身不发送追踪或模型请求。

所有 API 需要原所有者登录，修改须通过 CSRF。仓库来源须仍匹配原环境账号和当前激活的已验证 GitHub 身份；切换账号后不能用旧 ID 读取详情、历史或关闭。服务级记录没有目标仓库，归本地所有者查看。认证规则不是新的多人权限系统。

查询默认每页 50 条，上限 200；出现详情和历史独立分页。关闭使用出现记录版本，版本冲突返回 409，无手工“标记已修复”接口。

| API | 用途 |
| --- | --- |
| `GET /api/system/faults` | 分页与仓库/环境/任务/流程/聚合状态过滤 |
| `GET /api/system/faults/health` | 采集健康 |
| `GET /api/system/faults/{id}` | 分页出现记录与聚合状态 |
| `GET /api/system/faults/{id}/history` | 分页状态、证据与诊断时间线 |
| `POST /api/system/faults/{id}/occurrences/{occurrence}/dismiss` | `version` 与 `reason` 关闭出现 |
| `POST /api/system/faults/import-history` | `limit` 显式、按来源批量历史补录 |
| `POST /api/system/faults/settings` | `version` 与 `enabled` 控制采集开关 |

## 保留与回退

本阶段默认保留全部台账、来源信箱、游标和历史，不自动删除，也没有清零计数接口。定期备份原 SQLite 数据并监控文件大小；保留策略改变需单独设计并验证，不手工删除来源或游标来“修复”计数。回退可以停用采集并恢复旧应用，新增表可保留，不能用旧备份覆盖期间新增业务数据。
