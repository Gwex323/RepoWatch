# 自身代码维护策略（#81）

更新：2026-10-29。阶段四已实现并通过定向验证和独立 review，交付 PR 待创建；未合并、未部署、未在正式工作台启用。

## 授权与范围

- “系统故障 → 自身代码维护”具有独立开关，默认关闭。开启协调或规则恢复不会隐式授权代码维护。
- 固定维护仓库为 `Gwex323/RepoWatch`，固定远程身份为 `Gwex323`。开启时绑定账号版本和 GitHub 仓库数字 ID；没有 push 权限时拒绝开启，不 fork、不切换其他账号。
- 必须已配置并启用 `repair_agent`、`independent_reviewer`。诊断复用独立审查角色，不能自行创建新权限。
- 本阶段自动补丁仅支持 `repowatch/*.py`（含子目录）及新增 Python 回归测试。前端、依赖清单、CI、部署脚本和既有测试修改不在自动维护范围；没有合适验证器时受阻，不以 Python 测试证明其他语言正确。
- 默认到中文 PR 为止。合并保持 `owner_only`，不自动合并、部署、重启服务或调用被分析仓库的发布器。

## 维护链路

1. 只领取启用后新发生、当前可见且未被维护任务领取的最新故障；显式历史补录不会自动激活维护。
2. 单纯模型超时、外部不可达、目标测试失败和审查拒绝不触发自身代码修改。其余问题先取固定维护仓库最新实际默认分支及提交，读取有界、已安全筛查的实现片段。
3. 分类输出必须引用实际故障事实、精确路径、函数或类、绝对行号及源码原文，区分内部缺陷、目标缺陷、外部服务和未知。内部分类还需给出稳定约束、观察、预期及根因；缺少证据停止。
4. 先读取开放和已关闭的 Issue/PR。自动标记或人工描述必须同时支持实现位置、根因约束与验收目标；只有标题相似不复用。实现位置可能相关但根因不足时受阻，不盲目创建重复 Issue。
5. 有对应工作则保存绑定、补充故障证据并关联现有 PR。无对应工作先创建中文 Issue；持久化写入意图先于 POST，响应丢失先查回执，未找到不会盲目重发。
6. Issue 已确认后，重新验证身份与仓库权限，再建立独占维护目录、bare 仓库和 `feature/maintenance-...` worktree。fetch 的实际默认分支提交必须等于证据基础。已有目录直接拒绝，不 reset、清理或覆盖；不使用运行 checkout、用户分支或目标项目目录。
7. 修复复用原 SDK 工具、隔离验证和 `repair_agent → independent_reviewer` 交接。每次准备补丁前再次核对维护权限；模型无 GitHub 写入或宿主 shell 工具。
8. 原始套件需通过；新增回归在原实现上失败，在候选实现上通过，候选套件通过。测试在现有 Docker 边界内运行，不在宿主执行模型命令。安装阶段允许联网获取固定项目依赖，测试阶段不联网；GitHub token 不进入验证容器。
9. 审查拒绝反馈修复，重新验证、重新独立审查，沿用原有纠正上限。批准绑定当前修订和补丁摘要；发布前核对原始树、完整候选树、验证历史和独立批准。后改补丁不能沿用旧批准。
10. 保存不可变批准工件后，通过可信 GitHub REST 适配器创建同名远程 feature 分支和中文 PR。远程 HEAD 必须等于已审查补丁提交，重试也重新检查；新 PR 响应核对 head、base、来源仓库和正文。PR 五部分齐全并引用维护 Issue、故障、任务、基础提交及补丁摘要。

## 状态与证据

专用 `maintenance_tasks`、`maintenance_events`、`maintenance_remote_operations` 保存故障、基础、分支、分类、补丁、验证、审查和远程回执。不插入虚假 `analysis_findings` 或用户复现确认。

工作台显示未确认内部缺陷、维护中、受阻、已关联 PR、待所有者处理 PR、已合并待部署验证；支持查看补丁/review、Issue/PR 链接、累计用量及核对远程回执。

- PR 创建或复用后，原故障仍为未恢复；GitHub 合并核对只转为 `waiting_deployment`。
- 未经部署及原步骤真实验证，不将故障改为 `resolved`。部署、服务恢复和完整验收分别属于 #82、#83。
- 有效批准工件的发布失败可显式重试，最多两次，先核对既有意图和当前 HEAD；不重新调用修复模型或增加期限。
- Issue 响应丢失可显式核对并保存 Issue 绑定，任务仍受阻。未完成补丁或执行中断的工作区保留，不自动覆盖或无界重跑；本阶段不提供任意中断点的全量模型恢复。

## 预算与停止

维护任务最多 32 次模型请求、1800 秒，分类也计入；与原分析/验收及根任务共享计数和租约，不清零。根任务仍受既有 128 次请求、320 万已报告令牌、5400 秒及纠正/续办上限约束，实际剩余额度更少时从严使用。

原分析因协议问题停止自动续办不等于预算耗尽；仅允许 `non_recoverable`、`review_not_started`、`checkpoint_invalid` 在维护分类中继续使用原剩余额度，仍不能绕过取消、deadline、32 次请求或根预算。

关闭维护、更改账号/模型/来源、来源取消或真实恢复、租约或期限到期会停止执行。远程不确定结果保留为不确定，不当作成功或反复发布。SDK 未报告的令牌/费用保持未知，不估算为零。

## API

所有接口沿用所有者登录、CSRF 与严格请求 schema；写操作带版本。

- `GET /api/system/maintenance`：配置、固定范围、模型 readiness。
- `POST /api/system/maintenance/settings`：`version`、`enabled`。
- `GET /api/system/maintenance/tasks?fault_id=...`：当前作用域最近 50 个维护任务及证据。
- `POST /api/system/maintenance/tasks/{id}/reconcile`：核对未知 Issue 回执或 PR 合并事实。
- `POST /api/system/maintenance/tasks/{id}/retry-publication`：有限重试当前已批准补丁的发布。

启用可能消耗已配置供应商额度并产生固定维护仓库的 Issue/PR。当前交付只使用替代模型、远程模拟及隔离目录验证，未授权实际启用或真实维护写入。
