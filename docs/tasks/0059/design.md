# 技术设计

## 持久化与可信边界

新增 TaskScopes 服务管理 scope、item、evidence 与发布决定。Scope 按仓库和 Issue ID 分组；系统发现按分析分组。
原始问题快照、版本、审查和范围变动留有事件记录。范围仅追加，不提供删除或降低验证等级接口。
分析角色通过受控工具登记范围；独立审查的结构化结果必须覆盖所有已登记项且版本一致，才能冻结。
缺失范围/审查的旧报告仍可读取、修复及部分发布，不能自动关闭 Issue。

## 证据与完成

修复审查返回逐项覆盖和回归文件；后端从实际补丁、真实验证结果、当前范围版本生成证据。
额外环境/集成/客户端观察由已认证 owner 提交本人核验记录，明确标记来源，不声称为自动执行。
源码无缺陷结论需要独立源码审查及当前原版本的本人观察佐证。未验证、未映射、排除项目保留待办。
必要验证等级在范围冻结前确定；模型不能通过后来的审查降低等级。

## 发布与并发

每次发布持久化范围版本、补丁摘要、完成判定及引用模式。模型文本中的关闭指令不构成授权。
默认 Refs；Closes 要求所有必需项均有效，且所有修复证据对应当前组合补丁，不能拼接互不包含的 PR。
源 Issue 新鲜度、源码版本与范围版本变化使旧 Closes 决定失效；存在不确定意图时停止而非改写。
发布前后保留原先的账号、版本、审查、分支与不确定写入校验。

## 数据流

同步/发现 → 建立范围 → 分析角色追加 → 独立范围审查 → finding 复现确认 → 隔离修复验证
→ 独立补丁及逐项覆盖审查 → 后端生成证据 → 整体判定 → Refs/Closes → 持久化剩余项。

## 兼容

增加表，不改写旧任务/远程结果。旧任务按需建立未核验范围；旧发布意图保留其摘要与不确定状态。
范围识别本身仍依赖语义分析；独立审查降低漏项风险，后端保证已登记项不会静默消失。
