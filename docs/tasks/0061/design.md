# 设计

## 根因与职责

原格式纠正属于模型请求循环；检查点恢复属于 owner retry 接口。工作线程捕获失败后只保存 failed，两者没有跨失败状态的调度契约。此前增加提示或单请求重试不能补齐该断点。

此处修复分析报告恢复，对应 Issue #61 / PR #62；PR #73 的工具参数绑定及交接纠正仍独立维护。本分支更新至当前主干实现，不复制未合并的 PR #73 或工作台集成树。

## 数据与状态

新增私有表 analysis_report_recovery，主键为 analysis_id。记录首次开始和绝对 deadline、已预占请求数、已预占续办次数、retry_after、全部已知纠正计数、最后安全报告诊断、当前角色、检查点绑定摘要及固定停止原因。表中不保存失败报告、原始参数、凭据或异常正文。

queued → running → completed；可恢复失败在同一事务内先记 failure，再变 queued/waiting_model，并将恢复状态置 waiting。每次最多预占一个续办名额，退避时间写数据库。tick 查询只选择退避已到期的队列项，不使用长 sleep。

运行租约到期后，只有已加入此表、且状态 active 的 interrupted 分析进入相同恢复判定；旧失败记录不扫描。服务关闭产生的可恢复中断也通过同一入口。没有最终审查检查点的中断明确停止。

## 预算和并发

每次 delegate.get_response 前，在版本仍归本次运行所有的事务内预占一个请求。计数包含超时及截断的请求，崩溃后不返还。32 次为整条分析而非每轮上限。纠正名额在决定纠正时持久记录，并在下一请求前同步；合并取最大值，禁止清零。原每次运行 600 秒、单请求 120 秒及既有局部纠正上限保留；新增整条链 1800 秒硬期限，退避和服务中断计入其中。

自动及 owner retry 共用最多三次续办，退避依次为 10、30、60 秒。owner retry 不补充额度；耗尽后需产生新的真实执行依据来建立新分析。迁移之前失败任务首次显式 retry 才建立额度记录，不能声称知道旧版本未记录的请求数。

仓库分析的单次生成硬上限为 100000 tokens，由报告预算与截断扩容共用；初始预算仍按任务规模计算。局部输出纠正次数、每次请求时限及整条链的请求数和期限继续独立生效。

现有“继续分析与范围审查”是 owner 主动改变任务范围版本的独立请求，不是 retry。该入口在同一事务中归档上一条链的完整计数及固定诊断，再建立新范围审查的额度记录；历史表和专用事件保留来源。模型登记范围、自动恢复、服务重启及普通 retry 均不能走此入口。避免已完成分析的 30 分钟期限阻止后续合法范围审查。

调度、claim、预算计数和最终报告提交均检查任务版本。恢复检查点再次校验绑定、内容摘要、读取区间和真实交接；已经安排的自动续办如果失效，停止并记录 basis_changed，而不是悄悄重跑完整流程。恢复后仍使用原完整 Review、精确证据、范围及持久化门禁。

## 诊断与前端

JSONDecodeError 的消息只映射为固定原因；输入字符不进入日志。字段位置从可信 schema 属性名和有界数组序号生成，未知名称以 [unknown] 代替；错误值和任意异常消息均不输出。

当前进程内纠正收到具体安全诊断，下一次检查点续办也收到最后一次诊断。前端通过现有轮询展示 waiting、下一次时间、累计请求和续办额度、停止原因，额度耗尽禁用 retry。原 failure 事件保留，恢复时不显示仍需人工点击的失败提示。
