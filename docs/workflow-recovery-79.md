# 第二阶段：规则恢复（Issue #79）

日期：2026-10-28。分支：`feature/workflow-recovery-79`。
基础提交：`ba043b1`，创建分支时的最新实际默认分支。

## 范围与状态

本阶段实现确定的规则恢复，不增加中央模型角色，不修改 RepoWatch 自身源码工作流，
不授权合并或部署。已实现并通过验证及独立 review，PR #90 于 2026-10-28 合并为
`367baff`，部署尚未核验；合并、部署和真实供应商联调分别记录。
没有修改正式数据库、生产模型配置或被分析仓库，没有调用付费模型。

“系统故障”页面新增默认关闭的恢复开关。只有开关启用后新发生、依据仍有效且满足
已有修复资格的白名单故障才会自动排队。开关不重新启动取消、旧历史或缺权限任务。
关闭或修改开关版本会阻止尚未开始及运行中的新增自动恢复；旧有分析检查点、
审查反馈和验收重试仍遵守各自原有策略。故障采集开关与恢复开关相互独立。

## 策略与执行权

- 策略标识：`workflow-recovery-v1`。动作身份由根分析、业务流程、任务、尝试和依据
  计算，不包含 worker 身份；同一动作重放不能重新领取。
- 分析、修复和验收沿用原业务领取事务，同时领取同一根分析的唯一执行权。
  数据库 `BEGIN IMMEDIATE` 与业务版本共同约束并发，不另起竞争的模型执行链。
- 动作、根任务、消费事件及自动排队决定分别持久化。动作回执保留来源状态和停止原因；
  过期租约记录 `execution=unknown`，不能当作成功。
- 过期 worker 的模型请求、检查点、产物和发布结果写回受 action、owner、attempt
  或分析版本约束。旧执行者不能覆盖新尝试产物。
- 自动修复白名单覆盖模型超时、供应商不可达、中断、输出截断、工具参数及交接异常。
  资格判断仍由现有 `Repairs.retry` 完成；白名单本身不增加尝试额度或发布权限。
- 排队和执行期间核对实际角色模型、账号及令牌版本、源码版本和不可变范围依据。
  依据变化明确停止；不会悄悄切换模型、恢复失效证据或变更原验收要求。

## 累计预算

| 根任务上限 | 数值 |
| --- | ---: |
| 实际模型请求 | 128 |
| 已报告令牌 | 3,200,000 |
| 执行耗时 | 5,400 秒 |
| 纠正 | 32 |
| 同一任务续办累计 | 12 |
| 新策略自动排队 | 3 |

以上为额外保护上限，不是新授权。分析原有 32 次请求、1800 秒及三次续办，修复的
逐次探索、输出和返工上限，验收原有 12 次请求等更小限制继续生效。
单请求等待继续采用原流程的有界配置；根任务累计耗时同时进入业务 guard，
外层轮询在根任务剩余时间耗尽时取消请求或停止验证与发布。
新增自动排队退避为 10、30、60 秒，不在数据库事务中睡眠。

交接、重启和验收派生修复复用根分析，不清零计数。安装前已有的持久化请求、
纠正及续办计数首次接管时导入。令牌只累计供应商/SDK 明确报告的消费，包括截断
及停止后的迟到回执；没有报告的历史令牌和耗时不虚构补齐。费用未提供时为 `null`，
不以零表示免费，也不按当前公开价格猜测历史账单。恢复账本不是供应商账单。

`GET /api/analyses/{id}` 的 `recovery_ledger` 返回根预算和最近 100 条动作回执。
根累计值不因回执列表分页上限而减少。开关及固定保护策略可通过认证的
`GET /api/system/recovery` 查询；写入 `POST /api/system/recovery/settings` 需要
登录、CSRF 和配置版本，陈旧版本返回 409。

## 范围登记

一次响应最多两条 `register_task_scope`，每条 1 至 3 项。工具参数先按原模型 schema
整批校验，再对角色、路径、不可变键、总条目数及范围版本预演。预演在 savepoint
中回滚，不留下条目或事件。实际 SDK 执行时在同一事务中按原顺序登记，保存每条
调用的真实范围回执；重放读取原回执，不重复新增。

非法参数沿用共享上限的定向纠正，保留已合法字段及列表结构。混合工具、超量和
矛盾要求不做部分执行，不以删除验收项换取成功；无法安全纠正时明确受阻。
提交时范围已变化则整批回滚，不覆盖其他任务新增内容。

## 原步骤验证与远程结果

审查拒绝沿用原“修复、隔离测试、独立再审”反馈链；验收真实失败沿用原证据和后续
修复意图，不自动确认新的系统发现。动作完成不直接把故障改为已恢复；仍由原来源
适配器根据报告、验证或发布的真实通过事实更新故障状态。

远程发布复用已有持久化 mutation intent。Issue、PR、提交或分支写入结果未知时先
查询对应标记、内容和远程身份并补记回执；未能确认不存在的写入保持 uncertain，
不会因新规则直接重发。保留原账号权限、源码、补丁、测试与审查门禁。

## 回退与验收

回退采用关闭恢复开关，不删除表、不清空预算、不恢复正式数据库备份。
开关关闭不撤销已发生的远程事实，正在进行的请求可能产生迟到消费，仍需入账。
已合并与已部署必须由对应 GitHub 和运行版本事实证明。

验收记录见 [第二阶段验证](workflow-recovery-79-validation.md)。第三阶段在独立分支实施与验证，
第四至六阶段仍未实施。
