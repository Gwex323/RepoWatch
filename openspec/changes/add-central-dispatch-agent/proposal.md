# Proposal

## Why

RepoWatch 已具备分散的分析、修复和验收恢复逻辑，但模型超时、任务范围工具调用数量异常等故障仍会停止流程，依赖用户发现、报告并推动处理。需要统一记录故障，再逐步建立受预算、权限和独立验证约束的中央调度，让系统主动接管自身运行故障与自身代码缺陷。

## What Changes

- 按六阶段交付：统一故障记录 → 自动恢复机制 → 中央调度 Agent → 自身代码修复闭环 → 发布与服务恢复 → 完整验收与逐步启用；第一阶段单独验收、上线。
- 建立本地持久化故障台账，关联来源事件、仓库、任务、阶段、运行版本、实际模型配置、字段级诊断、预算、执行结果与可选 Langfuse 追踪；同一事件幂等接收，相似故障聚合但保留每次出现记录。
- 在现有工作流上增加统一恢复策略和执行契约，支持定向纠正、退避重试、审查反馈续办与检查点恢复，避免与已有恢复器重复执行或重置额度。
- 新增独立配置的 `system_coordinator`（系统协调）角色，使用受校验的工具选择恢复动作；规则调度、授权、租约、预算和执行由服务端控制，复用现有五个业务角色。
- 为确定的 RepoWatch 自身缺陷提供维护任务：查找相似 Issue/PR，登记中文 Issue，在最新实际默认分支上创建 `feature/` 分支，修复和验证，经独立 review 后提交中文 PR；遵守 GitHub 合并与部署授权。
- 建立固定部署清单、前后端版本核验、启动配置恢复、独立进程监护和回滚机制，防止再次从旧目录启动。
- 工作台增加系统故障入口与处理时间线；例行恢复保持安静，仅在完成、处理失败或需要新增授权时通知。
- 兼容现有数据库、五角色模型配置和已有任务。新增自动动作按阶段启用；历史失败记录不因安装而自动重跑。

## Capabilities

### New Capabilities

- `system-fault-records`：统一事件、故障聚合、脱敏、来源关联、处理状态、查询和通知依据。
- `workflow-recovery`：跨流程恢复策略、执行幂等、共享预算、检查点有效性与恢复后验证。
- `system-coordination`：系统协调角色、诊断计划、受限动作调度、兼容配置和可解释处理过程。
- `system-maintenance`：RepoWatch 自身缺陷的证据、Issue/PR 去重、开发分支、独立审查和修复结果关联。
- `workbench-release`：经授权的合并发布、部署清单、精确启动、健康验证、独立监护和回滚。

### Modified Capabilities

无。当前 OpenSpec 规格库为空；已有实现与约束将在设计中列为接入基础，不视为已经具备上述完整能力。

## Impact

- 后端：SQLite `Store` 初始化与事务，`repository_analysis.py`、`report_scheduler.py`、`repairs.py`、`acceptance.py`、`execution.py`、`diagnosis.py`、`github_issues.py`、`github_contributions.py` 的故障与恢复边界，`app.py` 生命周期和认证 API。
- 模型与追踪：`roles.py`、`analysis_model.py`、`model_providers.py`、`observability.py`；保留供应商导入、五角色配置及元数据追踪，不保存密钥或模型原始推理。
- 界面与部署：现有故障提示、系统页面、导航和模型配置；`scripts/start.ps1` 及新增受管启动/发布入口。运行数据继续使用明确绑定的原数据库。
- 验证：扩展现有前置调用、分析恢复、修复反馈、验收恢复和供应商路由测试；新增故障台账、幂等、权限、部署版本及服务重启验收。
- 范围边界：本变更仅规划；不运行真实模型、不重启服务、不修改生产数据、不发布 GitHub 内容。实施时先落实中文 Issue 与合规分支；不自动确认目标仓库的新问题、放宽验收标准、覆盖取消决定或绕过 PR。
