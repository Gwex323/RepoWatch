# Proposal

## Why

RepoWatch 已能按角色选择模型，但还缺少一种可审计的执行策略，明确保证低成本 flash 模型持续负责观察、分析、审查与发布协调，只有服务端确认需要修改代码时才交给 v4pro，并在修复结束后回到 flash。目标仓库 `Gwex323/gateway-model-assistant` 已登记，但当前角色统一使用 `glm-5.3`，最近一次分析失败，尚不能证明这条升级链能够完整跑通。

## What Changes

- 新增版本化的“flash 监控 + v4pro 修复”模型升级编排；模型仍从既有供应商目录和角色选择解析，不复制凭据，不写死供应商地址。
- 将升级触发绑定到持久化故障事实、现有授权和明确的代码修改动作，而不是按错误文本或模型自述切换；非代码故障不得自动使用 v4pro。
- 在任务与阶段快照中记录实际供应商、模型、版本和切换原因，模型交接不得绕过工具权限、预算、测试、独立审查、发布或远程写入门禁。
- v4pro 修复结束、失败或受阻后回到 flash 的协调与审查路径；保留累计用量和故障历史，禁止以切换模型重置预算或无限重试。
- 增加配置、只读状态和审计展示，使所有者能够选择并核对监控模型、修复模型及当前阶段实际使用的模型。
- 使用 `Gwex323/gateway-model-assistant` 完成一次真实分析、修复、验证、独立审查和中文 PR 发布验收；没有真实有效问题或审查未通过时不得伪造目标仓库 Issue/PR。
- 验收中若发现 RepoWatch 自身代码缺陷，先创建中文 Issue，再从最新实际默认分支建立 `feature/` 分支，review 通过后才提交中文 PR。

## Capabilities

### New Capabilities

- `model-escalation-routing`: 定义监控模型与代码修复模型之间的受控升级、阶段模型快照、触发条件、恢复回路、审计和预算连续性。

### Modified Capabilities

无。当前 OpenSpec 正式规格库为空；本变更只新增模型升级编排能力，不修改尚未归档的提案规格。

## Impact

- 后端：`roles.py`、`model_providers.py`、`analysis_model.py`、`coordination.py`、`repairs.py`、`app.py` 的角色解析、阶段交接、恢复预算、事件和 API。
- 界面：模型与供应商设置、系统协调状态、修复阶段实际模型和切换历史。
- 验证：新增离线路由、触发、快照、回路、预算与发布门禁测试，并执行 `gateway-model-assistant` 的真实端到端验收。
- 数据与权限：保持现有数据库加法升级、角色凭据加密和配置版本语义；升级策略默认关闭，不自动修改历史任务，不自动合并或部署。
- 仓库流程：关联 Issue #108；规划阶段不修改业务代码、不运行真实模型、不向目标仓库写入 Issue、分支、提交或 PR。
