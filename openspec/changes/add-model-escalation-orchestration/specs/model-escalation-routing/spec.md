# Spec Delta

## Purpose

定义一条可审计、可恢复的模型升级路径：由低成本监控模型持续处理观察、分析、审查与协调，仅在服务端确认需要修改代码时调用高能力修复模型，并在修复阶段结束后回到监控模型。

## ADDED Requirements

### Requirement: 版本化升级策略

系统 SHALL 保存启用状态和版本化的模型升级策略，从既有供应商目录解析监控模型与代码修复模型；策略默认关闭，启用前必须确认两个模型及其凭据可用。

#### Scenario: 显式启用 flash 与 v4pro 策略

- **WHEN** 所有者选择已配置的 flash 模型作为监控模型、v4pro 模型作为修复模型并提交当前版本
- **THEN** 系统保存该策略并显示启用状态、模型身份和策略版本

#### Scenario: 模型或凭据不可用

- **WHEN** 策略引用的供应商、模型或凭据已删除或失效
- **THEN** 系统阻止启用或继续调度该策略，显示缺失条件且不隐式改用其他模型

### Requirement: 监控与修复角色分流

系统 SHALL 使用监控模型执行协调、仓库分析、问题调查、复现辅助和独立审查，仅在代码修复阶段使用升级后的修复模型；后台发布逻辑继续独立执行，模型不得获得额外发布权限。

#### Scenario: 进入代码修复阶段

- **WHEN** 经过授权的代码修复任务开始
- **THEN** 代码修复角色解析为策略中的修复模型，其他监控与审查角色仍解析为监控模型

#### Scenario: 生成修复后的 PR

- **WHEN** 修复和独立审查均已通过并进入发布步骤
- **THEN** 系统由后端发布器创建内容，修复模型和监控模型均不直接获得 GitHub 发布工具

### Requirement: 服务端控制的升级触发

系统 MUST 仅在持久化故障事实、当前授权和允许动作共同证明需要修改代码时升级到修复模型；模型建议、错误文本相似性或单一异常不得成为升级依据。

#### Scenario: 授权的修复动作

- **WHEN** 故障已持久化，来源任务仍有效，且服务端授权执行代码修复或重试修复
- **THEN** 系统记录触发依据并使用升级后的修复模型开始修改

#### Scenario: 非代码故障

- **WHEN** 故障仅表现为超时、鉴权失败、环境不可用、外部服务错误或未知原因
- **THEN** 系统沿用监控模型和既有恢复策略，不自动启动 v4pro 修复

#### Scenario: 用户取消或预算不足

- **WHEN** 原任务已取消、授权撤回或恢复预算不足
- **THEN** 系统不启动升级后的修复调用，并记录受阻原因

### Requirement: 阶段快照不可变

系统 MUST 在模型阶段开始时固定该阶段实际使用的供应商、模型、版本和凭据依据；阶段执行期间修改策略不得改变运行中的 Agent、工具权限或历史事件。

#### Scenario: 运行中修改策略

- **WHEN** 监控或修复阶段执行期间所有者保存了新的升级策略
- **THEN** 当前阶段继续使用原快照，新策略只影响尚未开始且可重新解析模型的阶段

#### Scenario: 阶段交接

- **WHEN** 监控角色完成交接并将控制权交给代码修复角色
- **THEN** 新阶段取得新的不可变模型快照，旧阶段事件保留其原模型身份

### Requirement: 修复后回到监控模型

系统 SHALL 在代码修复调用结束、失败、取消或受阻后，把后续协调、验证汇总和独立审查交回监控模型，禁止持续占用高成本模型或通过重新开始任务绕过现有恢复边界。

#### Scenario: 修复成功

- **WHEN** 修复模型提交补丁并完成隔离验证
- **THEN** 独立审查和后续协调使用监控模型，并在审计时间线中记录返回原因

#### Scenario: 修复失败

- **WHEN** 修复模型无法生成合规补丁、验证失败或审查拒绝
- **THEN** 系统保存失败证据并回到监控模型的协调路径，由既有预算和策略决定下一步；不得无限自动升级

### Requirement: 实际模型与切换理由可审计

系统 MUST 在每次升级和返回时记录实际供应商、模型、版本、阶段、触发依据和时间，并在任务详情与故障时间线中提供只读视图。

#### Scenario: 查看升级时间线

- **WHEN** 所有者打开一次包含模型交接的任务
- **THEN** 页面按发生顺序显示监控模型阶段、升级原因、修复模型阶段和返回监控模型阶段

#### Scenario: 历史依据缺失

- **WHEN** 旧任务没有保存可靠的实际模型或切换理由
- **THEN** 系统显示未知并保持该任务与其他依据隔离，不用当前策略倒推历史调用

### Requirement: 权限与预算跨模型连续

系统 MUST 在模型切换前后保留同一根任务的权限、工具边界、累计请求、纠正、续办、耗时、费用和其他预算；模型升级不得创建第二个恢复执行者或放宽既有门禁。

#### Scenario: 已用预算接近上限

- **WHEN** 监控阶段已消耗部分总预算后进入修复阶段
- **THEN** 修复模型只使用剩余预算，累计用量包含两个模型的实际请求

#### Scenario: 审查未通过

- **WHEN** 升级模型生成的补丁未通过独立审查
- **THEN** 系统保留拒绝结论并回到既有修复反馈边界，不创建 PR 或绕过审查

### Requirement: 完整修复链验收证据

系统 SHALL 为一次真实监控修复运行保留分析、故障、模型交接、补丁验证、独立审查和 PR 的关联证据；只有目标仓库存在真实有效问题且所有门禁通过时才允许发布 PR。

#### Scenario: 端到端验收通过

- **WHEN** 指定目标仓库产生有效分析结果，修复补丁通过验证和独立审查，且远程权限有效
- **THEN** 系统创建一个关联 Issue、包含规定中文描述的 PR，并把 PR 关联回原分析与模型升级时间线

#### Scenario: 没有有效问题或验证失败

- **WHEN** 分析没有产生可实施问题、补丁验证失败、审查拒绝或账号权限不足
- **THEN** 系统记录真实受阻结果且不创建空 Issue、空 PR 或宣称升级链验收通过

### Requirement: 合并与部署保持独立授权

模型升级策略和 PR 创建 SHALL NOT 自动授予合并、发布或部署权限；这些动作继续遵循现有独立授权和 GitHub 合并事实核验。

#### Scenario: PR 已创建

- **WHEN** 目标仓库 PR 创建成功但所有者尚未独立授权合并或部署
- **THEN** 系统停留在等待合并状态，不自行合并、部署或把原故障标记已恢复
