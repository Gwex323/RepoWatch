# Spec Delta

## Purpose

在每次导入后完成可追踪的全仓审查，并通过固定版本、覆盖清单和真实检查证据管理扫描完成条件，使漏扫、输出截断和环境缺口能够受控补齐，而非依赖 Agent 自行声明完成。

## ADDED Requirements

### Requirement: 每次导入完成完整扫描后才可修复

系统 SHALL 为每次新的导入请求原子增加导入代次、撤销就绪并建立完整扫描任务；修复及发布核对仓库、目标配置、导入代次、目标 SHA 和扫描策略修订，不能仅凭 SHA 相同放行；用户选中的本地候选不得绕过门槛。

#### Scenario: 扫描尚未完成但用户选择候选
- **WHEN** 用户选择修复扫描过程中发现的缺陷
- **THEN** 系统保存任务并等待扫描就绪，不立即开始代码修改

#### Scenario: 重新导入已有仓库
- **WHEN** 用户再次导入同一仓库
- **THEN** 系统建立新的完整扫描任务，不以日常增量结果替代本次导入要求

#### Scenario: 同一提交重新导入且旧扫描随后完成
- **WHEN** 新导入代次已建立，旧代次在同一 SHA 上返回完成结果
- **THEN** 旧结果只登记为历史，本次完整扫描完成前不放行修复或发布

#### Scenario: 修复期间重新导入
- **WHEN** 正在修复的仓库被新的导入请求撤销就绪
- **THEN** 运行在安全边界保存现场并等待本次完整扫描，发布前复核当前代次

### Requirement: 完整清单和排除项可审计

系统 SHALL 枚举全部自有源码、测试、配置、CI 及依赖声明，记录路径、内容标识和模块／分块范围；构建产物、第三方源码及二进制排除项必须有版本化依据。

#### Scenario: 自有受检文件过大
- **WHEN** 一个文件无法在单次审查输入内完整处理
- **THEN** 系统拆分受检范围并保留完整覆盖关系，不因大小或忽略规则静默排除

### Requirement: 模块覆盖基于真实输入和产物

系统 SHALL 为受检范围记录实际审查输入及结果、适用检查基线和候选证据，只有全部范围具备有效结果才完成扫描；列举文件名或模型宣称完成不能代替证据。

#### Scenario: 一个模块缺少结果
- **WHEN** 覆盖核验发现清单项没有对应有效审查产物
- **THEN** 系统报告具体缺口，不将该批次标记完成

### Requirement: 区分已有失败和检查无法执行

系统 SHALL 区分检查通过、已有代码失败、有依据的不适用和无法执行；原有 Bug 的真实失败可以构成基线，但声明存在的检查因环境缺失无法运行属于缺口。

#### Scenario: 原仓库存在已证实的失败测试
- **WHEN** 测试真实执行并显示已有缺陷
- **THEN** 系统保存失败基线及候选，不要求扫描自动修改代码使测试通过

#### Scenario: 缺少运行环境
- **WHEN** 适用检查因缺依赖未执行
- **THEN** 系统先尝试受控补全，不能把检查记为通过或无依据地记为不适用

### Requirement: 覆盖缺口先受控自动补全

系统 SHALL 在原预算和授权内补扫、拆分重试、重收真实证据或重建受管环境，每次重新核验；无法恢复或耗尽上限才进入全局阻塞，不修改业务源码、放宽门槛、增加预算或切换供应商。

#### Scenario: 审查输出被截断
- **WHEN** 模块结果不完整且仍有授权预算
- **THEN** 系统拆小同一范围重新审查，全部子范围有效后再核验

#### Scenario: 补全达到上限
- **WHEN** 缺口未解决且原任务预算耗尽
- **THEN** 扫描保持未完成并全局暂停，等待用户处理，不自动开始新预算任务

### Requirement: 扫描批次固定版本且可续扫

系统 SHALL 保持一个批次的提交和输入清单不变；同版本仅在产物仍有效时续扫，目标分支或实质扫描策略变化后重新建立覆盖依据，环境／工具变化须复核相关结果，逐项提供新检查或可靠的覆盖复用依据。

#### Scenario: 目标分支发生变化
- **WHEN** 已完成扫描不再对应当前目标提交
- **THEN** 系统撤销新版本的修复就绪，补扫受影响范围；影响无法确定时全仓重扫，不改写旧批次的版本

#### Scenario: 修复需要补扫
- **WHEN** 修复发布前发现目标分支变化
- **THEN** 修复保存现场并释放执行位，前置扫描完成后再整合、验证和审查

#### Scenario: 代码未变但检查策略改变
- **WHEN** 新策略增加必要受检内容或检查，目标 SHA 未变化
- **THEN** 旧就绪不能覆盖新策略，系统补齐并核验新要求后才放行

### Requirement: 本地候选先建立 GitHub Issue

系统 SHALL 将扫描发现保留为附位置、代码版本和依据的本地候选。用户选择候选并通过 repair-verification 的准入及敏感信息核验后，系统查询目标仓库中的相似 Issue；确认同一问题则关联已有 Issue，未发现相似 Issue 才由系统创建 Issue。Issue 身份未确认前不得创建修复分支或修改代码；扫描发现本身不创建 PR，敏感披露方式未确认不自动发布候选。

#### Scenario: 扫描发现疑似 Bug
- **WHEN** 模块审查产生有依据的缺陷线索
- **THEN** 系统展示本地候选及来源，未被选择时不创建 Issue、修复分支或 PR

#### Scenario: 相似 Issue 已存在
- **WHEN** 用户选择候选且系统查到并确认同一问题的 Issue
- **THEN** 系统将候选关联已有 Issue 和主任务，完成 PR 冲突检查前不创建修复分支或修改代码

#### Scenario: 没有相似 Issue
- **WHEN** 用户选择候选且准入／敏感核验通过，目标仓库的必要查询已完整成功，没有发现相似 Issue
- **THEN** 系统创建含扫描来源和证据的 GitHub Issue，并核实 Issue 身份后才允许进入后续修复门禁

#### Scenario: 查重不完整或语义不确定
- **WHEN** Issue 查询分页未完成、请求失败或候选与结果的同一性无法确认
- **THEN** 系统保留候选并等待／阻塞核对，不创建 Issue、分支或代码修改

#### Scenario: Issue 创建回执丢失
- **WHEN** 创建 Issue 的远端结果未知或响应丢失
- **THEN** 系统按持久操作意图对账远端 Issue，确认身份前不重发创建，也不创建修复分支
