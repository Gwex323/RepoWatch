# Spec Delta

## Purpose

将已通过验收的候选受控交付到 GitHub，并持续关联 PR、CI、维护者评审和后续修订，使重复信号、分支漂移和远端不确定结果不会转化为盲目重复发布或错误宣告 Issue 已解决。

## ADDED Requirements

### Requirement: 仅受控发布器可创建或更新 PR

系统 SHALL 在当前任务输入、准入／占用、Issue／受管 PR 唯一绑定、执行权、扫描就绪、候选内容、验证与独审均有效时才允许受控发布器写 GitHub；处理／审查角色不得持有直接发布权限。

#### Scenario: 候选缺少有效独审
- **WHEN** 发布被请求但该候选未通过独审
- **THEN** 发布器拒绝操作，不推送或创建 PR

### Requirement: 发布路径和分支更新具有版本保护

系统 SHALL 分别处理有维护权限仓库和用户 Fork，保存上游／发布仓库身份、base／head 及预期版本，使用稳定受管分支；默认不盲目覆盖外部提交或自行重建关闭的交付链。

#### Scenario: 外部用户更新 PR 分支
- **WHEN** 远端 head 与预期旧版本不一致
- **THEN** 系统保留外部改动并重新整合／验证，不能强制覆盖后继续宣称原证据有效

#### Scenario: 候选引用不可交付的外部内容
- **WHEN** 候选引用尚未发布的子模块提交，或所需 LFS 内容无法通过已验收的受控适配交付
- **THEN** 系统阻塞发布，不仅推送指针，不自动推送子仓库、创建额外 PR 或执行持凭据 hook

### Requirement: Issue 与受管 PR 一一对应

系统 SHALL 为每个受管 PR 绑定且只绑定一个稳定 GitHub Issue，同一 Issue 的受管生命周期最多一个受管 PR，创建前可为零。以双方稳定仓库／对象 ID 建立双向唯一约束并在发布意图、结果对账及更新前核对，返修只更新原 PR。禁止一 PR 修复多个独立 Issue、一个 Issue 拆为多个受管 PR，或经新 Run／重导入／解绑绕过唯一性；正文及提交消息的自动关闭声明只针对所绑定 Issue。

#### Scenario: 重复发布或跨 Issue 复用 PR
- **WHEN** 同一 Issue 被请求创建第二个受管 PR，或已有受管 PR 被请求交付另一个 Issue
- **THEN** 系统拒绝新的绑定及远端创建，不因原 PR 已关闭就释放生命周期唯一约束

#### Scenario: 多轮返修和跨模块修改
- **WHEN** 同一 Issue 的修复需多轮评审或多个模块的必要修改
- **THEN** 系统保持原 Issue／PR 绑定，在同一 PR 重新验证、审查和更新，不按模块另建 PR

#### Scenario: Issue 包含多个独立目标
- **WHEN** 分诊发现原 Issue 实际包含需要分别交付的独立问题
- **THEN** 系统通过 UI 确认收敛／拆分方案；经确认并查重创建独立 Issue 后分别交付，不自动批量合入一个 PR 或未经确认修改原 Issue

#### Scenario: 外部 PR 竞争与关闭
- **WHEN** GitHub 上他人为同一 Issue 创建竞争 PR 或该外部 PR 关闭未合并
- **THEN** 系统保留外部事实并按等效性等待或重新评估，不把观测当作受管绑定；仅在本系统没有受管 PR 时可创建首个 PR，已有受管 PR 则延续原交付链而不另建

#### Scenario: 受管 PR 已关闭或合并后 Issue 重开
- **WHEN** 受管 PR 关闭未合并、原分支删除，或合并后同一 Issue 重开
- **THEN** 系统保留原绑定并在 UI 按终态请求处理，不自动重开／重建或发布第二个受管 PR，也不复制相同 Issue 规避限制

### Requirement: 外部开放 PR 阻止重复修复

系统 SHALL 在创建修复分支前及发布前读取该 GitHub Issue 的开放 PR。确认外部 PR 正在处理同一问题时，关联 PR 并等待其结果；有证据确认与当前问题无关时记录依据并继续原任务，仅关系无法判断时通过 UI 请求用户决定。不得仅因关联同一 Issue、涉及不同范围或修改同一文件而阻止任务；读取不完整或权限故障须核对，不得误判为无关。不得并行启动重复修复或创建重复 PR。

#### Scenario: 外部 PR 处理同一问题
- **WHEN** 修复候选已关联 Issue，且同一 Issue 存在外部开放 PR，经证据确认处理同一问题
- **THEN** 系统关联外部 PR、释放执行位并等待，不创建修复分支或重复 PR

#### Scenario: 同一 Issue 的开放 PR 已确认无关
- **WHEN** 对开放 PR 的范围及证据核对确认其不处理当前问题
- **THEN** 系统保存判定依据并继续原任务，在其余门槛满足时可建分支或发布，不要求用户额外批准

#### Scenario: 开放 PR 关系无法判定
- **WHEN** 完成必要读取后仍无法确认开放 PR 是否处理当前问题
- **THEN** 系统保留候选、释放执行位，并在 UI 提供 PR 对照及确认同一问题、确认无关、补充信息或取消入口；决定经当前版本核验后再推进

#### Scenario: 发布前出现外部 PR
- **WHEN** 本地修复通过验证后、创建或更新 PR 前发现新的相关外部 PR
- **THEN** 系统重新分类关系；同一问题则停止发布并关联等待，确认无关则满足其他门槛后继续，无法确定时通过 UI 请求用户决定，不创建重复 PR

#### Scenario: 等待的外部 PR 已合并
- **WHEN** 关联的外部 PR 变为已合并
- **THEN** 系统确认合并提交进入当前目标分支并重新取得有效扫描／复现证据；确认问题已解决则将主任务标为外部修复解决，不创建修复分支或替代 PR

#### Scenario: 首次发现相关 PR 时已经合入目标分支
- **WHEN** 相关 PR 在本系统建分支或发布前已经合入目标分支
- **THEN** 系统直接核验最新版本的扫描／复现证据，不进入等待开放 PR；确认解决则标记外部修复解决并停止重复发布

#### Scenario: 外部 PR 合入后问题仍存在
- **WHEN** 最新目标版本的有效证据表明相关 PR 仅部分解决或没有解决当前问题
- **THEN** 系统重新核实剩余范围及相关 PR，满足当前输入、扫描和其他门槛后基于最新目标版本继续原任务，不沿用失效证据

#### Scenario: 等待的外部 PR 关闭但未合并
- **WHEN** 关联的外部 PR 关闭且未合并
- **THEN** 系统重新读取 Issue 和所有相关开放 PR；只有 Issue 仍有效、问题仍存在且无同一问题的外部修复或待核实关系时才恢复原主任务，确认无关的 PR 不阻止恢复；其他情形按最新状态处理或在 UI 请求澄清

### Requirement: 远端写入意图和结果可核对

系统 SHALL 保存稳定操作意图并在写入后核对实际仓库、分支及 SHA；回执丢失先查询相关全部状态，结果不明保持阻塞，不凭标题认领或盲目重发，不宣称普适恰好一次。

#### Scenario: 创建成功但响应丢失
- **WHEN** 本地没有收到创建回执
- **THEN** 系统查询已打开／关闭等相关 PR 并核对身份，确认之前不再次创建

#### Scenario: 创建窗口发生分支竞争
- **WHEN** 返回 PR 的实际版本不符合预期
- **THEN** 系统记录不确定操作并阻塞核对，不按预期值伪记成功

### Requirement: PR 正文提供可核查交付依据

系统 SHALL 以“概述、变更内容、设计方案／说明、验证／验收、review 记录”组织正文，列出验证事实和已知限制，并关联已确认的 GitHub Issue 编号及候选来源。

#### Scenario: 本地扫描候选修复交付
- **WHEN** 系统交付源自本地扫描的候选
- **THEN** PR 正文关联候选对应的已确认 Issue 编号并引用证据

### Requirement: CI 和评审按实际版本跟进

系统 SHALL 关联实际提交、base／合并 ref、版本化必要检查集合、来源、适用运行尝试和评审版本，区分 pending、缺失、失败及通过；旧版本绿灯、未经策略认定的 skipped／neutral 等结果或等待维护者授权不得当作当前通过。

#### Scenario: Fork CI 等待维护者批准
- **WHEN** 尚未取得本次必要检查结果
- **THEN** PR 正常等待并释放执行位，不伪记检查通过

#### Scenario: 同一提交上的必要检查重跑
- **WHEN** 新的适用尝试仍 pending，之前有成功或失败记录
- **THEN** 系统等待新尝试，不沿用旧绿灯；新尝试产生有效结果后按策略取代旧记录，历史失败不永久阻塞

### Requirement: 人工请求修改进入原任务返修

系统 SHALL 合并评审意见到原任务，核对已撤销／已处理意见和对应代码版本；明确范围内修改自动排队，歧义或扩展范围等待确认，返修重验重审后更新同一 PR 并累计原预算。

#### Scenario: 其他仓库运行时收到评审
- **WHEN** 当前 PR 被请求修改
- **THEN** 系统保存反馈并排队，不抢占执行位或创建第二个 PR

#### Scenario: 评审要求新增产品功能
- **WHEN** 请求越过已批准修复范围
- **THEN** 系统正常等待方案确认，不自行扩展实现

### Requirement: 验证与交付终态分开记录

系统 SHALL 分别记录代码验证、PR 交付和 Issue 状态，合并由用户或仓库规则执行；关闭未合并、批准或 PR 创建本身都不得代替修复验证或成功交付。

#### Scenario: PR 被关闭未合并
- **WHEN** 系统取得该关闭结果
- **THEN** 记录关闭未合并并保留独立 Issue 状态，不自动重开、另发替代 PR 或标记已解决
