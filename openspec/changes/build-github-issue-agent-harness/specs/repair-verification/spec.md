# Spec Delta

## Purpose

在提交或更新 PR 前，以任务验收规范和真实执行证据判断修改是否满足目标，防止环境失败、旧版本结果、弱化测试或 Agent 自证完成被误用为成功，并为无法可靠验证的任务保留阻塞路径。

## ADDED Requirements

### Requirement: 分诊确定任务范围及验收规范

系统 SHALL 按版本化仓库准入策略推进条件明确的 Bug，对功能和大规模重构先形成方案并等待用户批准；验收目标、类型和规范版本与任务绑定。分诊结果固定为自动修复、等待补充信息、等待方案批准、已排除、外部修复处理中、执行阻塞，分别保存原因、证据、输入／策略版本和重新分诊条件，不把分类直接混同为任务完成。

#### Scenario: 功能请求未获批准
- **WHEN** 分诊判断 Issue 为新增功能
- **THEN** 系统只形成方案和验收条件并正常等待，不自行决定产品需求并开始实现

### Requirement: Issue 入口按仓库模式和实际权限配置

系统 SHALL 支持手动选择、标签准入、全部合格 Bug 三种仓库模式；自有或有维护权限仓库默认全部合格 Bug，第三方公共仓库默认标签准入。允许标签未配置时显示待配置，不降级为全部准入；标签名称／严重程度及排除映射按仓库版本化配置。入口过滤不丢弃同步对象，用户选择只替代入口筛选，不绕过后续门槛。

#### Scenario: 第三方仓库未配置允许标签
- **WHEN** 通过 Fork 路径导入的第三方公共仓库仍使用默认模式且未配置允许标签
- **THEN** 系统同步已有及新增 Issue 并显示准入待配置，不自动修复所有 Bug；用户可配置标签或明确选择具体 Issue 后再核验

#### Scenario: 全部模式中的 Bug 没有 bug 标签
- **WHEN** 自有仓库 Issue 开放且内容符合 Bug 条件，未命中排除或占用限制，但没有 bug 标签
- **THEN** Worker 可形成可验证目标并推进原任务，不要求额外打标签，实际复现和扫描门槛仍适用

#### Scenario: 手动模式的新 Issue 到达
- **WHEN** 仓库处于手动选择模式且同步到未选择的新 Issue
- **THEN** 系统保存对象并在 UI 提供选择，不自动启动其模型分诊／修复；选择后仍须核验安全、占用、Issue／PR 关系及验收

### Requirement: 分诊区分信息不足、排除和执行障碍

系统 SHALL 仅对开放、未持久排除、Bug 目标和复现路径明确且无重复任务／外部等效修复／他人处理的 Issue 自动推进。非当前执行身份的 assignee、维护者明确占用及配置的排除标签不自动修复；标签／正文或占用关系不明时通过 UI 澄清。初诊信息不足正常等待，正式执行阶段无法复现、缺环境／权限等才按执行阻塞处理。

#### Scenario: 有其他 assignee 或已排除标签
- **WHEN** Issue 有其他 assignee、他人明确处理证据，或命中 wontfix／duplicate／question 等排除映射
- **THEN** 系统保存已排除原因且不修改 assignee、不启动重复修复；标签或 assignee 改变可重新分诊，用户持久排除必须明确重新启用

#### Scenario: 需要补充信息
- **WHEN** 初诊缺少定位／复现条件或命中 needs-info，尚未进入正式复现
- **THEN** 系统正常等待并在 UI 列出待补充项，不因此暂停所有仓库，也不声称已经尝试复现

#### Scenario: 信息足够但实际无法复现
- **WHEN** 准入后正式执行复现，仍无法取得目标 Bug 的有效修改前证明
- **THEN** 系统按既有验证障碍阻塞并全局暂停，不降格为无限等待信息或伪记复现成功

#### Scenario: 已有主任务或等效外部 PR
- **WHEN** 分诊发现同一 Issue 已有受管任务或同一问题的外部开放 PR
- **THEN** 系统复用原任务或记录外部修复处理中并等待，不新建并行修复或重复 PR

#### Scenario: 敏感候选准备创建 Issue
- **WHEN** 本地候选涉及漏洞披露、密钥／敏感数据泄漏或披露方式不明
- **THEN** 系统先保存仓库范围脱敏待办并请求用户确定处理方式，不自动创建公开 Issue／PR 或认领评论；普通选择及允许标签不构成披露批准

### Requirement: Bug 必须有有效的修改前后证明

系统 SHALL 以相同有效复现／回归探针在未修复代码上证明目标失败、在修复代码上通过；无测试时补齐探针，测试辅助材料不得夹带实现修复。

#### Scenario: 仓库没有现成测试
- **WHEN** 处理角色新增回归测试
- **THEN** 系统在独立原始代码副本与候选上运行该测试，保存内容和两侧真实结果

#### Scenario: 测试因缺包而失败
- **WHEN** 探针未执行到目标条件，仅因导入或环境错误退出
- **THEN** 系统不把该失败认定为目标 Bug 已复现

#### Scenario: 已修好原问题的 PR 只需格式返修
- **WHEN** 旧 PR head 上原 Bug 探针已通过，但收到范围内格式意见
- **THEN** 原问题仍在上游未修复 base 与新候选之间核验，格式意见按目标验证，不要求旧 PR head 重新出现原 Bug

### Requirement: 获批功能和重构使用对应证据

系统 SHALL 对功能证明新增能力，对纯重构证明原结构目标未满足、修改后满足及约定行为保持；二者仍须回归、独审和发布门槛，不允许把 Bug 改名规避复现。

#### Scenario: 纯重构前行为测试已通过
- **WHEN** 已批准方案要求结构改善及行为保持
- **THEN** 系统使用结构目标和前后行为证据验收，不伪造原本不存在的行为 Bug

### Requirement: 既有失败必须证明无关且未恶化

系统 SHALL 在当前 base 和可解释一致的环境／命令下建立基线，比较失败用例及原因、测试发现、跳过项和检查变化；新增、相关或无法归因的失败不得放行。

#### Scenario: 失败数量相同但用例不同
- **WHEN** 修改前后失败总数相同但出现新失败用例
- **THEN** 系统不能仅凭数量认定未恶化，须返修或阻塞

#### Scenario: 既有无关失败
- **WHEN** 有证据证明失败与修改无关且未恶化，目标修复仍有有效验证
- **THEN** 系统记录其依据和限制，不仅因存在该旧失败拒绝发布

#### Scenario: 本轮返修增量通过但完整 PR 引入回归
- **WHEN** 新候选相对旧 PR head 的检查通过，但相对当前上游 base 的必要回归出现新增失败
- **THEN** 系统拒绝发布，完整候选须通过基线比较及独审，不能只凭本轮增量放行

### Requirement: 验收条件不能被自动弱化

系统 SHALL 审查测试断言、发现范围、忽略规则及检查配置变化；不得通过删断言、增加 skip 或减少检查换取通过，实质验收变更必须另获用户确认。

#### Scenario: 修改通过减少测试覆盖取得绿灯
- **WHEN** 候选减少必要检查或改变目标断言
- **THEN** 独审和验收门槛阻止发布，不能仅接受成功退出码

### Requirement: 最终证据绑定冻结的实际候选

系统 SHALL 在最终验证及独审期间停止处理角色写入，绑定输入／规范、base、候选提交和实际树、环境、探针、命令及产物；候选内容变化后重新验证与审查。

#### Scenario: HEAD 未变但有未提交修改
- **WHEN** 工作区实际内容与最终证据绑定候选不一致
- **THEN** 系统使旧证据失效，不发布未被测内容

#### Scenario: 目标分支变化
- **WHEN** 发布前读取到新的 base
- **THEN** 系统等待新版本扫描就绪并整合，再取得有效验证及独审证据

### Requirement: 发布前后检查分别记录

系统 SHALL 在有效提交前证据和独审满足后才允许发布，再跟进 PR 专属检查；若目标问题只能在 PR 环境验证且无其他有效提交前证明，任务保持阻塞。

#### Scenario: PR 专属 CI 尚未存在
- **WHEN** 本地和预设可执行证据已有效证明修复并通过独审
- **THEN** 系统可按门槛创建 PR，但不得提前把 PR 专属检查标记通过

#### Scenario: 唯一修复证明只能来自 PR 环境
- **WHEN** 没有其他有效提交前证据
- **THEN** 系统保持阻塞，不为触发 CI 而绕过门槛发布 PR

### Requirement: 有界返修与无法验证的阻塞

系统 SHALL 在剩余授权及无进展检测允许时对可修复验证失败或审查发现返回修改；按 task-orchestration 的持久进展规则识别重复失败与振荡，不能仅因任务复杂或测试尚未全通过而判为无进展。有真实进展且预计剩余额度不足时在耗尽前申请有限续期；无法复现、无法验证、触发无进展／安全上限或已耗尽预算时全局暂停。

#### Scenario: 独审发现可修复问题
- **WHEN** 原任务仍有预算
- **THEN** 系统返回处理阶段，修改后重新验证和独审，不直接发布旧结论

#### Scenario: 长任务逐步修复不同子问题
- **WHEN** 验证仍未全通过但每轮有新证据确认不同子问题已解决，预算接近上限
- **THEN** 系统记录真实进展，按续期流程申请有限追加，不将修复轮数多等同于无进展；未批准不超额执行，最终仍需完整回归和独审
