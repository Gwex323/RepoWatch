# Spec Delta

## Purpose

在本地多仓库环境中提供可靠的串行执行和可追踪恢复，确保扫描、分诊、修复、审查、返修与提炼不会绕过执行权、预算或人工暂停，并区分正常等待与真正执行障碍。

## ADDED Requirements

### Requirement: 全局只有一个常规重任务执行者

系统 SHALL 串行执行扫描、模型分诊、方案、修复、独审、返修、模型提炼与受管维护任务；只读同步不占用该执行位且不得调用推理模型或仓库命令。

#### Scenario: 多仓同时排队
- **WHEN** 多个仓库的重任务同时可执行
- **THEN** 同一时刻最多一个运行发起模型或仓库工具执行

#### Scenario: 暂停时同步新 Issue
- **WHEN** 全局已暂停且只读同步发现新 Issue
- **THEN** 系统保存对象与待分析信号，不旁路调用模型分诊

### Requirement: 持久队列按就绪条件领取

系统 SHALL 持久化任务和执行前置条件，在满足全局状态、仓库状态及依赖后按用户显式优先级、自动严重程度及老化、原入队时间和稳定标识领取；正常等待的队首不得阻塞其他可执行任务，不抢占执行中任务。自动排序域按累计可执行排队时间每个配置间隔提升一级，最高至最高自动优先级，初始间隔 24 小时；不能越过人工优先级或就绪门槛。

#### Scenario: 修复等待前置扫描
- **WHEN** 修复任务需要新目标版本的扫描
- **THEN** 它保存现场并释放执行位，扫描可运行，不能占位等待自身前置任务

#### Scenario: 共享扫描完成或非预算归属等待方取消
- **WHEN** 多个任务依赖同一前置扫描，扫描完成或非预算归属的等待方被取消
- **THEN** 完成结果与合格等待方的唤醒原子保存；非预算归属等待方取消仅解除自身依赖

#### Scenario: 共享扫描的预算授权被撤销
- **WHEN** 取消预算归属任务使扫描失去继续消耗的授权
- **THEN** 系统安全停止扫描并保留其他依赖，等待用户明确处理，不自动转移预算或继续消费

#### Scenario: 低严重程度任务持续处于可执行队列
- **WHEN** 未人工排序的任务累计可执行排队时间达到老化间隔
- **THEN** 自动优先级提升至配置上限，同级取原入队时间；正常等待和暂停不累计，重试不清零，人工显式优先级仍优先

### Requirement: 同一问题保持稳定主任务

系统 SHALL 将同一仓库同一 Issue 的分诊、规划、修复和 PR 返修关联同一主任务；重试、重复反馈或重启不得生成重复活跃修复或 PR。

本地占用 SHALL 依靠主任务唯一约束及执行权，不视为 GitHub 远端独占；建分支前及发布前重新核验准入、标签、assignee、占用和 PR 状态。

#### Scenario: 重复评审信号到达
- **WHEN** 相同评审意见被多次同步
- **THEN** 系统更新原任务的后续工作，不复制任务或并行分支

#### Scenario: 已排除任务再次收到更新
- **WHEN** 人工排除／取消的 Issue 被同步、重开或随仓库重新导入
- **THEN** 系统保留排除／取消标记，明确重新启用前不自动恢复修复或复制任务

#### Scenario: 本地候选获得 Issue 身份后再排队修复
- **WHEN** 用户选择本地候选，系统已关联相似 Issue 或成功创建 Issue，并完成开放 PR 检查
- **THEN** 系统按稳定 GitHub Issue ID 创建或复用唯一主任务，扫描就绪后才允许领取修复执行位

#### Scenario: 修复期间他人接手 Issue
- **WHEN** 最新读取发现其他 assignee 或维护者明确由他人处理
- **THEN** 系统安全保存现场并停止按旧条件发布，在 UI 展示排除／澄清入口，不覆盖他人 assignee，不把本地占用当作远端锁

### Requirement: 执行权失效后禁止旧执行者继续写入

系统 SHALL 维护有期限的唯一执行权与递增代次，并拒绝失效执行者发起新工具、发布或状态覆盖；执行权到期不等于旧命令已经停止。

#### Scenario: 旧执行者返回迟到结果
- **WHEN** 旧运行失去执行权后返回结果
- **THEN** 结果不得覆盖新代次状态，系统核对旧命令及现场后才能恢复执行

### Requirement: 预算按原任务累计

系统 SHALL 固定每项执行的预算归属，累计有效执行时长、调用／token 与修复／恢复轮数，将子任务、SDK 重试、拆分、重建、新建前置补扫、返修及提炼计入原预算；共享执行只计一次，任一适用上限耗尽后停止继续消耗并阻塞。

#### Scenario: PR 返修创建新运行
- **WHEN** 同一 PR 的后续评审触发新运行
- **THEN** 运行继承原任务累计消耗，不重新取得完整预算

#### Scenario: 等待维护者评审
- **WHEN** 任务处于不执行模型或命令的正常等待
- **THEN** 等待时间不计入有效执行时长

#### Scenario: 修复新建前置补扫任务
- **WHEN** 修复因目标漂移创建独立调度的扫描 Task
- **THEN** 扫描仍消耗发起修复的预算，父任务等待不使实际扫描消耗漏记；关联已有共享扫描则保留原归属且不重复记账

### Requirement: 执行障碍暂停全局队列

系统 SHALL 在权限、环境、验证、必需模型能力、无进展或预算等障碍需要人工介入时记录阻塞并暂停全部常规重任务；不能自动跳过阻塞或自动解除暂停。未耗尽且无障碍的预算续期申请属于正常等待。

#### Scenario: 一个仓库无法验证
- **WHEN** 仓库 A 的任务无法在预算内完成必要验证
- **THEN** A 阻塞且其他仓库常规重任务等待，API 与只读同步仍可工作

### Requirement: 无进展与振荡由持久证据检测

系统 SHALL 按实施契约 §3 为各模式记录阶段目标、输入／代码／环境／策略修订、归一化动作、失败签名、有效证据与进展水位。初始连续 3 次已完成可比尝试无有效进展，或 2 个重复状态／代码周期没有净进展时，在下次调用前阻塞并全局暂停；阈值版本化且不得自动放宽。新日志、时间戳、Diff、运行／批次标识、分支 SHA 或模型自述不能单独算进展。单步超时与阶段工具步数等安全上限独立生效。

#### Scenario: 重复执行相同无效修复
- **WHEN** 同一目标连续 3 次已完成尝试只改变日志或代码而仍有同一失败且无新增有效证据
- **THEN** 系统保存比较窗口并停止下一次调用，在 UI 提供处理入口，不因仍有预算继续重复

#### Scenario: 复杂调查不断取得真实反证
- **WHEN** 多轮实验分别排除了此前未排除的相关假设，或扫描持续新增有效覆盖，或逐步修好不同子问题
- **THEN** 程序核实相关证据并推进进展水位，不仅因总轮数多、测试尚未全通过或总任务未完成而判为无进展

#### Scenario: 候选在两个版本间来回修改
- **WHEN** 候选 A 与 B 之间发生 2 个重复周期且没有净新增有效证据或已解决子目标
- **THEN** 系统记录振荡并阻塞，正常修改—验证往返且持续有进展的流程不被误判

#### Scenario: 长检查与外部等待
- **WHEN** 检查尚在独立超时内执行，或任务正在排队、退避、等待用户／CI／外部 PR
- **THEN** 该等待不增加无进展尝试计数，心跳也不算进展；执行超时仍须停止／隔离并核对旧命令

#### Scenario: 重启续期或目标分支持续变化
- **WHEN** 已有尝试记录的任务重启、新建 Run／批次、追加预算或追赶新的目标 SHA
- **THEN** 原目标的进展历史与计数保留，SHA 改变本身不构成进展，不能靠更换标识逃避检测

#### Scenario: 用户处理无进展后授权重试
- **WHEN** 用户提交实质策略／输入／环境变化并明确授权有界重试
- **THEN** 系统保留旧检测记录，核验安全重试条件后允许新窗口，不要求先有重试的通过结果；仅加预算或普通确认不能清除该阻塞，发布仍需真实验证

### Requirement: 预算按有效进度申请有限续期

系统 SHALL 区分可批准追加的任务授权总额与独立运行安全上限，按任务工作量初始分配，在每步执行前核对已用、预留及未知用量占用。初始任一授权维度达到 80% 时预警；有实质进展但预计剩余额度不足、无法可靠估计或下一步不能足额预留时，在安全边界保存现场并提出有限追加申请。预警不强制有足够额度完成的任务等待，用户未批准前不得超额调用或自动扩额。

#### Scenario: 复杂任务在耗尽前申请追加
- **WHEN** 任务有经核实的新进展，原额度尚未耗尽但预计不足以完成剩余阶段，且无其他障碍
- **THEN** 系统生成包含证据、累计／预留消耗、剩余目标、继续策略、各维追加及估计不确定性的申请，安全释放执行位并正常等待批准，其他合格任务可运行

#### Scenario: 预警后现有额度足够完成
- **WHEN** 任一维度达到 80% 且可依据现有证据确认剩余额度足够
- **THEN** 系统可在原授权内继续，不仅因预警比例暂停或请求追加

#### Scenario: 下一必要步骤无法足额预留
- **WHEN** 尚有未耗尽余额但不足以预留下一步上界
- **THEN** 系统不发起该步，保存续期申请并正常等待，不缩小预留假装够用；已实际耗尽则按全局阻塞处理

#### Scenario: 预算已耗尽或无进展
- **WHEN** 任一授权上限耗尽，或任务已触发无进展／其他执行障碍
- **THEN** 系统保持阻塞及全局暂停，追加额度不自动解除障碍，不能用续期等待代替阻塞

#### Scenario: 没有额度调用模型生成续期报告
- **WHEN** 剩余额度不足以支持估算模型调用
- **THEN** 系统从持久产物生成报告，未知估计标为待核实并允许用户选择有限额度，不为申请预算先超额消耗

### Requirement: 续期批准绑定账本且只增加有限授权

系统 SHALL 持久化单一待处理续期修订，批准绑定主任务／预算归属、账本与申请修订、输入及进展水位，并记录用户、依据和各维有限增量。新总额等于原授权加已批准增量，已用量及无进展历史不变；不自动调整独立安全上限、不转移共享扫描成本、不扩大任务范围。任务恢复仍须核验当前前置条件及适用暂停。

#### Scenario: 同一申请被重复批准
- **WHEN** 用户双击批准或网络重发同一申请及操作
- **THEN** 增量只入账一次，返回原结果，不重复加额或新建任务

#### Scenario: 申请过期或新消耗使依据变化
- **WHEN** 批准前账本／输入／进展修订已变化
- **THEN** 系统返回冲突并刷新申请，不能按旧摘要追加；同一预算归属的同一申请修订不产生多份待办

#### Scenario: 正常续期等待获批
- **WHEN** 用户批准未耗尽且无阻塞任务的有限追加
- **THEN** 系统保留累计值，重核输入、代码、配置、预算、扫描和安全条件后重新排队；另有全局／仓库暂停时继续等待显式恢复

#### Scenario: 用户拒绝追加或改变任务目标
- **WHEN** 用户拒绝申请、明确取消，或要求修改任务范围／验收
- **THEN** 系统分别保留等待、按明确选择取消，或进入方案确认；不擅自续跑、不降低验收换取完成

### Requirement: 释放执行位前确认写命令结束

系统 SHALL 在取消、暂停或进入正常等待前停止或隔离遗留写命令，确认安全后再释放工作区和执行位。

#### Scenario: 用户取消正在运行的检查
- **WHEN** 检查的子进程仍在写工作区
- **THEN** 系统不得先释放执行位供下一任务复用该现场

### Requirement: 异常恢复先对账再人工恢复

系统 SHALL 对异常遗留运行核对业务记录、检查点、代码、产物、旧命令和远端操作，并等待用户明确恢复；有意挂起或正常 PR 等待不得被误判为崩溃。

#### Scenario: 等待 PR 时重启
- **WHEN** 重启前任务已安全进入 PR 正常等待且没有遗留执行
- **THEN** 系统恢复等待及同步，不仅因存在检查点或开放 PR 而全局阻塞

#### Scenario: 进程异常退出
- **WHEN** 重启发现无法解释的执行中运行或远端副作用
- **THEN** 系统维持全局暂停，完成核对后由用户决定恢复

### Requirement: 阻塞时仅允许明确授权的有界排障

系统 SHALL 在用户明确请求、旧执行已核实停止的条件下独占执行位进行具有单独有限预算的诊断；诊断不得修改业务代码、发布 PR、重置业务预算或自动解除全局暂停。

#### Scenario: 验证调整后的供应商配置
- **WHEN** 用户在阻塞状态发起能力诊断
- **THEN** 系统记录诊断结果和消耗，常规队列仍保持暂停，直到用户明确恢复
