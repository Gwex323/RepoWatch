# Design

## Context

动机见 `proposal.md`。本设计以 2026-10-29 已获取的远程默认分支快照 `f8e91ed45a463d3d056856da57d59cfbbef46a5a` 作只读依据，使用 `git show origin/HEAD:<path>` 检查；当前工作区仍在 `feature/schedule-history` 的 `02f5295`，不能以工作区旧代码代表最新主干，也不据此声明部署状态。

| 已观察到的实现 | 设计落点 |
| --- | --- |
| `Analyses` 在保存最终报告时插入发现，默认状态为 `waiting_reproduction`；`feedback` 写入 owner 确认并调用修复入队 | 将资格产生点移到有效最终报告落库，分析完成和候选来源同事务保存 |
| `Repairs.current` 要求 `confirmed`、owner 反馈及相同 revision；`enqueue_in` 保存 `context.confirmation`，`backfill` 只查 confirmed | 建立共享资格判定及独立来源实体，入队和后续执行共同使用 |
| `claim`、恢复器和发布阶段有开关、租约、账号、源码、预算等校验 | 仅替换人工确认依赖，逐入口核对其他约束与取消状态 |
| `Acceptance._repairs`、`_followup` 依赖 owner 确认；后者生成 confirmed 发现并继承原授权 | 支持来源链为分析候选的验收续办，不制造 owner 确认 |
| `finding_continuation.py` 用当前历史复查、源码、scope 及旧 owner 确认创建新发现 | 接续改为当前证据产生候选，替换旧 owner 确认条件；保留范围重新审查和旧任务取消 |
| `historical_review.py` 只收集 confirmed/waiting_reproduction；`task_scopes.py` 用 confirmed 推断状态 | 纳入新候选；模型判断、本人历史事实及任务范围结论分开表达 |
| `publish` 硬编码“已由工作台用户确认复现”；`repair_model.py` 读取 confirmation 并要求 owner-confirmed | 模型输入与发布文案按真实来源生成 |
| `app.py`、`dashboard.py`、前端依赖 waiting_reproduction 计数、筛选及按钮 | 一次适配状态、计数、API 和页面，并提供旧数据提示 |

主规格库为空。现有中央调度草案和 ADR 0018 的“仅 owner 确认可修复/续办”规则将被本变更对目标仓库发现的新规则取代，须在实施分支同步相关说明。专用 RepoWatch 自身维护任务继续使用其独立维护授权，不能让新候选规则替换维护、合并或部署权限。

## Goals / Non-Goals

**Goals:**

- 将“分析发现允许尝试修复”与“本人已复现”“自动验证通过”分开存储与展示。
- 用单一资格规则贯穿修复与验收链路，避免去掉入队门槛后仍在发布或续办阶段受阻。
- 沿用自动修复开关及现有启用状态，新候选在开关开启时无需逐项授权。
- 通过可重放的候选登记和已有唯一任务约束，覆盖重启、并发及错过完成回调的情况。

**Non-Goals:**

- 不增加替代人工确认的新模型角色或额外“确认”流程；已有分析独立审查仍生成有效最终报告。
- 不扩展修复次数、验收额度、合并或部署授权，不删除运行环境与自动回归验证。
- 不将历史待复现积压直接标为有效候选，不把安装升级视作旧任务的重试请求。

## Decisions

### 1. 候选状态与来源实体独立于本人反馈

新增发现状态 `repair_candidate`，含义是“分析已完成，可按策略尝试修复”，UI 根据修复任务与开关派生“待修复／修复中／等待条件”等文案。旧 `confirmed` 保留其真实历史意义；旧 `waiting_reproduction` 显示“历史待重新分析”。不改写范围审查中既有 `confirmed` 结论的语义。

建议新增 `finding_repair_origins` 表：以 finding ID 唯一关联，保存 `kind`（`analysis_review`、`legacy_owner`、`acceptance_followup`、`current_recheck`）、策略版本、analysis ID、revision、fingerprint、trigger_key、报告或有效复查的摘要标识、来源记录/根发现引用和时间。账号及 GitHub Issue 来源绑定继续通过现有 origin 契约核验。该表只接受服务端已验证的结果，不暴露客户端写入入口；本人处置仍写入原反馈记录。

不采用“批量改成 confirmed 并写 owner 反馈”：这会破坏历史事实，也会使 PR、指标和模型输入产生错误陈述。仅删除 `personally_reproduced` 校验也不足以打通其他入口。

### 2. 完成事务登记来源，幂等补采负责入队

新策略上线后，只有最终有效分析报告保留的发现才登记为候选。在保存发现、scope 映射、有效独立分析审查和 completed 状态的同一事务内写入来源；事务失败则候选一并回滚。原来源已存在时不覆盖历史处置、取消记录或旧依据。

分析提交完成后调用幂等入队；worker 的有界补采同时覆盖当前策略候选和既有有效 owner 确认。利用每发现唯一修复任务的约束和写事务处理并发。未配置 repairer、进程恰好退出或完成回调遗漏时，由补采补齐任务。已存在的任务返回原 ID；取消、失败、预算耗尽或已发布任务不通过补采被重新激活。

开关关闭时可以保存候选，待开启后入队；沿用既有 enabled 值，不增加逐条许可。仅模型或环境暂不可用时保存真实等待原因，按已有调度恢复；仓库暂停或依据过期不能当作环境重试。

替代方案是只依靠前端或完成回调创建任务；这无法覆盖关闭页面、重启及回调失败，故采用持久化来源和补采。

### 3. 统一资格与执行条件，保留分层校验

建议新增 `finding_eligibility.py`：返回有效来源、允许动作及稳定阻断原因。资格要求 finding 仍可处理、来源真实且与当前分析一致；`legacy_owner` 只接纳真实旧 owner 确认。运行条件继续使用现有开关、仓库暂停、模型就绪、环境忙碌、分析和源码有效性、账号/远程 origin、取消、租约及预算校验。

`Repairs.current/enqueue_in`、领取与恢复、显式重试、运行中的检查回调、发布前检查，以及验收消费和接续都接入共同规则，禁止某入口仍只检查 owner。`context` 改为记录 `repair_origin`；旧任务可读旧 `confirmation`，但服务端必须回查原数据，不能单凭 task JSON 宣称已授权。

处置与取消的版本更新在事务内完成，现有排队任务同步关闭；运行任务在下一受控步骤复查。远程调用发出后无法保证撤回，必须记录并核对真实结果，后续不重发。发布前依然要求补丁摘要、真实验证及独立修复审查与本次补丁一致。

已解决发现可保留验证记录供验收查询和展示，但不再允许新的修复执行；读取历史证明与发起新动作使用明确的不同检查，不能靠放宽 resolved 资格实现兼容。

### 4. 历史复查与验收接续使用来源链

`historical_snapshot` 纳入未关闭的 `repair_candidate`，保持同仓库过滤、数量上限和裁剪提示。旧 `human_status` 字段保留兼容，新结果提供中性的状态和来源，不能将候选计入本人确认指标。

历史待复现发现必须先重新分析。若最终报告产生新发现，按正常候选登记；若只有 `still_present` 历史复查且需接续，则沿用现有接续入口校验当前源码、origin、证据、scope 覆盖和独立范围审查，产生 `current_recheck` 候选，移除“旧发现必须 owner 确认”的依赖。该入口是历史问题的可选接续操作，不是新发现的必经人工步骤；生成后继时处理旧任务并防止重复候选。

`Acceptance._repairs` 接纳有效的分析来源与 legacy 来源，仍要求补丁、验证、独立修复审查和当前依据。`_followup` 为已映射原问题的行为失败登记 `acceptance_followup` 来源，绑定原根发现、验收运行、验收项与实际日志，并沿用原续办上限和累计预算。与原问题无关的新缺陷必须通过正常分析形成自己的来源。

### 5. API 明确停用正向人工确认，保留处置

旧 `/feedback` 接口保留用于兼容分流：认证和作用域检查后，对 `decision=confirmed` 返回 409 / `manual_confirmation_retired` 和重新分析或升级客户端提示，既不写 owner 反馈也不排队。`personally_reproduced` 仅作为弃用兼容输入被接收，不参与新资格判断。

旧 `not_reproduced` 请求委托统一处置逻辑，遵守该入口适用状态及现有原因要求；新前端全部使用 `/disposition`。候选可选择误报、未能复现或已解决，并具备现有取消修复操作。旧 `/continue` 路由按上一节的新证据规则适配，避免隐藏的本人确认要求。

不选择立即删除旧路由：旧标签页会收到难以解释的 404；也不把旧 confirmed 请求静默解释为新的修复资格。

### 6. 产品文案与证据展示同步修改

主流程表述改为“分析 → 自动修复 → 自动验证 → 独立审查 → 按现有权限发布”。问题入口使用“问题与修复”，移除必点“复现成功”按钮和人工确认催办；保留复现步骤、源码依据及历史本人反馈展示。路由中的旧 reproduction 标识可作为兼容别名，避免收藏链接失效。

`dashboard.py`、仓库列表统计与筛选按新状态统一计算，旧计数字段保留兼容或提供明确新字段，不能用“待人工复现”承载自动候选数量。模型提示词和 `repair_model.py` 输入声明真实分析来源，`publish` 仅对 legacy 记录表述历史本人确认，其余记录给出分析及自动验证证据。远程生成内容遵守仓库要求的中文标题、Issue 关联与五部分描述。

### 7. 本轮规划采用的默认选择

- 保留现有自动修复开关的启用值；新安装仍关闭。仅取消逐项本人确认，不新增总开关确认步骤。
- 历史 pending 不自动执行；从当前版本重新分析后按新规则推进。
- 不移除复现辅助角色及复现说明字段，它们仍用于分析和测试设计。
- 本轮仅创建此变更的规划文件，旧中央调度草案的冲突在实施准备任务中同步，不静默改动另一变更。

## Risks / Trade-offs

- [误报可能自动消耗修复额度] → 候选只来自有效最终报告；继续实行现有预算、修复前后回归和独立修复审查，允许用户处置和取消。
- [用户关闭问题与执行并发] → 版本校验、事务处置、运行中副作用前复查；保存已在途远程结果，不承诺撤回远程请求。
- [多处仍遗留 owner 条件] → 覆盖历史接续、验收、重试、发布、提示词与指标的定向回归，不能仅验证自动入队。
- [旧 pending 仍需一次重新分析] → 明确历史状态与入口，保证最新版本证据；避免升级时意外处理旧积压。
- [新状态造成旧版本遗漏] → 加法迁移、只读历史兼容和受控回退；保留数据库与新增候选，不靠覆盖备份消除记录。
- [已开启自动修复的用户会发现新问题直接推进] → 发布说明和开关旁文案明确新语义，保留随时关闭的入口。

## Migration Plan

1. 实施前核对 GitHub 写入账号、中文 Issue、最新实际默认分支和 `feature/` 分支；重新检查本设计涉及的具体调用点是否变化，同步中央调度草案的相关确认依赖。
2. 在隔离数据库验证加法表与版本标记；仅真实历史 owner 记录可登记 `legacy_owner` 来源。重复初始化不修改 enabled、反馈、任务状态、远程回执或已用预算。
3. 后端资格、入队、验收及 API 与前端一并交付。历史 pending 只展示重新分析入口；新策略完成的报告登记候选。旧确认请求返回明确错误。
4. 用替代模型及远程发布桩完成规格场景验证，并核对现有运行环境、预算、测试、review、远程幂等和关闭/取消行为；本轮规划不调用真实模型、不操作运行服务。
5. 按仓库约定先 review，通过后创建中文 PR，注明 Issue；仅经 GitHub 合并才能更新主干。PR 合并与运行服务部署分别记录，不将生成提案视作已实现。
6. 回退前关闭领取并排空或检查点停止活动任务，保留新增表、候选、预算及远程结果；使用兼容数据库的旧版本回退，新候选不转成 confirmed。存在新数据时不覆盖整库备份，不自动复活旧任务。
