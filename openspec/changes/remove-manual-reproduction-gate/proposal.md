# Proposal

## Why

当前仓库分析结束后，发现必须等待本人点击“复现成功”，自动修复才能继续，导致已开启自动修复的工作流仍依赖逐项操作。用户希望取消人工复现确认，由有效的分析结果直接驱动修复。

## What Changes

- **BREAKING**：新分析发现不再进入“待人工复现”流程，也不再以 `personally_reproduced` 或本人确认记录作为修复前置条件；改由服务端校验分析结果及其版本依据。
- 新发现使用独立的修复候选状态和来源依据，沿用自动修复开关；开关开启且分析有效时自动入队，关闭时展示等待开启原因。模型就绪、仓库暂停及现有执行条件继续决定能否执行。
- 将入队、领取、重试、发布前校验和验收续办统一接入新资格规则，记录分析来源，不生成虚假的本人确认。
- 更新问题页、通知、统计、历史复查、模型提示词和远程发布文案；提供误报、关闭及取消修复操作，保留复现步骤作为问题说明和回归验证素材。
- 兼容已有本人确认和修复记录。历史待复现发现不因升级直接入队，通过当前版本重新分析产生新候选；已经关闭、取消或判为误报的记录不自动复活。
- 停用旧“确认复现”写入 API，提供明确的迁移错误；保留负向反馈的兼容路径及真实历史记录。

## Capabilities

### New Capabilities

- `finding-repair-eligibility`：分析发现的自动修复资格、来源记录、历史兼容、全流程校验及工作台操作。

### Modified Capabilities

无。主规格库为空；已有代码行为在本变更中建立契约。现有 `add-central-dispatch-agent` 草案中的“仅本人确认发现可续办”等表述与本变更冲突，实施时须同步相关规划，采用明确的新来源契约。

## Impact

- 后端：`repository_analysis.py`、`repairs.py`、`acceptance.py`、`finding_continuation.py`、`historical_review.py`、`app.py`、`dashboard.py`、记忆指标与提示词；新增共享资格判断与加法存储字段。
- 前端：`analysis.tsx`、`main.tsx`、修复配置和状态展示；API 的确认操作及状态枚举需要适配。
- 文档与验证：README、自动修复与历史复查 ADR、分析/修复/验收/处置测试及相关端到端用例。
- 沿用现有运行环境、隔离测试、独立审查、预算、账号与源码校验、远程写入和合并授权；本变更不增加模型角色，不取消自动验证，不修改合并发布权限。
